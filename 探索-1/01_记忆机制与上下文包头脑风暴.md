# 01. 记忆机制与上下文包头脑风暴

> 生成时间：2026-07-07  
> 关键词：Workspace Memory、Context Pack、Workspace Digest、Trace、Asset Graph、Codex Session、上下文压缩、父子工作空间通信。

---

## 1. 先把“记忆”拆开

如果只说“记忆机制”，会非常模糊。至少要拆成 6 类：

| 记忆类型 | 作用 | 示例 | 是否稳定 |
|---|---|---|---|
| 原始记忆 Raw Trace | 保存发生过什么 | 对话、命令、MCP 调用、文件 diff、工具日志 | 不稳定但完整 |
| 工作记忆 Working Memory | 当前 Workspace 正在用的上下文 | 当前目标、当前假设、当前正在执行的计划 | 高频变化 |
| 摘要记忆 Digest Memory | 对外暴露的摘要 | 当前结论、风险、阻塞、下一步 | 中等稳定 |
| 资产记忆 Asset Memory | 被确认、有价值、可引用的内容 | 决策卡、报告、PR、测试结果、证据卡 | 较稳定 |
| 语义记忆 Semantic Memory | 可检索知识 | embedding、标签、主题、相似案例 | 稳定但可更新 |
| 程序记忆 Procedural Memory | 做事方式 | 工作流模板、节点模板、工具链模板、Prompt 模板 | 稳定且可复用 |

所以系统中的记忆不应该只是“把聊天压缩一下”，而是：

```text
Raw Trace
  → 提取 Working Memory
  → 生成 Workspace Digest
  → 固化为 Asset Memory
  → 建立 Asset Graph / Semantic Index
  → 抽象为 Procedural Memory
```

---

## 2. Workspace 需要哪些记忆？

每个 Workspace 至少应该有：

```text
Workspace Goal：这个空间要解决什么问题
Workspace State：当前状态
Workspace Digest：对外摘要
Workspace Trace：完整过程记录
Workspace Assets：输入/输出资产
Workspace Decisions：关键决策
Workspace Open Questions：未解决问题
Workspace Agent Sessions：关联 AI 会话
Workspace Context Packs：生成过的上下文包
```

可以理解为：

```text
Workspace 不是一个页面，而是一个小型记忆容器。
```

---

## 3. Context Pack 是什么？

Context Pack 不是简单摘要，也不是所有历史记录。

它应该是：

> **为了让某个接收者完成某个任务而组装的上下文包。**

接收者可以是：

- Codex；
- Claude Code；
- 普通 LLM；
- 另一个 Workspace；
- 一个节点插件；
- 人类用户；
- MCP Server 暴露出去的 Resource。

所以 Context Pack 必须有目标：

```text
Context Pack = receiver + purpose + selected context + constraints + expected output
```

---

## 4. Context Pack 和 Workspace Digest 的区别

| 对象 | 给谁看 | 目的 | 内容粒度 |
|---|---|---|---|
| Workspace Digest | 父/同级 Workspace、人类用户 | 了解当前状态 | 摘要、结论、风险、下一步 |
| Context Pack | AI Runner / 工具 / 另一个工作空间 | 完成具体任务 | 目标、约束、输入、资产、可用工具、期望输出 |
| Raw Trace | 系统/高级用户/审计 | 回溯发生过什么 | 全量记录 |
| Asset | 人/AI/工作流 | 作为稳定输入输出 | 被确认的结构化内容 |

一句话：

> Digest 负责“让别人理解我现在怎样”，Context Pack 负责“让别人接着干活”。

---

## 5. Context Pack 怎么产生？

建议采用 5 步：

```text
1. 明确接收者
2. 明确任务目的
3. 选择相关上下文
4. 压缩与结构化
5. 生成可验证输出要求
```

### 5.1 明确接收者

不同接收者需要的上下文不同：

```text
给 Codex：代码、文件路径、接口约束、测试命令、验收标准
给 Claude Code：类似 Codex，但要适配其 CLI 输入格式
给父 Workspace：当前结论、风险、阻塞、下一步
给评审节点：产出物、证据、质量标准、争议点
给工具插件：严格结构化参数
```

### 5.2 明确任务目的

同一个 Workspace，不同任务生成不同 Context Pack。

例如“GitHub Issue 同步能力” Workspace：

```text
任务 A：让 Codex 实现代码
任务 B：让评审空间检查设计
任务 C：让父空间了解当前进度
任务 D：让测试插件运行验证
```

它们需要的 Context Pack 不一样。

### 5.3 选择相关上下文

上下文来源：

- 当前 Workspace Goal；
- 当前 Workspace Digest；
- 父 Workspace Digest；
- 相关兄弟 Workspace Digest；
- 输入资产；
- 输出资产；
- 决策记录；
- 约束；
- 验收标准；
- 工具权限；
- 最近 Trace；
- 用户明确 pin 的材料；
- AI 认为相关的历史材料。

### 5.4 压缩与结构化

不能只做“摘要”，还要做结构化：

```text
目标是什么？
已确认事实是什么？
仍然是假设的是什么？
约束是什么？
不能做什么？
要输出什么？
可用工具是什么？
哪些内容必须引用证据？
```

### 5.5 输出要求

Context Pack 最后必须告诉接收者：

```text
你要产出什么？
格式是什么？
完成标准是什么？
是否允许修改文件？
是否需要先给计划？
是否需要等待人类确认？
```

## 6. Context Pack 的候选结构

```yaml
context_pack_id: cp_001
source_workspace_id: ws_github_issue_sync
receiver:
  type: ai_runner
  name: codex
purpose: implement_feature

goal: 实现 GitHub Issue 同步能力

role_instruction:
  - 你是本地编码协作 Agent
  - 优先保持现有架构
  - 先给计划，再修改代码

background:
  project_summary: 面向具体业务场景的 MCP-first AI 协作工作流系统
  workspace_summary: 当前节点目标是完成 GitHub Issue 同步能力

confirmed_facts:
  - 系统以 Asset 记录外部对象
  - GitHub Issue 应转为 issue_asset

hypotheses:
  - GitHub API 可以作为第一版实现，不一定必须走 MCP

constraints:
  - 不训练自有大模型
  - 不把 GitHub 作为唯一状态源
  - 不破坏现有资产模型

inputs:
  assets:
    - asset_requirement_github_sync
    - asset_api_notes
  files:
    - src/integrations/github/
    - docs/architecture/v3-clean-break.md

available_tools:
  - filesystem.read
  - filesystem.write
  - shell.test
  - git.diff
  - github.api

permissions:
  file_write: true
  shell_exec: true
  network: github_only

acceptance_criteria:
  - 能读取 GitHub Issue 列表
  - 能转换为系统 Asset
  - 能记录同步来源和时间
  - 至少有一个测试或演示脚本

expected_outputs:
  - implementation_plan
  - code_diff
  - test_result
  - implementation_note
  - open_questions

return_schema:
  implementation_plan: markdown
  code_diff: git_diff_ref
  test_result: structured
  open_questions: list

trace_policy:
  record_tool_calls: true
  record_files_changed: true
  summarize_session: true
```

## 7. Context Pack 生命周期

```text
Draft
  → Built
  → Sent
  → Consumed
  → Result Received
  → Summarized
  → Archived / Superseded
```

每个 Context Pack 应该记录：

- 谁生成；
- 为什么生成；
- 给了谁；
- 包含了哪些资产版本；
- 接收者产出了什么；
- 是否成功；
- 是否生成新资产；
- 是否导致 Workspace Digest 更新。

---

## 8. Context Pack 是一次性的，还是持续更新的？

建议分两种：

### 8.1 Snapshot Context Pack

一次性上下文快照。

适合：

- 给 Codex 执行一次代码任务；
- 给评审节点做一次 Review；
- 给父 Workspace 汇报一次状态。

优点：

- 可追溯；
- 可复现；
- 不会被后续变化污染。

### 8.2 Live Context Channel

持续上下文通道。

适合：

- 长时间协作会话；
- Codex 常驻某个 Workspace；
- 子 Workspace 持续向父 Workspace 汇报状态。

风险：

- 上下文容易漂移；
- 压缩策略更复杂；
- 需要 checkpoint。

MVP 建议：

> 先做 Snapshot Context Pack，再用 Workspace Digest 模拟轻量 Live Channel。

---

## 9. 父子 Workspace 如何交互？

推荐模式：

```text
子 Workspace 内部自由推进
  → 定期生成 Workspace Digest
  → 父 Workspace 读取 Digest
  → 父 Workspace 如需细节，请求 Context Pack / Asset / Trace
  → 子 Workspace 可根据父空间请求生成定制 Context Pack
```

父 Workspace 不应该默认把子 Workspace 全部上下文拉进来。

否则：

- 上下文爆炸；
- 结论被细节淹没；
- AI 误用未确认信息；
- 历史噪声污染当前判断。

---

## 10. Workspace Digest 怎么更新？

触发时机：

- Work Thread 完成；
- 关键资产产生；
- 用户做出决策；
- 节点状态变化；
- Runner 完成任务；
- 出现阻塞；
- 父 Workspace 请求刷新；
- 用户手动刷新。

Digest 生成方式：

```text
Raw Trace + 新资产 + 当前状态
  → AI 生成 Digest 草稿
  → 用户可确认/修正关键结论
  → 系统保存 Digest 版本
```

Digest 也要版本化：

```text
Workspace Digest v1
Workspace Digest v2
Workspace Digest v3
```

否则父空间看到的摘要来源无法追溯。

---

## 11. 记忆压缩不要只依赖 Codex

Codex 的压缩能力可以利用，但不应成为唯一记忆机制。

更合理的组合：

```text
Codex session memory：短期工作过程
Workspace Digest：系统侧对外摘要
Asset Graph：稳定资产和证据
Trace Store：完整历史
Context Pack：任务型上下文快照
```

这样即使换成 Claude Code：

```text
原始 Trace 还在
资产还在
Digest 还在
Context Pack 还在
只是 Runner 的内部记忆不同
```

## 12. 一个具体例子

### 父 Workspace

```text
节点：确定 AI 协作核心架构
```

### 子 Workspace A

```text
研究 Codex 作为 Workspace 核心的可行性
```

### 子 Workspace B

```text
设计 AI Runner Adapter
```

### 子 Workspace C

```text
设计 Context Pack Schema
```

### 子 Workspace A 给父空间的 Digest

```yaml
goal: 研究 Codex 作为 Workspace 核心的可行性
status: completed
conclusion:
  - Codex 适合作为首个 Runner
  - 但不应拥有系统上下文主权
risks:
  - Codex CLI 接口变化会影响集成
  - 不同 Runner 的能力不完全一致
outputs:
  - codex_runner_assessment
  - ai_runner_risk_card
next:
  - 继续设计 Context Pack 和 Adapter
```

父空间默认只看这个。

如果父空间需要更多：

```text
展开证据 → 查看测试记录 → 查看原始 Codex 会话 Trace
```

---

## 13. 暂定原则

1. Workspace 是记忆容器，不只是 UI 页面。
2. Context Pack 是任务型上下文快照，不是简单摘要。
3. Workspace Digest 是对外状态摘要，不是执行上下文。
4. Codex 可以常驻 Workspace，但系统不能把记忆主权交给 Codex。
5. 不同 Workspace 默认通过 Digest / Asset / Decision 通信。
6. 需要深挖时再按需展开 Trace。
7. MVP 先做 Snapshot Context Pack，后做 Live Context Channel。
8. Digest、Context Pack、Asset 都要版本化。
