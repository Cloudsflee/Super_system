# 06. 权威资料补充调研：工作空间记忆、开放节点、资产追溯与多模态展示

> 生成时间：2026-07-07  
> 定位：互联网补充调研材料，不等同于最终方案。  
> 目的：回应“当前设想是否有大量权威资料能够相互印证”的问题，重点考察：Workspace 记忆、Context Pack、可替换 Runner、开放节点、资产图谱、多模态展示、工作流演化、MCP-first 工具接入。  
> 资料索引：详见同目录 `资料索引_自动验证.csv`。

---

## 0. 总结论

当前方案的各个关键部件都有现实依据，但**没有一个现有项目完整覆盖你的设想**。更准确的判断是：

```text
你的系统不是复刻某个现成工具，
而是把 AI coding agent / agent memory / MCP / workflow graph / plugin ecosystem / asset provenance / local-first collaboration
这些已经存在的方向重新组合到“自托管小团队 AI 协作工作空间”里。
```

可以被外部资料印证的核心点：

| 你的设想 | 主要外部依据 |
|---|---|
| 每个 Workspace 有自己的 AI 协作核心 | Codex、Claude Code、OpenHands、SWE-agent 都围绕工作目录/仓库/运行环境工作。 |
| Runner 内部记忆不能成为系统记忆主权中心 | Codex Memories、Claude Memory、LangGraph persistence/store 均强调记忆/状态需要显式管理。 |
| Context Pack 是必要中间层 | Aider repo map、Continue context providers、MCP resources、OpenHands dynamic context、LangGraph memory/state。 |
| 子 Workspace 默认向父级返回摘要/产物，而非全量历史 | Codex Subagents、Claude Code subagents、LangGraph subgraphs。 |
| 节点可以是较大粒度的自主工作空间，而不是原子操作 | CMMN case management、Temporal workflow execution、OpenHands workspace、Claude/Codex subagent task。 |
| 开放节点/插件生态合理 | VS Code contribution points、Node-RED/n8n custom nodes、ComfyUI custom nodes、Backstage plugins/templates。 |
| 资产高于节点，需要血缘/证据/版本 | Dagster assets、W3C PROV、OpenLineage、ML Metadata、OpenTelemetry traces。 |
| 前端不应只是聊天框，而应是事件流 + 状态 + 审批 + 工具结果 | AG-UI、OpenAI Agents tracing/approval、Claude hooks、Langfuse/Phoenix tracing。 |
| 本地优先、自托管、小团队更合理 | Docker Compose、Coolify、Dev Containers、local-first/CRDT 相关资料。 |

不应被误解的点：

1. **MCP 能解决工具/资源接入，但不能单独解决业务工作流、资产图谱、团队决策、记忆版本。**
2. **LangGraph / Temporal / Dagster / n8n 等都可借鉴，但不宜直接把系统降级成其中一种。**
3. **Codex / Claude Code 可作为强 Runner，但系统必须保留 Context Pack、Digest、Trace、Asset 的所有权。**
4. **开放节点不是 SaaS 市场式审核模型，而是本地项目可声明、可启用、可追溯、可回滚的扩展模型。**

## 1. AI Runner 与 Workspace 记忆

### 1.1 OpenAI Codex：适合作为首个 Runner，但不应拥有上下文主权

来源：

- [Codex Memories](https://developers.openai.com/codex/memories)
- [Use Codex with the Agents SDK](https://developers.openai.com/codex/guides/agents-sdk)
- [Codex SDK](https://developers.openai.com/codex/sdk)
- [Codex Subagents](https://developers.openai.com/codex/subagents)

能印证的点：

1. Codex 有 memories，但官方资料把 memories 定位为跨 thread 的辅助回忆层；团队必须遵守的规则更适合放入 `AGENTS.md` 或仓库内文档。
2. Codex 可通过 MCP server/SDK 等方式被上层 Agent 或系统调用，这证明 Codex 不必只作为“人打开的终端工具”。
3. Codex Subagents 支持把任务分给子 agent 并收集结果，说明“子空间独立处理，父级收摘要”是合理模式。

对本系统的映射：

```text
Workspace System
  ├── Context Store / Asset Graph / Trace Store / Digest
  └── AI Runner Adapter
        └── CodexRunner
              └── Codex session / Codex MCP server / Codex CLI
```

设计结论：

> Codex 可以作为第一个强力 Runner，但系统记忆、资产、决策、Digest、Context Pack 必须由系统持有。

---

### 1.2 Claude Code：独立上下文、权限、hook、结构化输出，对替换 Runner 很有参考价值

来源：

- [Claude Code Memory](https://docs.anthropic.com/en/docs/claude-code/memory)
- [Claude Code Subagents](https://docs.anthropic.com/en/docs/claude-code/sub-agents)
- [Claude Code Hooks](https://docs.anthropic.com/en/docs/claude-code/hooks)
- [Claude Code CLI Reference](https://docs.anthropic.com/en/docs/claude-code/cli-reference)
- [Claude Code MCP](https://docs.anthropic.com/en/docs/claude-code/mcp)
- [Claude Agent SDK](https://docs.anthropic.com/en/docs/claude-code/sdk)

能印证的点：

1. `CLAUDE.md` / memory 是上下文注入方式，适合项目约定和长期提示，但不是业务状态数据库。
2. Subagents 有独立 context window、工具权限和 summary return，直接支持“子 Workspace 不污染父 Workspace 上下文”的设计。
3. Hooks 体现了 Agent 生命周期可事件化处理，例如工具调用前后检查、审计、阻断或提示。
4. CLI/SDK 支持非交互调用和结果流式输出的设计方向，对 `ClaudeCodeRunner` 适配有价值。

对本系统的映射：

```text
Runner 能力声明：
  - code_edit
  - shell_exec
  - mcp_tools
  - hook_lifecycle
  - structured_output
  - session_context
```

设计结论：

> 不同 Runner 的能力不一样，所以系统不能写死 Codex；应通过 Runner Adapter + capability negotiation + Result Normalizer 做兼容。

---

### 1.3 LangGraph / LlamaIndex / AutoGen / Letta：状态、记忆、上下文都必须显式建模

来源：

- [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
- [LangGraph Memory](https://docs.langchain.com/oss/python/langgraph/add-memory)
- [LangGraph Subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)
- [LlamaIndex Agent State](https://developers.llamaindex.ai/python/framework/understanding/agent/state/)
- [LlamaIndex Managing State](https://developers.llamaindex.ai/python/llamaagents/workflows/managing_state/)
- [AutoGen Memory and RAG](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/memory.html)
- [Letta Memory](https://docs.letta.com/guides/agents/memory)

能印证的点：

1. LangGraph 区分 thread-scoped state/checkpointer 与 cross-thread store。
2. LlamaIndex 强调 workflow / agent state 需要显式 `Context`，并且可序列化状态与外部资源要区分。
3. AutoGen 把 memory 检索后显式加入上下文，说明“记忆不是玄学生效，而是被取出、格式化、注入”。
4. Letta/MemGPT 系列强调多层记忆和上下文窗口管理。

对本系统的映射：

| 外部概念 | 本系统概念 |
|---|---|
| thread state / checkpointer | Work Thread / AgentSession state |
| store / long-term memory | Context Store / Asset Graph |
| subgraph | Sub Workspace / Node Workspace 内部子流程 |
| retrieved memory | Context Pack 中的 selected context |
| serializable context | Digest / Context Pack / AssetRef |

设计结论：

> Context Pack Builder 不是摘要器，而是有目标的上下文检索、裁剪、格式化、版本绑定与权限绑定模块。

## 2. MCP-first 工具接入，但不是 MCP-only

### 2.1 MCP 的适用边界

来源：

- [MCP Specification](https://modelcontextprotocol.io/specification/2025-06-18)
- [MCP Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- [MCP Resources](https://modelcontextprotocol.io/specification/2025-06-18/server/resources)
- [MCP Prompts](https://modelcontextprotocol.io/specification/2025-06-18/server/prompts)
- [MCP Roots](https://modelcontextprotocol.io/specification/2025-06-18/client/roots)
- [MCP Sampling](https://modelcontextprotocol.io/specification/2025-06-18/client/sampling)
- [MCP Elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation)

MCP 能提供：

| MCP 能力 | 对本系统的价值 |
|---|---|
| Tools | 让 AI 调用 GitHub、文件系统、数据库、部署工具、知识库等能力。 |
| Resources | 把文档、日志、截图、Issue、代码片段等作为可读上下文暴露给 AI。 |
| Prompts | 提供可复用提示模板。 |
| Roots | 声明文件系统边界，有助于本地项目权限控制。 |
| Sampling | MCP server 可以请求模型生成，适合某些工具侧智能能力。 |
| Elicitation | 工具执行中向用户请求补充信息，适合人机协作。 |

MCP 不能单独解决：

```text
Workspace 层级
资产确认与版本
团队决策冲突
工作流图变更
节点 UI
长期项目记忆
Digest 过期/争议状态
跨 Workspace 上下文策略
```

设计结论：

> MCP 是 AI 协作的工具/资源接入协议，不是业务协作内核。系统应 MCP-first，但不是 MCP-only。

---

### 2.2 没有 MCP 适配的工具怎么办？

大量开源工具不会天然提供 MCP server。可参考 VS Code、Backstage、Node-RED/n8n 的生态接入思想，把工具接入分层：

```text
L0 展示接入：iframe/link/API read-only
L1 数据导入：导入文件、Issue、任务、知识库内容
L2 API/CLI 适配：用 REST API、GraphQL、CLI、Webhook、SDK 操作工具
L3 MCP 适配：封装为 MCP server，供 AI 调用
L4 本地部署适配：Docker Compose / Coolify / Dev Container 启动服务
L5 深度节点插件：自定义 Executor + Renderer + Schema + Asset 输出
```

因此，插件 manifest 里可以声明：

```yaml
integration_modes:
  - link
  - api
  - cli
  - mcp
  - docker_compose
  - custom_renderer
```

设计结论：

> 对工具生态来说，MCP 是 AI 可用性的增强层；但开源工具进入系统还需要部署、配置、权限、UI、数据映射、资产输出等适配层。

## 3. 工作流、节点与自主工作空间

### 3.1 Temporal / Argo / Airflow / Prefect：说明“工作流执行状态和历史”很重要，但它们偏自动化调度

来源：

- [Temporal Workflows](https://docs.temporal.io/workflows)
- [Temporal Event History](https://docs.temporal.io/workflow-execution/event)
- [Argo Workflows DAG](https://argo-workflows.readthedocs.io/en/latest/walk-through/dag/)
- [Apache Airflow DAGs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dags.html)
- [Prefect Flows](https://docs.prefect.io/v3/concepts/flows)

能借鉴的点：

1. Workflow 不只是图，还包含运行状态、事件历史、失败重试、版本演化。
2. DAG 能描述任务依赖，但不等于适合全部人机协作。
3. Temporal 的 durable execution / event history 思想对 Trace Recorder 有启发。
4. Prefect/Airflow/Argo 更适合自动化任务流，本系统更偏探索式、可变更、人机协作式流程。

对本系统的修正：

```text
工作流图 = 当前路线图
NodeRun = 某次节点执行
TraceEvent = 执行过程中发生的事件
ChangeSet = 对工作流结构的变更提案
DecisionRecord = 人类/团队对变更或结论的确认
```

设计结论：

> 不应把系统做成 Airflow/Argo 式调度平台；但要学习它们对运行历史、失败、依赖、状态的严肃建模。

---

### 3.2 BPMN / CMMN：说明“非线性、人参与、动态 Case”比固定流程更适合探索型协作

来源：

- [BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2/)
- [CMMN 1.1](https://www.omg.org/spec/CMMN/1.1/)

BPMN 偏结构化业务流程，CMMN 偏 case management。你的场景更接近：

```text
不是严格固定流程，
而是有目标、有阶段、有可选任务、有人工判断、有动态增删节点的 Case。
```

对本系统的启发：

1. 主工作流可以提供路线，但不应强制所有情况按固定路径走。
2. 节点可根据上下文动态增加、跳过、回退、拆分。
3. 人类判断不是异常，而是流程的一部分。

设计结论：

> “节点 = 围绕目标运行的自主工作空间”比“节点 = 一个原子动作”更适合本项目。

## 4. 开放节点与插件生态

### 4.1 VS Code：Contribution Points 证明“平台定义接入点，用户/插件定义能力”是成熟模式

来源：

- [VS Code Contribution Points](https://code.visualstudio.com/api/references/contribution-points)
- [VS Code Extension Manifest](https://code.visualstudio.com/api/references/extension-manifest)

VS Code 的关键启发：

```text
平台不需要预置所有功能，
而是定义 package/manifest/contribution points/activation/permissions，
让扩展按约定把能力接入进来。
```

对应本系统：

```yaml
node_types:
  - type: github.issue_triage
renderer: ./renderer.tsx
executor: ./executor.ts
inputs: ./schema/input.schema.json
outputs: ./schema/output.schema.json
permissions:
  - github.read
  - github.write_labels
  - mcp.github
```

设计结论：

> 用户有权自实现节点；系统负责节点注册、权限声明、运行记录、资产接线、版本兼容和回滚。

---

### 4.2 Node-RED / n8n / ComfyUI：说明可视化节点生态可行，但本系统不能退化为“低代码自动化画布”

来源：

- [Node-RED Creating Nodes](https://nodered.org/docs/creating-nodes/)
- [n8n Creating Nodes](https://docs.n8n.io/integrations/creating-nodes/overview/)
- [ComfyUI Custom Nodes](https://docs.comfy.org/custom-nodes/overview)

这些项目证明：

1. 节点可以由社区/用户定义。
2. 节点可以有输入、输出、配置 UI、执行逻辑。
3. 画布可以承载复杂工作流。

但你的系统不同：

| 现有工具 | 主要关注 |
|---|---|
| Node-RED | 事件流、IoT、自动化。 |
| n8n | SaaS/API 自动化集成。 |
| ComfyUI | 生成式媒体 pipeline。 |
| 本系统 | AI 协作、上下文、资产沉淀、工作空间追溯。 |

设计结论：

> 可借鉴节点注册、配置、连线和自定义节点机制，但主节点粒度应更大，避免把人类协作拆成大量无意义小节点。

---

### 4.3 Backstage / Coolify / Docker Compose / Dev Containers：说明开源工具接入要同时考虑部署和软件目录

来源：

- [Backstage Plugins](https://backstage.io/docs/plugins/)
- [Backstage Software Catalog](https://backstage.io/docs/features/software-catalog/)
- [Backstage Software Templates](https://backstage.io/docs/features/software-templates/)
- [Docker Compose](https://docs.docker.com/compose/)
- [Docker MCP Catalog and Toolkit](https://docs.docker.com/ai/mcp-catalog-and-toolkit/)
- [Coolify Docs](https://coolify.io/docs)
- [Dev Containers Specification](https://containers.dev/implementors/spec/)

对本系统的启发：

1. 需要一个类似“项目工具目录 / 能力目录”的东西，而不是只做 MCP server 列表。
2. 工具接入要同时描述：用途、部署方式、访问地址、凭据、MCP/API/CLI 能力、适用工作流阶段。
3. Coolify/Docker Compose 更像部署运行时，不是业务核心。
4. Dev Containers 说明“把开发环境声明为文件”是成熟做法，可用于编码节点 workspace 环境。

设计结论：

> 插件市场不应只是 MCP 市场，而应是“工具/节点/模板/Runner/Context Provider/Renderer”的本地能力目录。

## 5. 资产、证据、追溯与可复盘

### 5.1 Dagster / OpenLineage / ML Metadata：资产不等于文件，资产是有血缘、版本和生成过程的对象

来源：

- [Dagster Assets](https://docs.dagster.io/guides/build/assets)
- [OpenLineage Object Model](https://openlineage.io/docs/spec/object-model/)
- [ML Metadata](https://www.tensorflow.org/tfx/guide/mlmd)

能印证的点：

1. 资产应有上游依赖和下游影响。
2. 运行记录、输入、输出、版本和元数据很重要。
3. 资产图谱可以用于理解系统状态、影响分析和复盘。

对本系统的映射：

```text
Asset
  ├── asset_type
  ├── content / external_ref
  ├── version
  ├── status: draft | confirmed | stale | disputed | archived
  ├── produced_by: NodeRun / WorkThread / HumanDecision
  ├── evidence_refs
  └── relations: depends_on / supersedes / contradicts / derived_from / used_by
```

设计结论：

> 资产是节点之上的项目记忆层；节点产生、消费、更新资产，但资产不应被当作普通节点。

---

### 5.2 W3C PROV：用 Entity / Activity / Agent 建模“谁基于什么做了什么”

来源：

- [W3C PROV Overview](https://www.w3.org/TR/prov-overview/)
- [W3C PROV-DM](https://www.w3.org/TR/prov-dm/)

W3C PROV 的核心思路可以简化借鉴：

| PROV | 本系统 |
|---|---|
| Entity | Asset / Document / Code / Decision / Context Pack |
| Activity | NodeRun / ToolCall / AI Run / Review |
| Agent | Human / AI Runner / MCP Server / Plugin |
| wasGeneratedBy | 资产由哪个活动生成 |
| used | 活动使用了哪些资产 |
| wasAssociatedWith | 活动由谁执行或参与 |

设计结论：

> TraceEvent 和 AssetRelation 不是附属日志，而是全流程追溯的核心数据结构。

---

### 5.3 OpenTelemetry / Langfuse / Phoenix / Weave / LangSmith：AI 协作需要可观测性，不只是保存聊天记录

来源：

- [OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/)
- [OpenTelemetry GenAI Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/)
- [Langfuse Tracing](https://langfuse.com/docs/tracing)
- [Arize Phoenix Tracing](https://arize.com/docs/phoenix/tracing/llm-traces-1)
- [W&B Weave Tracing](https://weave-docs.wandb.ai/guides/tracking/tracing)
- [LangSmith Observability](https://docs.langchain.com/langsmith/observability)

对本系统的启发：

1. 一个 AI 工作过程应该有 trace/span/event，而不是只记录最终文本。
2. 应区分用户输入、模型调用、工具调用、检索、文件修改、测试、审批。
3. 观测数据可用于复盘、调试、质量评估和责任追踪。

设计结论：

> `Trace Recorder` 应成为核心模块；MVP 可以简化，但至少应记录 AI 调用、工具调用、输入资产、输出资产、人工确认和失败原因。

## 6. Context Pack 的外部先例

### 6.1 Aider Repo Map：上下文包不是全量材料，而是结构化地图

来源：

- [Aider Repository Map](https://aider.chat/docs/repomap.html)
- [Aider repo map blog](https://aider.chat/2023/10/22/repomap.html)

Aider 的 repo map 证明：

```text
给代码 Agent 的上下文不应只是“把所有文件塞进去”，
而是提供一张经过选择、压缩、结构化的代码库地图。
```

对本系统的启发：

```text
Context Pack = 任务目标 + 关键事实 + 约束 + 相关资产 + 文件/Issue/Trace 引用 + 可用工具 + 预期输出
```

---

### 6.2 Continue Context Providers：上下文来源可以插件化，用户可以选择

来源：

- [Continue Context Providers](https://docs.continue.dev/customize/deep-dives/custom-providers)

Continue 的 `@file`、`@codebase`、`@terminal`、`@docs`、MCP 等上下文来源说明：

1. Context Provider 可以插件化。
2. 用户应能主动选择某些上下文。
3. AI 不应该神秘地“知道一切”。

对应本系统：

```text
Context Pack Builder
  ├── AssetProvider
  ├── TraceProvider
  ├── GitProvider
  ├── IssueProvider
  ├── KnowledgeBaseProvider
  ├── MCPResourceProvider
  └── UserPinnedProvider
```

设计结论：

> 用户应拥有 pin/unpin 材料、预览上下文包、查看“为什么包含这些材料”的能力。

---

### 6.3 OpenHands / SWE-agent：编码节点必须是工作空间，不是聊天框

来源：

- [OpenHands SDK](https://docs.openhands.dev/sdk)
- [OpenHands Agent API](https://docs.openhands.dev/sdk/api-reference/openhands.sdk.agent)
- [OpenHands paper](https://arxiv.org/abs/2407.16741)
- [SWE-agent paper](https://arxiv.org/abs/2405.15793)
- [SWE-agent ACI docs](https://swe-agent.com/0.7/background/aci/)
- [SWE-bench](https://arxiv.org/abs/2310.06770)

这些资料共同说明：

1. 代码 Agent 需要工作目录、shell、编辑、测试、版本控制、反馈循环。
2. Agent-Computer Interface 会显著影响软件工程 Agent 的效果。
3. 真实 GitHub Issue 解决能力需要 repository context、test feedback、patch/diff 等。

对本系统的设计约束：

```text
编码节点应该包含：
  - 需求 / Issue / 验收标准
  - 相关资产与 Context Pack
  - branch / diff / commit / PR
  - test command / test result
  - AI 执行记录
  - 人工 review
  - 产物资产化
```

设计结论：

> 编码节点本质是“实现工作空间”，不是一个“让 AI 写代码”的聊天输入框。

## 7. 多模态展示与动态产物

### 7.1 Jupyter / Observable / Streamlit / Gradio / Storybook：产物可以是交互式页面，不必只是静态文档

来源：

- [Jupyter Notebook documents](https://docs.jupyter.org/en/latest/projects/architecture/content-architecture.html)
- [Observable Framework](https://observablehq.com/framework/)
- [Streamlit concepts](https://docs.streamlit.io/get-started/fundamentals/main-concepts)
- [Gradio quickstart](https://www.gradio.app/guides/quickstart)
- [Storybook docs](https://storybook.js.org/docs)

对资产展现形式的启发：

| 展现形式 | 适合资产 |
|---|---|
| Markdown / 文档 | 决策、调研、说明、复盘。 |
| 表格 / 看板 | 任务、Issue、候选工具、实验结果。 |
| 图谱 | 资产关系、工作流依赖、证据链。 |
| Notebook | 数据分析、实验过程、可执行推理。 |
| Dashboard | 指标、进度、质量趋势。 |
| Storybook-like 页面 | UI 组件、节点 Renderer、交互原型。 |
| 小型交互应用 | Demo、推荐结果、工具选择向导。 |

关键判断：

```text
资产不一定是静态的。
资产可以有多个 ViewSpec，
同一个资产可以被 Markdown、表格、图谱、网页、Notebook 等方式展示。
```

设计结论：

> “资产内容”和“资产展示”应分离：Asset 保存语义和版本，ViewSpec 决定前端如何展示。

---

### 7.2 AI 是否能直接修改前端展示？

结合上述资料，更稳妥的分层是：

```text
Asset 数据层：系统持有，版本化。
ViewSpec 展示层：声明资产可如何展示。
Renderer 渲染层：插件或内置组件实现。
AI 生成层：AI 可以生成 ViewSpec 草稿或 Renderer 代码草稿。
Review/Enable 层：用户/开发者确认后启用。
```

不建议：

```text
AI 直接在线改正式前端，并立即影响所有人。
```

建议：

```text
AI 生成一个展示方案 → 保存为候选 ViewSpec / Renderer 草稿 → 用户预览 → 启用/回滚。
```

设计结论：

> 多模态展示可以动态，但动态变更本身也要进入 Trace 和 ChangeSet。

## 8. 本地优先、多人协作与冲突处理

### 8.1 Local-first / CRDT：适合长期方向，MVP 不必一开始做完整实时协作

来源：

- [Ink & Switch Local-first Software](https://www.inkandswitch.com/local-first/)
- [Yjs Docs](https://docs.yjs.dev/)
- [Automerge Docs](https://automerge.org/docs/hello/)
- [Cambria](https://www.inkandswitch.com/cambria/)
- [Potluck](https://www.inkandswitch.com/potluck/)

这些资料支持：

1. 本地优先软件强调用户拥有数据、离线可用、同步协作。
2. CRDT 适合多人实时编辑，但工程复杂度不低。
3. Cambria/Potluck 提醒：数据结构会演化，用户会需要可塑性和自定义展示。

对本系统的选择：

```text
MVP：PR-like ChangeSet + version + review + merge
长期：局部引入 CRDT / local-first sync
```

设计结论：

> 小团队自托管场景下，先做可审查的变更提案，比一开始做完整实时 CRDT 更稳。

### 9.1 Agent 记忆、反思、行动、技能库

来源：

- [Generative Agents](https://arxiv.org/abs/2304.03442)

## 10. 对当前系统的进一步修正建议

### 10.1 核心模型建议稳定为四层

```text
Project Workspace：项目级容器，管理目标、成员、全局资产、工具目录、主工作流。
Node Workspace：主工作流中的自主工作单元，围绕一个目标推进。
Work Thread：节点内部的具体协作线程，承载 AI run、人工讨论、工具调用。
Asset Graph：高于节点的项目记忆层，记录资产、版本、证据和关系。
```

### 10.2 核心模块建议稳定为七个

```text
Context Pack Builder
AI Runner Adapter
Tool/MCP Bridge
Trace Recorder
Asset Extractor / Asset Manager
Workflow ChangeSet Manager
ViewSpec / Renderer Runtime
```

### 10.3 插件市场建议从“工具市场”升级为“能力市场”

插件可包含：

```text
Node Type
Tool Connector
MCP Server config
Context Provider
Asset Type
ViewSpec / Renderer
Runner Adapter
Workflow Template
Deployment Recipe
```

这样才能解决：

```text
用户根据项目需要随取随用，
而不是平台自带一堆无效功能。
```

### 10.4 第一版 MVP 可验证的闭环

```text
1. 创建 Project Workspace
2. 通过向导描述目标、角色、已有工具
3. AI 推荐候选工具链和工作流
4. 用户确认生成主工作流
5. 进入一个 Node Workspace
6. 系统生成 Context Pack，用户预览/调整
7. CodexRunner / SimpleRunner 执行
8. 记录 TraceEvent
9. 产出 Asset 候选
10. 用户确认资产
11. 更新 Workspace Digest
12. 父工作空间读取 Digest，并可提出 ChangeSet
```

### 10.5 毕设论文中可写的差异化表达

> 现有工作流系统多关注自动化任务编排，现有 Agent 框架多关注单次 Agent 执行或多 Agent 协作，现有知识库多关注内容沉淀而缺少过程追溯。本文面向小团队自托管 AI 协作场景，提出一种分层工作空间模型，将工作流节点抽象为具备自主执行、上下文管理和产物沉淀能力的 Node Workspace，并通过 Context Pack、Workspace Digest、Trace 和 Asset Graph 实现 AI 协作过程的可观测、可介入、可复盘与可复用。

## 11. 当前仍没有被现有资料完全解决的问题

这些问题仍需要你自己的设计，而不是简单照搬开源项目：

1. **Context Pack 的质量如何评价？** 现有工具多有上下文机制，但很少定义“上下文包是否足够好”的评价指标。
2. **资产从 Trace 中自动抽取到什么程度？** 过度自动化会污染资产库，过度人工确认会增加负担。
3. **节点粒度如何在 UI 上自然表达？** 现有可视化工作流多偏原子节点，你的节点更像自主工作空间。
4. **父子 Workspace 的上下文如何逐级展开？** Subagent 只返回 summary，但项目协作需要可追溯展开。
5. **用户自定义节点如何兼顾自由度和学习成本？** VS Code/Node-RED 证明插件可行，但不直接解决面向毕业设计场景的 UX。
6. **工作流推荐如何保持一致性？** 需要模板库、约束、评分、版本和解释，不能完全依赖随机生成。
7. **错误的人类纠偏如何处理？** 需要 disputed/stale/superseded 状态和证据追溯。
8. **事实变化后如何更新资产和下游节点？** 需要 stale 标记、影响分析和重新执行建议。
9. **多 Runner 替换是否真能无缝？** 可替换架构可行，但不同 Runner 能力差异很大，实际需要降级策略。
10. **MCP server 的本地部署如何产品化？** Docker/Coolify 可辅助，但还需配置、凭据、权限和健康检查。
