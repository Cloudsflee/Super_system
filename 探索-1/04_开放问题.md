# 04. 开放问题

> 生成时间：2026-07-07  
> 说明：这些问题暂时不要急着写入“核心想法”，除非后续进一步确认。

---

## 1. Context Pack 相关

### Q1. Context Pack 是用户可见的吗？

候选：

1. 默认隐藏，只显示摘要；
2. 用户可预览关键字段；
3. 高级用户可完整编辑；
4. 每次发给 Runner 前都必须确认。

倾向：

> MVP 可以让用户预览“目标、约束、输入资产、可用工具、预期输出”，不必展示完整 JSON。

---

### Q2. Context Pack 应该自动生成还是用户参与生成？

候选：

```text
全自动：系统根据工作空间生成
半自动：AI 生成，用户确认关键上下文
手动：用户选择资产和约束
```

倾向：

> 半自动更合理。否则容易把错误上下文喂给 Codex。

---

### Q3. Context Pack 太长怎么办？

可能策略：

- 分层压缩；
- 只给 Digest + 资产引用；
- 让 Runner 按需请求更多上下文；
- 使用 retrieval；
- 根据任务类型裁剪；
- 用户 pin 关键材料；
- 过期信息不默认加入。

---

### Q4. Context Pack 是否应该包含未确认信息？

候选：

- 可以包含，但必须标记为 hypothesis；
- 默认不包含，除非任务需要探索；
- 未确认信息只能作为“待验证材料”。

倾向：

> 可以包含，但必须明确区分 confirmed_facts 和 hypotheses。

---

## 2. Workspace Digest 相关

### Q5. Digest 由谁生成？

候选：

- Codex 生成；
- 系统普通 LLM 生成；
- 当前 Workspace 的 active Runner 生成；
- 多来源生成，系统归一化；
- 用户手动写。

倾向：

> 可以由 Agent 生成草稿，但系统保存版本，用户可确认关键结论。

---

### Q6. Digest 是否需要用户确认？

不是所有 Digest 都需要强确认，否则交互成本过高。

候选：

| Digest 类型 | 是否需要确认 |
|---|---|
| 普通进度摘要 | 不一定 |
| 决策摘要 | 需要 |
| 对父空间可见的重要结论 | 建议确认 |
| 自动运行日志摘要 | 不需要 |

---

### Q7. Digest 过期怎么办？

需要状态：

```text
active
stale
superseded
disputed
```

如果子 Workspace 有新关键资产或决策，旧 Digest 应标记可能过期。

---

## 3. Codex / Runner 相关

### Q8. Codex Session 如何恢复？

需要调研 Codex CLI 是否支持：

- session id；
- resume；
- history export；
- summary export；
- non-interactive mode；
- machine-readable output；
- tool call log。

这会直接影响实现方式。

---

### Q9. 如果 Runner 不支持长会话怎么办？

可以退化成：

```text
每次任务重新生成 Snapshot Context Pack
  → 调用 Runner
  → 收结果
  → 更新 Digest
```

也就是说，长会话是增强能力，不是系统必需能力。

---

### Q10. 不同 Runner 输出格式不同怎么办？

需要 Result Normalizer。

问题是：

- 由系统规则解析？
- 让 Runner 按 return_schema 输出？
- 再调用一个 LLM 做归一化？
- 人工确认关键字段？

倾向：

> return_schema + 结果归一化 + 用户确认关键资产。

---

### Q11. Runner 的内部记忆和系统 Digest 冲突怎么办？

例如 Codex 认为 A，系统 Digest 记录 B。

可能策略：

- 系统 Digest 优先；
- 冲突进入 disputed 状态；
- 让 Runner 重新读取最新 Context Pack；
- 记录冲突为问题资产。

倾向：

> 系统侧确认资产和 Digest 优先，Runner 内部记忆只是执行辅助。

---

## 4. 父子 Workspace 相关

### Q12. 子 Workspace 什么时候应该提升为主节点？

可能标准：

- 目标足够独立；
- 有明确对外交付；
- 影响多个后续节点；
- 需要单独验收；
- 被多人协作；
- 产生关键资产或决策。

---

### Q13. 父 Workspace 能否直接修改子 Workspace？

候选：

- 只能提出变更建议；
- 可以修改目标和约束；
- 可以关闭/归档子空间；
- 可以覆盖子空间 Digest。

倾向：

> 父空间可以提出目标/约束变更，但子空间内部 Trace 和资产不应被静默覆盖。

---

### Q14. 子 Workspace 之间如何避免重复工作？

策略：

- 父空间维护子空间列表和 Digest；
- 创建新子空间时先检索相似 Workspace；
- AI 提示“已有类似工作空间”；
- 资产图谱建立 `overlaps_with` 或 `depends_on`。

---

## 5. 用户体验相关

### Q15. 用户会不会被 Workspace / Sub Workspace / Work Thread 搞晕？

风险很高。

前端不一定暴露这些术语。

可以显示为：

```text
主任务
  └── 子任务
        └── 讨论/执行记录
```

内部叫 Workspace / Work Thread，UI 上可以更自然。

---

### Q16. 良好的 Context Pack 交互长什么样？

不建议给用户一个 JSON 编辑器。

更好的 UI：

```text
将发送给 Codex 的上下文：
  目标：...
  关键材料：...
  约束：...
  可用工具：...
  期望输出：...

[确认发送] [调整材料] [调整约束] [展开完整上下文]
```

---

### Q17. 用户如何知道 AI 没漏上下文？

可以提供：

- Context Pack 预览；
- “为什么包含这些材料”；
- “还有哪些相关材料未包含”；
- 用户 pin/unpin；
- AI 自检缺失上下文。

---

## 6. MVP 范围相关

### Q18. MVP 是否真的需要完整 Workspace 分层？

可能不需要。

MVP 可以只做：

```text
Project Workspace
  └── Node Workspace
        └── Work Thread
```

Sub Workspace 可以先用 Work Thread 分组模拟。

---

### Q19. MVP 是否需要 Claude Code Adapter？

不一定。

可以先做：

- AgentRunner interface；
- CodexRunner；
- MockRunner；
- 文档中说明 ClaudeCodeRunner 可扩展。

如果有时间再实现 ClaudeCodeRunner。

---

### Q20. MVP 如何证明可替换性？

可以用 MockRunner / SimpleCLIRunner 证明：

```text
同一个 Context Pack
  → CodexRunner
  → MockRunner / SimpleLLMRunner
```

即使能力不同，也能说明系统核心不绑定 Codex。

---

## 7. 当前最需要验证的事

1. Codex CLI 能否稳定接收结构化 Context Pack；
2. Codex CLI 能否输出可解析结果；
3. Codex session 能否恢复或至少可追溯；
4. Context Pack 预览是否会让用户觉得有控制感；
5. Workspace Digest 是否足以让父空间理解子空间；
6. 同一 Context Pack 给不同 Runner 是否基本可用；
7. 用户是否能理解 Work Thread，而不会觉得层级过多。
