# 05. 互联网权威资料调研：Workspace 记忆、Context Pack 与可替换 Agent Runner

> 生成时间：2026-07-07  
> 说明：本文件是在已有头脑风暴基础上，进一步通过互联网查询官方文档、论文、开源项目文档和协议规范后形成的对照调研。  
> 关注问题：是否有现有资料能印证“每个 Workspace 以 Codex/Claude Code 这类工具作为协作核心，同时用 Context Pack / Digest 做跨 Workspace 通信，并保留 Runner 可替换性”的设想。

---

## 0. 调研结论概览

当前设想不是凭空产生的，已有资料可以从多个方向印证：

1. **Workspace 内驻留 Agent 是合理的。**  
   OpenAI Sandbox Agents、Claude Code Agent SDK、OpenHands Software Agent SDK 都支持“Agent 在一个工作目录/沙箱/工作空间中读文件、改代码、跑命令、产生 artifacts”的模式。

2. **Runner 内部记忆不能替代系统记忆。**  
   OpenAI Codex Memories 文档明确提醒 required team guidance 应放在 `AGENTS.md` 或 checked-in docs 中，而 memories 只是 local recall layer；Claude Code Memory 也把 `CLAUDE.md` 和 auto memory 作为 context，而不是确定性控制层。

3. **Context Pack 有大量相似先例。**  
   Aider 的 repo map、Continue 的 context providers、Claude/Codex 的项目记忆文件、MCP Resources、OpenHands dynamic_context、LangGraph Store/Checkpointer，本质都在解决“如何把相关上下文按任务组装给 Agent”。

4. **子空间/子 Agent 返回摘要而不是全量 Trace 是成熟模式。**  
   Codex Subagents、Claude Code Subagents、LangGraph Subgraphs 都体现了“子任务独立上下文执行，向父级返回结果/摘要”的思想。

5. **可替换 Runner 可行，但不是零成本。**  
   OpenAI Agents SDK、Claude Agent SDK、OpenHands SDK、MCP、AG-UI、A2A 都说明 Agent runtime 可以被协议化/适配化；但不同 Runner 的能力、会话、权限、输出格式不同，所以需要 `AI Runner Adapter + Capability Negotiation + Result Normalizer`。

## 1. OpenAI / Codex 相关资料

### 1.1 Codex Memories：有记忆，但不能当唯一事实源

来源：[OpenAI Codex Memories](https://developers.openai.com/codex/memories)

官方文档说明：

- Memories 让 Codex 把早期 threads 中有用上下文带到未来工作中；
- 适合稳定偏好、重复工作流、技术栈、项目约定、已知坑；
- 但 required team guidance 应放在 `AGENTS.md` 或 checked-in documentation；
- Memories 应被视为 helpful local recall layer，而不是必须总是适用的规则来源；
- memories 更新不是实时的，Codex 会跳过 active / short-lived sessions，并在后台生成本地 memory files。

对当前设计的印证：

```text
Codex 内部记忆可以利用；
但系统不能把 Workspace 的唯一记忆和规则交给 Codex memories；
系统应自己维护 Workspace Digest、Asset Graph、Trace、Context Pack。
```

结论：

> Codex 可以作为 Workspace Runner，但不能成为 Workspace 记忆主权中心。

---

### 1.2 Codex 可以作为 MCP Server 被上层编排

来源：[Use Codex with the Agents SDK](https://developers.openai.com/codex/guides/agents-sdk)、[Codex SDK](https://developers.openai.com/codex/sdk)

OpenAI 文档给出一种模式：把 Codex CLI 启动为 MCP server，让 Agents SDK 调用。该 server 暴露：

- `codex()`：开始 conversation；
- `codex-reply()`：继续 conversation；
- 并让 Codex 在多个 agent turns 之间保持 alive。

对当前设计的印证：

```text
Codex 不一定只能作为一个独立终端工具；
它可以被包装为一个被系统调用的 Runner；
这与 CodexRunner / AI Runner Adapter 的设想高度一致。
```

可映射为：

```text
Workspace System
  → AI Runner Adapter
      → Codex MCP Server
          → Codex Session
```

### 1.3 OpenAI Agents SDK：sessions、tracing、approval、sandbox 支持系统侧编排

来源：

- [OpenAI Agents SDK guide](https://developers.openai.com/api/docs/guides/agents)
- [OpenAI Agents SDK Sessions](https://openai.github.io/openai-agents-python/sessions/)
- [Sandbox Agents](https://developers.openai.com/api/docs/guides/agents/sandboxes)
- [Building Reliable Agents with Memory and Compaction](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction)

官方文档强调：

- Agents SDK 适合需要 built-in sessions、tracing、guardrails、resumable approval flows 的场景；
- Sessions 可以在 multiple agent runs 之间保存 conversation history；
- Sandbox Agents 用于 agent 的答案依赖 sandbox workspace 中的实际工作，而不仅是 prompt reasoning；
- Cookbook 展示了 memory 和 compaction 这类可靠性原语。

对当前设计的印证：

```text
Workspace 内 Agent 工作不是一次 LLM 调用；
需要 session、approval、trace、sandbox workspace、compaction；
系统侧编排 Runner 是合理模式。
```

### 1.4 Codex Subagents：子任务独立上下文、父级收集结果

来源：[Codex Subagents](https://developers.openai.com/codex/subagents)

官方文档说明：

- Codex 可以 spawn specialized agents in parallel；
- 适合 codebase exploration 或 multi-step feature plan；
- 子 Agent 完成工作后由 Codex 收集结果并合成最终响应；
- Subagents 能降低主上下文污染，但有上下文管理 tradeoff。

对当前设计的印证：

```text
复杂任务不应把全部内容塞进一个主上下文；
子工作空间/子 Agent 独立处理后，返回 Workspace Digest / 结果摘要给父空间；
父空间不需要默认读取子空间全部 Trace。
```

## 2. Claude Code / Claude Agent SDK 相关资料

### 2.1 Claude Code Memory：CLAUDE.md + auto memory，但仍是 context

来源：[Claude Code Memory](https://code.claude.com/docs/en/memory)

官方文档说明：

- Claude Code 有 `CLAUDE.md` 和 auto memory；
- 二者会在 conversation 开始时加载；
- Claude 将这些 memory 当作 context，而不是 configuration；
- 如果要阻止某些行为，应使用 PreToolUse hook；
- subagents 也可以有自己的 auto memory。

对当前设计的印证：

```text
Runner 的 memory 是辅助上下文；
控制、权限、状态、事实确认仍应由系统侧掌握；
不同 Workspace / Sub Workspace 可以有自己的记忆层。
```

---

### 2.2 Claude Code Subagents：独立 context window、工具权限和 summary return

来源：[Claude Code Subagents](https://code.claude.com/docs/en/sub-agents)

官方文档说明：

- Subagents 是 specialized AI assistants；
- 当 side task 会污染主对话时，subagent 在自己的 context 中工作；
- subagent 最终只返回 summary；
- 每个 subagent 有自己的 context window、system prompt、tool access、permissions。

这几乎直接印证当前 Workspace 设想：

```text
Sub Workspace / Work Thread 可以有独立上下文；
父 Workspace 默认只接收摘要；
子空间工具权限可以不同；
子空间不应默认污染父空间上下文。
```

### 2.3 Claude Agent SDK：可编程 Agent Loop 与工具权限控制

来源：

- [Claude Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- [How the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- [Claude Agent SDK Quickstart](https://code.claude.com/docs/en/agent-sdk/quickstart)
- [Claude Code hosting](https://code.claude.com/docs/en/agent-sdk/hosting)

官方文档说明：

- Agent SDK 可嵌入 Claude Code 的 autonomous agent loop；
- SDK 可以控制 tools、permissions、cost limits、output；
- 每个 agent session 会经过 evaluate → tool call → receive results → repeat 的 loop；
- hosting 文档强调 SDK 会 spawn/supervise `claude` CLI subprocess，该 subprocess 拥有 shell、working directory、session files on disk。

对当前设计的印证：

```text
Claude Code 可以作为可编程 Runner；
Runner 有自己的工作目录、shell 和 session files；
系统需要保存 workspace 与 runner session 的映射；
这支持 AgentSession / RunnerAdapter / TraceRecorder 的设计。
```

### 2.4 Claude Hooks / Skills / Plugins：生命周期、扩展和上下文注入

来源：

- [Claude Hooks](https://code.claude.com/docs/en/hooks)
- [Claude Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- [Claude Agent SDK Hooks](https://code.claude.com/docs/en/agent-sdk/hooks)

关键点：

- Skills 是文件系统 artifact，包含说明、资源和可执行命令；
- feature overview 明确提到 subagents run their own loops in isolated context, returning summaries；
- settings 有 user / project / local / managed scopes。

对当前设计的印证：

```text
Agent 生命周期可以被事件化捕获；
权限、hook、skills、subagent、MCP 是可组合扩展点；
Workspace Trace / Result Normalizer / Plugin Runtime 的设计有现实依据。
```

### 2.5 Claude Agent Teams：子 Agent 与团队 Agent 的区别很有启发

来源：[Claude Agent Teams](https://code.claude.com/docs/en/agent-teams)

官方文档对比：

- Subagents：父 Agent 管理，子 Agent 只向父级返回结果；
- Agent teams：多个独立 sessions，通过共享任务列表和 peer-to-peer messaging 协同；
- 每个 teammate 有自己的 context window。

对当前设计的启发：

```text
Sub Workspace 更像 subagent：向父空间汇报结果；
多个 Node Workspace 并行协作时，可能更像 agent team；
MVP 先做 Digest 汇报，不做复杂 peer-to-peer agent team。
```

## 3. LangGraph / LlamaIndex / AutoGen 等 Agent 框架

### 3.1 LangGraph：thread-scoped memory 与 cross-thread store 分离

来源：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[LangGraph Memory](https://docs.langchain.com/oss/python/langgraph/add-memory)

官方文档明确区分：

- Checkpointers：保存 thread graph state，用于短期、thread-scoped memory；
- Stores：保存 application-defined data，用于长期、cross-thread memory；
- 支持 conversation continuity、human-in-the-loop、time travel、fault tolerance。

对当前设计的印证：

```text
Work Thread / AgentSession 需要短期状态；
Project / Workspace 需要长期 Store；
Trace / checkpoint / asset memory 不应该混成一个聊天历史。
```

映射：

| LangGraph | 当前系统 |
|---|---|
| Checkpointer | Work Thread / AgentSession state |
| Store | Context Store / Asset Graph |
| Time travel | Trace 回放 / 版本恢复 |
| Human-in-the-loop | 用户确认 / Review / DecisionRecord |

---

### 3.2 LangGraph Subgraphs：父图把子图当 node，但靠 input/output schema 通信

来源：[LangGraph Subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)

官方文档说明：

- subgraph 是另一个 graph 中的 node；
- 适合 multi-agent systems、复用节点集合、分布式开发；
- 关键是子图 interface，即输入输出 schema。

对当前设计的印证：

```text
Sub Workspace 可以被父 Workspace 看成一个整体；
父空间不必了解子空间内部细节；
关键是 Workspace Digest / Context Pack / Asset 输出接口。
```

---

### 3.3 LlamaIndex：Context 显式保存，Workflow 状态可跨 run

来源：[LlamaIndex Maintaining state](https://developers.llamaindex.ai/python/framework/understanding/agent/state/)、[LlamaIndex Managing State](https://developers.llamaindex.ai/python/llamaagents/workflows/managing_state/)

官方文档说明：

- AgentWorkflow 默认 stateless；
- 要维持状态，需要显式创建 Context；
- Context 可以在 run 之间传递；
- workflow state store 应是可序列化数据；
- heavyweight clients、indexes、file handles 等应放 resources，不应放 state。

对当前设计的印证：

```text
系统应显式建模 Workspace Context；
Context Pack / Digest 应可序列化；
Runner / MCP / 文件句柄属于资源或工具，不属于长期状态本身。
```

---

### 3.4 AutoGen：Memory 检索后显式注入上下文

来源：[AutoGen Memory and RAG](https://microsoft.github.io/autogen/stable//user-guide/agentchat-user-guide/memory.html)

AutoGen 的 memory 示例强调：

- Memory system 检索相关 chunks；
- 把相关内容添加到 context；
- 用于让 assistant grounded 在检索内容上回答。

对当前设计的印证：

```text
长期记忆不是自动神秘生效；
需要显式检索、格式化、注入上下文；
Context Pack Builder 本质上就是有目标的上下文检索与组装器。
```

## 4. 协议：MCP / AG-UI / A2A

### 4.1 MCP：工具与资源接入，不是完整记忆模型

来源：

- [MCP Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- [MCP Resources](https://modelcontextprotocol.info/docs/concepts/resources/)
- [OpenAI Agents SDK MCP guide](https://openai.github.io/openai-agents-js/guides/mcp/)

MCP 支持：

- Tools：让模型调用外部系统，例如数据库、API、计算；
- Resources：让 server 暴露文件、数据库记录、API 响应、截图、日志等上下文；
- Prompts：复用提示模板。

对当前设计的印证：

```text
MCP 很适合给 Workspace Runner 提供工具和上下文；
Context Pack 可以引用 MCP tools/resources；
但 MCP 本身不负责 Workspace 记忆、Digest、父子空间通信和资产版本。
```

---

### 4.2 AG-UI：Agent ↔ 前端交互协议，印证工作空间事件流

来源：[AG-UI Overview](https://docs.ag-ui.com/introduction)、[AG-UI State Management](https://docs.ag-ui.com/concepts/state)、[AG-UI GitHub](https://github.com/ag-ui-protocol/ag-ui)

AG-UI 强调：

- event-based protocol；
- agent backend 与 user-facing app 双向连接；
- streaming；
- shared state；
- human-in-the-loop approvals；
- 用户可以观察 agent 当前状态，并通过修改 state 指导 agent。

对当前设计的印证：

```text
Workspace UI 不应只是最终结果页；
Agent 执行、状态变化、工具调用、审批请求都应以事件流方式呈现；
Work Thread / Trace / UI State 可以借鉴 AG-UI。
```

---

### 4.3 A2A：Agent ↔ Agent 通信，MVP 可暂不做

来源：[A2A GitHub](https://github.com/a2aproject/A2A)、[Google A2A announcement](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/)

A2A 目标是让不同厂商、不同框架、不同 server 上的 agents 能发现能力、协商模态并协作。

对当前设计的启发：

```text
如果未来 Workspace 之间真的演变成多个独立 Agent 系统，可以参考 A2A；
但 MVP 更适合先用内部 Workspace Digest / Context Pack，而不是引入完整 A2A。
```

## 5. 代码 Agent / 开源项目的上下文组织经验

### 5.1 Aider Repo Map：Context Pack 不应是全量内容，而应是结构化地图

来源：[Aider Repository Map](https://aider.chat/docs/repomap.html)、[Aider repo map blog](https://aider.chat/2023/10/22/repomap.html)

Aider 使用 repo map：

- 生成整个 git repo 的 concise map；
- 包含重要 classes / functions / types / signatures；
- 每次变更请求时发送给 LLM；
- 帮助模型理解正在编辑的代码与其他部分的关系。

对当前设计的印证：

```text
Context Pack 不应简单塞全量文件；
代码 Workspace 应包含 repo map / selected files / diff / test commands / constraints；
上下文包应是任务相关的结构化上下文地图。
```

---

### 5.2 Continue Context Providers：上下文来源可以插件化和用户选择

来源：[Continue Context Providers](https://docs.continue.dev/customize/deep-dives/custom-providers)

Continue 的 Context Providers 允许通过 `@` 选择上下文，例如 file、code、git diff、terminal、docs、repo-map、MCP 等。

对当前设计的印证：

```text
Context Pack Builder 可以由多个 Context Provider 组成；
用户应能预览和选择哪些材料进入 Context Pack；
MCP 只是上下文来源之一。
```

---

### 5.3 OpenHands：Workspace 抽象与 Agent Server 分离

来源：

- [OpenHands Agent Server Overview](https://docs.openhands.dev/sdk/guides/agent-server/overview)
- [OpenHands Software Agent SDK](https://docs.openhands.dev/sdk)
- [OpenHands Agent API](https://docs.openhands.dev/sdk/api-reference/openhands.sdk.agent)
- [OpenHands Software Agent SDK paper](https://arxiv.org/html/2511.03690v1)

OpenHands 体现：

- agent server 管理 execution 和 streaming；
- workspace 提供 secure / isolated runtime；
- local ↔ remote workspace 可以替换；
- dynamic_context 包含 repository information、runtime information、user secrets/settings 等；
- SDK 把 agents、tools、workspace、server 分为可组合组件。

对当前设计的印证：

```text
Workspace 作为 Agent 执行容器是成熟模式；
Runner 与 workspace runtime 可以分离；
dynamic_context 与 cached/static context 应区分；
当前 Workspace + Context Pack + Runner Adapter 架构有类似工程先例。
```

## 6. Agent Memory 论文与研究

### 6.1 Generative Agents：完整记录 → 反思 → 计划

来源：[Generative Agents: Interactive Simulacra of Human Behavior](https://arxiv.org/abs/2304.03442)

论文提出：

- 存储 agent experiences 的完整自然语言记录；
- 随时间合成为 higher-level reflections；
- 动态检索记忆以计划行为；
- observation、planning、reflection 都对可信行为重要。

对当前设计的印证：

```text
Raw Trace → Workspace Digest / Reflection → Plan / Next Actions
```

这支持你的 Digest / Trace / Plan 三层设计。

---

### 6.2 MemGPT / Letta：虚拟上下文管理与多级记忆

来源：

- [MemGPT: Towards LLMs as Operating Systems](https://arxiv.org/abs/2310.08560)
- [MemGPT project](https://research.memgpt.ai/)

MemGPT 提出：

- LLM context window 有限；
- 需要 virtual context management；
- 通过在不同 memory tiers 间移动信息，模拟更大的上下文；
- 适用于 multi-session chat 和长文档分析。

对当前设计的印证：

```text
Context Pack = 当前注入快记忆的工作集；
Asset Graph / Trace Store = 慢记忆；
Digest = 压缩后的中间记忆；
系统应管理什么进入 Runner 上下文，而不是依赖 Runner 自己无限记住。
```

---

### 6.3 Voyager：技能库、执行反馈、自验证

来源：[Voyager paper](https://arxiv.org/abs/2305.16291)、[Voyager project](https://voyager.minedojo.org/)

Voyager 包含：

- automatic curriculum；
- ever-growing skill library of executable code；
- iterative prompting；
- environment feedback；
- execution errors；
- self-verification。

对当前设计的印证：

```text
工作流/节点经验可以抽象成可复用能力；
代码或插件节点可以形成技能库；
执行反馈和错误应进入 Trace / Asset / Digest。
```

---

### 6.4 SWE-agent：Agent-Computer Interface 影响 Agent 效果

来源：

- [SWE-agent paper](https://arxiv.org/abs/2405.15793)
- [SWE-agent ACI docs](https://swe-agent.com/0.7/background/aci/)
- [SWE-agent GitHub](https://github.com/swe-agent/swe-agent)

SWE-agent 研究 Agent-Computer Interface，强调：

- Agent 与计算机/仓库交互的接口设计会显著影响自动软件工程效果；
- ACI 应帮助 Agent 浏览仓库、编辑代码、执行测试、接收反馈；
- SWE-agent 支持让不同模型解决真实 GitHub 仓库问题。

对当前设计的印证：

```text
编码 Workspace 的 UI/工具接口不是附属问题，而是核心；
Context Pack + Runner Adapter + Tool Feedback 需要专门设计；
“编码节点不是聊天框，而是实现工作空间”有研究依据。
```

## 8. 对你当前方案的设计修正

### 8.1 Context Pack Builder 应成为核心模块

它不是普通摘要器，而是：

```text
输入：Workspace 目标 + Digest + 资产 + Trace + 约束 + 工具权限 + 接收者能力
输出：适配某个 Runner / Workspace / Plugin 的结构化上下文包
```

### 8.2 Workspace Digest 应该版本化，并区分确认状态

Digest 可以分：

```text
ai_draft
user_confirmed
stale
superseded
disputed
```

### 8.3 Runner Adapter 必须声明能力

例如：

```yaml
runner: codex
capabilities:
  - code_edit
  - shell_exec
  - git_ops
  - long_context
  - session_memory
  - mcp_tools
```

如果 Runner 能力不足：

```text
降级为只读分析
请求人工执行
换 Runner
拆分任务
```

### 8.4 Result Normalizer 必须存在

不同 Runner 输出差异很大，系统应归一化为：

```yaml
status: succeeded | failed | blocked | partial
summary: string
changed_files: []
generated_assets: []
suggested_decisions: []
open_questions: []
test_results: []
trace_refs: []
```

### 8.5 Workspace UI 应参考 AG-UI 思路做事件流

不是只展示最终结论，而应展示：

```text
状态变化
工具调用
用户审批
文件变化
测试结果
需要输入
输出资产
```

## 9. MVP 更合理的验证路径

### 9.1 最小闭环

```text
Workspace 目标
  → Context Pack Builder 生成上下文包
  → CodexRunner 消费上下文包
  → Runner 产出结果
  → Result Normalizer 归一化
  → Trace Recorder 记录过程
  → Asset Extractor 生成资产候选
  → 用户确认
  → Workspace Digest 更新
  → 父 Workspace 读取 Digest
```

### 9.2 可替换性验证

不必一开始完整接 Claude Code。可以先做：

```text
CodexRunner
MockRunner
SimpleCLIRunner
```

用同一个 Context Pack 测试不同 Runner：

- 是否能读取；
- 是否能产出结构化结果；
- 是否能被 Result Normalizer 处理。

### 9.3 前端验证

比较两种交互：

```text
A：用户直接把一堆上下文丢给 Codex
B：系统生成 Context Pack，用户预览后发给 Codex
```

观察：

- AI 是否少问已知信息；
- 用户是否更有控制感；
- 输出是否更符合验收标准；
- 后续能否形成 Digest；
- 父 Workspace 是否能快速理解子 Workspace。

## 10. 仍需继续调研的问题

1. Codex CLI 当前是否支持稳定 machine-readable output；
2. Codex session 是否能可靠 resume / export summary / 导出 tool log；
3. Claude Code `--output-format stream-json` 和 `--json-schema` 能否作为 ClaudeCodeRunner 基础；
4. OpenAI Codex MCP server 方式是否能满足本地 Workspace 驻留 Agent；
5. AG-UI 是否适合作为前端事件协议，还是只借鉴其思想；
6. A2A 是否在未来 Workspace 间独立 Agent 协作时值得引入；
7. Workspace Digest 的用户确认成本如何降低；
8. Context Pack 是否应该支持“用户 pin/unpin 材料”；
9. 如何防止错误 Digest 被父空间继续传播；
10. 如何在论文中把这些资料组织为“相关工作”和“设计依据”。
