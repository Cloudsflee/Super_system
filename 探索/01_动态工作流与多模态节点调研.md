# 01. 动态工作流与多模态节点调研报告

> 调研时间：2026-07-05  
> 主题：工作流如何动态修改、节点如何通用定义、多模态节点如何展示、前置信息如何影响后续节点、编码节点与 Git/GitHub 如何接入、多人协作冲突如何处理。

---

## 1. 你现在的问题在业界通常被拆成哪些问题？

你的问题表面上是“节点怎么展示”，本质上涉及 8 个子问题：

| 子问题 | 相关领域 | 典型方案 |
|---|---|---|
| 节点如何通用定义 | Workflow / DAG / BPMN / 可视化编程 | 节点协议、输入输出 Schema、节点类型、状态机。 |
| 节点如何展示 | Node editor / low-code / no-code | 画布 + 侧边栏 + 类型化工作区。 |
| 工作流如何动态改动 | CMMN / Adaptive Case Management / LangGraph / Temporal | ChangeSet、状态 checkpoint、流程实例修改、人工任务。 |
| 新输入如何影响后续 | Provenance / Data lineage / Asset graph | 依赖图、血缘、stale 标记、选择性重跑。 |
| 多模态内容如何进入流程 | AI workflow / multimodal pipeline | 原始资产 + 派生文本/结构化资产 + 向量/摘要。 |
| 编码如何进入节点 | GitHub / Git / AI coding agent | Issue、Branch、Commit、PR、Review、Test Report。 |
| 多人冲突如何处理 | Git PR / CRDT / decision records | 变更提案、评论、评审、分支、合并。 |
| AI 如何调用工具 | MCP / API / CLI / adapters | Tool/Resource、连接器、权限、运行时管理。 |

所以你的系统不应该试图用一个概念解决全部问题，而应该组合：

```text
动态工作流图
  + 节点协议
  + 资产图谱
  + 变更提案 ChangeSet
  + 版本化执行记录
  + 类型化节点工作区
  + MCP/API/GitHub 等工具接入
```

## 2. 标准与理论：流程不只有 BPMN，还有 CMMN 和 Provenance

### 2.1 BPMN：适合稳定流程，不完全适合探索性协作

来源：OMG BPMN 2.0.2 官方规范  
<https://www.omg.org/spec/BPMN/2.0.2/>

BPMN 的价值：

- 提供成熟的流程表示：Task、Event、Gateway、Sequence Flow、Lane、Subprocess。
- 适合表达相对稳定、可重复的业务流程。
- 人工任务、服务任务、消息事件等概念可直接借鉴。

对你的启发：

```text
节点可以借鉴 Task；
节点之间的边可以借鉴 Sequence Flow；
不同角色/工具可以借鉴 Lane；
子流程可以借鉴 Subprocess；
人工确认可以借鉴 User Task。
```

局限：

- 对探索性、临时插入节点、用户随时改流程、过程不断演化的支持不够自然。
- 如果直接照搬 BPMN，系统会显得很企业流程管理，而不是 AI 协作系统。

结论：

> BPMN 可借鉴概念，不宜作为完整外显模型。

---

### 2.2 CMMN：更接近你的“动态工作流”问题

来源：OMG CMMN 1.1 官方规范  
<https://www.omg.org/spec/CMMN/1.1/>

CMMN 面向 Case Management，更适合：

- 知识工作；
- 非完全预设流程；
- 人类根据上下文选择下一步；
- 可选任务、里程碑、阶段、事件监听；
- 案例过程随信息变化而演化。

对你的启发：

```text
项目可以看成 Case；
工作流阶段可以看成 Stage；
节点可以看成 Task；
用户插入前置节点可以看成动态启用 Plan Item；
阶段完成条件可以看成 Milestone；
信息变化可以触发后续节点复核。
```

结论：

> 如果你的系统是“用户和 AI 在复杂上下文中协作推进项目”，CMMN / Adaptive Case Management 的思想比纯 BPMN 更贴近。

---

### 2.3 Workflow Patterns：用来判断节点协议是否足够通用

来源：Workflow Patterns  
<https://www.workflowpatterns.com/>

Workflow Patterns 研究把工作流中常见的控制模式、数据模式、资源模式、异常模式进行分类。

对你的启发：

- 节点不只是“顺序执行”，还要考虑分支、合并、并行、取消、重试、等待、跳过。
- 工作流不一定是简单链条，而是有条件、有状态、有异常处理的图。
- “通用节点”至少要能挂接控制流、数据流、资源分配和异常处理。

建议在毕设中不要实现全部模式，但可以用它说明：

> 第一版只覆盖顺序、插入、分支、人工确认、失败阻塞、选择性重跑等核心模式。

---

### 2.4 W3C PROV：资产追溯的权威基础

来源：W3C PROV-DM  
<https://www.w3.org/TR/prov-dm/>

W3C PROV 的核心可以简化理解为：

```text
Entity：东西/资产
Activity：产生或使用资产的活动
Agent：执行活动的人、系统或组织
```

对应你的系统：

| PROV 概念 | 你的系统 |
|---|---|
| Entity | 资产：文档、截图、Commit、报告、决策卡、节点输出。 |
| Activity | 节点执行、AI 分析、工具调用、人工确认。 |
| Agent | 用户、AI、MCP Server、GitHub、Codex。 |

这非常适合你的“全流程追溯”：

```text
某个结论资产
  ← 由哪个节点执行产生
  ← 使用了哪些输入资产
  ← 谁确认
  ← 调用了哪些工具
  ← 后续被哪些节点使用
```

结论：

> 你的资产图谱可以在底层借鉴 W3C PROV 的 Entity-Activity-Agent 模型，再扩展 supports、contradicts、superseded_by 等语义关系。

## 3. 现有系统如何处理“节点”

### 3.1 Node-RED：经典的可视化节点流

来源：Node-RED 官方文档  
<https://nodered.org/docs/>

Node-RED 的特点：

- 通过节点和连线构建 Flow；
- 节点有类型、配置和输入输出；
- 有节点库和社区节点；
- 面向事件、IoT、API、自动化任务。

对你的启发：

- 节点可以由“类型 + 配置 + 输入输出端口 + 运行时”组成；
- 节点市场可以参考 Node-RED Library；
- 节点工作区不一定复杂，很多节点只需要配置面板和执行日志。

不足：

- 对 AI Trace、资产图谱、协作决策、工作流演化支持较弱。
- 更偏自动化流，不是以“人机协作资产沉淀”为核心。

---

### 3.2 n8n：工具集成工作流的代表

来源：n8n 官方文档  
<https://docs.n8n.io/>

n8n 的特点：

- 大量工具节点；
- Trigger + Action + Transform；
- 执行记录；
- 社区节点；
- 适合自动化集成。

对你的启发：

- “能力市场”可以参考 n8n 节点生态；
- 每个节点应说明输入、输出、凭证、权限和典型用途；
- 工作流执行记录很重要。

不足：

- 强项是工具自动化，不是动态项目协作和资产抽象；
- 工作流推荐、争议记录、资产版本不是核心。

---

### 3.3 Dify / Flowise / Langflow：AI 工作流节点化

来源：

- Dify: <https://docs.dify.ai/>
- Flowise: <https://docs.flowiseai.com/>
- Langflow: <https://docs.langflow.org/>

这些工具说明：AI 工作流已经普遍采用节点化设计，包括：

- LLM 节点；
- Prompt 节点；
- 知识检索节点；
- 条件判断节点；
- 工具调用节点；
- 输出节点；
- API 发布。

对你的启发：

```text
AI 节点不是特殊例外，而应成为节点类型之一；
Prompt、模型、工具、知识库、输入输出都需要显式记录；
LLM 输出必须结构化，否则后续节点难以稳定复用。
```

不足：

- 多数平台更重视“构建 AI App”，而不是“记录项目协作过程并沉淀资产”；
- 动态插入节点后的影响分析通常不强。

---

### 3.4 ComfyUI：多模态节点展示的强参考

来源：ComfyUI 官方仓库与文档  
<https://github.com/comfyanonymous/ComfyUI>  
<https://docs.comfy.org/>

ComfyUI 是多模态 AI 节点工作流的典型代表，尤其在图像生成领域。

对你的启发：

- 多模态内容可以通过节点端口连接；
- 节点参数、模型、输入图像、输出图像都应作为可追溯对象；
- 自定义节点生态很重要；
- 节点图可以保存、分享、复用。

不足：

- 更偏生成式媒体生产；
- 不处理团队决策、GitHub 编码、项目资产沉淀等问题。

结论：

> 如果你要做“多模态节点展示”，ComfyUI 很值得参考；但你的节点需要比 ComfyUI 多出协作、版本、资产、决策和工具调用语义。

---

### 3.5 React Flow / Rete.js：实现节点画布的前端基础

来源：

- React Flow: <https://reactflow.dev/>
- Rete.js: <https://retejs.org/docs/>

这类库解决的是前端交互问题：

- 节点拖拽；
- 连线；
- 自定义节点；
- minimap；
- selection；
- edge；
- layout；
- 嵌套/分组；
- 交互事件。

对你的启发：

> 它们适合做工作流画布，但不提供你的业务语义。你的核心价值不在“画线”，而在节点协议、资产追溯、变更影响分析和 AI 协作。

## 4. 现有系统如何处理“工作流执行与版本”

### 4.1 Airflow / Argo / Prefect：DAG 执行与失败处理

来源：

- Airflow: <https://airflow.apache.org/docs/>
- Argo Workflows: <https://argo-workflows.readthedocs.io/>
- Prefect: <https://docs.prefect.io/>

它们的共同特点：

- 流程定义为 DAG 或 Flow；
- 节点有运行状态；
- 支持重试、失败、日志、调度；
- 产物和参数可被记录；
- 适合自动化任务。

对你的启发：

```text
节点状态机必须明确；
节点运行记录和节点定义要分离；
失败不能被忽略，必须成为状态；
重跑应该有 run id，而不是覆盖旧结果。
```

不足：

- 多数 DAG 系统假设流程定义较稳定；
- 不以人类随时插入前置节点为核心；
- 多模态 UI 和协作决策不是重点。

---

### 4.2 Temporal：长流程、人工介入和确定性重放

来源：Temporal 官方文档  
<https://docs.temporal.io/>

Temporal 对你的系统特别有启发：

- 长时间运行的工作流；
- 外部事件通过 Signal / Update 进入；
- 状态持久化；
- 工作流版本兼容；
- 失败重试；
- 可观察执行历史。

对你的启发：

```text
用户后续补充信息，可以看成外部事件；
工作流不一定一次执行完；
执行历史应可重放或追溯；
变更工作流时要考虑旧实例和新定义的兼容。
```

不足：

- 实现复杂；
- 更偏后端执行引擎，不提供多模态节点 UI。

---

### 4.3 Dagster：Asset Graph 与你的资产工作流高度相关

来源：Dagster 官方文档  
<https://docs.dagster.io/>

Dagster 的核心启发是：工作流不是只看任务，而是看任务产生的资产。

这与你的想法非常贴近：

```text
任务/节点不是目的；
资产才是工作结果；
工作流是资产生产、更新、验证、依赖的过程。
```

对你的启发：

- 节点输出应被资产化；
- 资产依赖图比任务列表更能说明价值；
- 下游资产可以因为上游变化而变成 stale；
- materialization 记录可对应节点运行结果。

结论：

> “工作流是资产的加工过程”这一点，可以重点参考 Dagster 的 Asset Graph 思想。

## 5. 现有系统如何处理“前置信息变化影响后续节点”

### 5.1 Provenance / Lineage：不要直接覆盖，要记录依赖

来源：

- W3C PROV: <https://www.w3.org/TR/prov-dm/>
- OpenLineage: <https://openlineage.io/>
- ML Metadata: <https://www.tensorflow.org/tfx/guide/mlmd>

这类系统的共同做法：

```text
记录一次运行用了哪些输入；
记录运行产生了哪些输出；
记录输出被哪些后续任务使用；
当输入变化时，通过依赖关系找到受影响输出。
```

对你的系统：

```text
前置节点新增资料
  → 生成新资产版本
  → 查询哪些节点依赖旧资产
  → 标记后续节点 Stale / Needs Review
  → 用户决定是否重跑
```

这比“自动把后续内容全改掉”可靠得多。

---

### 5.2 ML Metadata：Artifact / Execution / Context 模型很适合借鉴

来源：TensorFlow ML Metadata  
<https://www.tensorflow.org/tfx/guide/mlmd>

MLMD 的思想可映射为：

| MLMD | 你的系统 |
|---|---|
| Artifact | 资产：报告、截图、代码、PR、调研材料。 |
| Execution | 节点运行记录：AI 分析、工具调用、人工评审。 |
| Context | 项目、阶段、工作流、版本、场景。 |

结论：

> 如果你要设计数据库表，可以把 MLMD 作为很好的参考对象。

---

### 5.3 OpenLineage：事件化记录适合跨工具集成

来源：OpenLineage  
<https://openlineage.io/>

OpenLineage 的启发：

- 不同工具通过统一事件上报 lineage；
- 关注 Job、Run、Dataset 的关系；
- 支持跨系统血缘追踪。

对你的系统：

```text
MCP 工具调用、GitHub 同步、AI 分析、人工确认
都可以作为事件写入 Trace / Lineage。
```

## 6. AI Agent 工作流如何处理动态修改和人类介入

### 6.1 LangGraph：最接近“动态 AI 工作流图”的现有框架之一

来源：LangGraph 官方文档  
<https://langchain-ai.github.io/langgraph/>

LangGraph 值得重点研究，因为它强调：

- 图结构工作流；
- 状态对象；
- checkpoint；
- human-in-the-loop；
- persistence；
- time travel；
- 分支、回放和恢复。

对你的启发：

```text
工作流运行需要 checkpoint；
用户介入可以中断和恢复；
某个历史状态可以被 fork；
AI 的下一步不应该是黑盒，而应围绕状态图执行。
```

局限：

- 它是开发框架，不是完整的协作产品；
- 资产图谱、节点多模态 UI、团队争议和 GitHub 协作仍要自己设计。

---

### 6.2 LlamaIndex Workflows / AutoGen / CrewAI：事件和多 Agent 协作

来源：

- LlamaIndex Workflows: <https://docs.llamaindex.ai/en/stable/module_guides/workflow/>
- AutoGen: <https://microsoft.github.io/autogen/>
- CrewAI: <https://docs.crewai.com/>

共同启发：

- AI 流程通常不是单次 LLM 调用；
- 需要 step、event、state、agent、tool；
- 人类反馈可作为流程事件；
- 多 Agent 分工可作为节点执行器。

对你的系统：

> 可以把这些框架当成某些节点的 Executor，而不是把整个系统做成某个框架的皮肤。

## 7. 编码节点、GitHub 与协作变更

### 7.1 GitHub PR 是工作流变更提案的强参考

来源：

- GitHub Pull Requests: <https://docs.github.com/en/pull-requests>
- GitHub Flow: <https://docs.github.com/en/get-started/using-github/github-flow>

GitHub 的基本协作模型：

```text
创建分支
  → 提交改动
  → 发起 Pull Request
  → 讨论与 Review
  → 修改
  → 合并或关闭
```

对你的系统可以映射为：

```text
工作流变更提案
  → AI 影响分析
  → 团队评论
  → 修改提案
  → 合并到当前工作流 / 拒绝 / 形成分支
```

---

### 7.2 Git 适合管代码，不适合单独管完整协作状态

来源：Git 官方文档  
<https://git-scm.com/doc>

合理分工：

```text
Git：代码、文档快照、配置；
GitHub：Issue、PR、Review、Commit；
系统数据库：工作流状态、资产关系、节点运行、决策记录；
MCP：让 AI 调用外部工具和读取资源。
```

因此编码节点可以这样设计：

```text
Code Task Node
  输入：需求资产、设计资产、关联 Issue、仓库、约束、测试要求
  执行：Codex / Claude Code / GitHub Actions / 本地命令
  输出：branch、commit、PR、diff、测试报告、实现说明
  追溯：AI Trace、命令日志、人工 Review、最终决策
```

---

### 7.3 CRDT 适合多人同时编辑，但 MVP 不一定要做

来源：

- Yjs: <https://docs.yjs.dev/>
- Automerge: <https://automerge.org/docs/>
- Local-first software: <https://www.inkandswitch.com/local-first/>

如果未来多人实时编辑同一个工作流图，需要考虑：

- 冲突合并；
- 离线编辑；
- 实时协作光标；
- 本地优先同步。

但对毕设 MVP 来说，可以先不做完整 CRDT，而采用更简单的：

```text
单用户编辑锁 / 乐观锁
  + ChangeSet 记录
  + 审批确认
  + 版本回滚
```

## 8. MCP 与工具接入如何放进节点体系

来源：

- MCP 官方文档: <https://modelcontextprotocol.io/>
- MCP 规范: <https://modelcontextprotocol.io/specification/>
- MCP Servers: <https://github.com/modelcontextprotocol/servers>
- Docker MCP Catalog/Toolkit: <https://docs.docker.com/ai/mcp-catalog-and-toolkit/>
- MCPHub: <https://github.com/samanhappy/mcphub>

MCP 对你的节点体系的价值：

```text
节点需要能力
  → 能力可以来自 MCP Tool / Resource
  → AI 可以在节点上下文中调用工具
  → 工具调用结果转为资产
  → 调用记录进入 Trace
```

但 MCP 不能替代节点协议：

| MCP 解决 | MCP 不直接解决 |
|---|---|
| AI 如何调用工具 | 工作流节点怎么展示 |
| 工具/资源如何暴露 | 节点产出是否达标 |
| Server/Client 通信 | 团队争议如何决策 |
| 外部能力接入 | 资产关系和版本如何维护 |

结论：

> MCP 应作为节点可调用能力层，而不是把每个节点都等同于一个 MCP Tool。

## 9. 多模态节点当前通常怎么做？

### 9.1 常见处理方式

现有方案通常把多模态内容拆成三层：

```text
原始文件层：图片、音频、视频、PDF、代码、网页、截图
派生内容层：OCR 文本、ASR 转写、图像描述、摘要、embedding、结构化元数据
展示层：缩略图、播放器、正文、卡片、图谱、时间线、报告
```

这对你的系统很重要，因为不能让所有节点只处理文本。

例如一个“前期调研节点”可能输入：

- 老师语音；
- 截图；
- PDF；
- 网页链接；
- GitHub 仓库；
- 手写草图；
- 对话记录。

系统应该做：

```text
保存原始资产
  → 调用 AI/工具生成派生资产
  → 用户确认派生理解是否正确
  → 作为后续节点输入
```

---

### 9.2 ViewSpec 比 AI 直接生成前端代码更稳

已有系统大多采用固定组件或节点渲染器，而不是让 AI 随机生成 UI。

适合你的设计：

```text
Asset Data
  + Asset Relation
  + ViewSpec
  + 固定 Renderer
  → 多模态节点工作区
```

例如：

```json
{
  "view_type": "research_node_workspace",
  "layout": "split",
  "panels": [
    {"type": "asset_wall", "query": "inputs"},
    {"type": "evidence_table", "query": "evidence"},
    {"type": "decision_panel", "query": "pending_decisions"}
  ]
}
```

结论：

> AI 可以建议展示结构，但系统应通过固定 ViewSpec 和 Renderer 渲染，避免 AI 任意生成和执行前端代码。

## 11. 最适合你的组合方案

## 12. 关键结论

1. **节点可以通用定义，但只能通用协议，不能通用内部行为。**  
   通用的是输入、输出、状态、版本、执行、证据、验收；具体展示和执行必须按节点类型分化。

2. **节点不是页面，而是工作单元。**  
   页面只是节点的一种展示方式；节点还包括执行器、资产依赖、状态机和版本。

3. **工作流不是静态流程图，而是可演化的动态图。**  
   用户随时插入节点是合理需求，但必须通过 ChangeSet、影响分析和确认机制。

4. **前置节点变化不应自动覆盖后续节点。**  
   正确做法是通过资产依赖标记后续节点 stale / needs review / rerun suggested。

5. **多模态内容必须资产化。**  
   图片、音频、PDF、网页、代码都应保存原始资产，并生成可确认的派生资产。

6. **编码节点可行，但要和 Git/GitHub 绑定。**  
   Codex/Claude Code 应作为 Code Task Node 的执行能力，而不是系统里到处出现的自由聊天框。

7. **Git 不能替代系统数据库。**  
   Git 管代码版本，GitHub 管协作对象，系统数据库管工作流语义、资产关系和决策记录。

8. **协作争议要结构化。**  
   观点、争议、决策、变更提案都应成为资产，而不是淹没在聊天记录中。

9. **MCP 是能力调用层，不是完整工作流模型。**  
   MCP 很重要，但节点协议、资产图谱、版本、协作和展示仍然需要系统自己定义。

10. **MVP 应避免一口吃成完整平台。**  
    最小可行方案可以先做：动态节点图、节点详情、资产输入输出、ChangeSet、GitHub 关联、一个 AI 分析节点、一个人工决策节点、一个资产沉淀节点。
