# 03. 对毕设设计的启发：如何落地“动态多模态工作流节点”

> 调研时间：2026-07-05  
> 目的：把调研结果转化为你当前毕设可以使用的设计原则、数据模型草案和 MVP 切法。

---

## 1. 核心判断

你要做的节点系统不应该追求“一个节点页面适配所有事情”。

更合理的定义：

> **节点是工作单元，不是页面。节点的通用性来自统一协议，节点的差异性通过类型化 Renderer 和 Executor 实现。**

因此系统分层应是：

```text
Workflow Graph
  ├── WorkflowNode：节点定义
  ├── WorkflowEdge：依赖/顺序/条件边
  ├── NodeRun：节点执行记录
  ├── Asset：输入输出资产
  ├── AssetRelation：资产关系
  ├── WorkflowChangeSet：工作流变更提案
  ├── DecisionRecord：决策记录
  └── TraceEvent：AI/MCP/GitHub/人工操作事件
```

---

## 2. 建议采用的节点三层展示

### 2.1 流程图卡片

用于看全局，信息要少：

```text
[竞品分析]
状态：Needs Review
输入：需求调研 v2、目标说明 v1
输出：竞品分析报告 v1
风险：新增信息影响任务拆解
工具：Web Search / 知识库 / AI 分析
```

### 2.2 节点详情面板

用于解释节点为什么这样：

- 节点目标；
- 输入资产；
- 输出资产；
- 依赖关系；
- 执行记录；
- AI Trace；
- MCP 调用；
- 人工确认；
- 版本历史；
- 受影响后续节点。

### 2.3 节点工作区

根据类型切换：

| 节点类型 | 工作区 |
|---|---|
| Human Input Node | 文件、截图、语音、链接、文本输入区。 |
| AI Analysis Node | Prompt、模型输出、证据侧栏、人工修订。 |
| MCP / Tool Node | 工具配置、调用参数、调用结果、Trace。 |
| Code Task Node | GitHub Issue、Branch、Diff、Commit、PR、测试报告。 |
| Review / Decision Node | Checklist、争议、评论、通过/驳回、决策记录。 |
| Asset Output Node | 资产卡、模板、复盘、项目记忆页、导出。 |

## 3. WorkflowNode Schema 草案

```ts
type WorkflowNode = {
  id: string
  workflow_id: string
  type:
    | 'human_input'
    | 'ai_analysis'
    | 'mcp_tool'
    | 'code_task'
    | 'review_decision'
    | 'asset_output'

  title: string
  goal: string
  description?: string

  input_refs: AssetRef[]
  output_specs: OutputSpec[]
  required_capabilities: CapabilityRequirement[]

  acceptance_criteria: AcceptanceCriterion[]
  quality_checks: QualityCheck[]

  status:
    | 'draft'
    | 'ready'
    | 'running'
    | 'completed'
    | 'needs_review'
    | 'stale'
    | 'blocked'
    | 'superseded'

  node_version: string
  view_spec: NodeViewSpec
  executor_spec?: NodeExecutorSpec

  created_by: ActorRef
  created_at: string
  updated_at: string
}
```

## 4. NodeRun Schema 草案

```ts
type NodeRun = {
  id: string
  node_id: string
  workflow_id: string
  run_number: number

  started_at: string
  ended_at?: string
  status: 'running' | 'succeeded' | 'failed' | 'cancelled' | 'blocked'

  input_versions: AssetRef[]
  output_assets: AssetRef[]

  actor_refs: ActorRef[]
  tool_calls: ToolCallRef[]
  trace_events: TraceEventRef[]

  summary: string
  error?: string
  human_review?: ReviewRef
}
```

关键点：

> Node Definition 和 Node Run 必须分开。节点定义说明“这个节点是什么”，运行记录说明“这次怎么执行、用了什么输入、产生了什么输出”。

## 5. Asset Schema 草案

```ts
type Asset = {
  id: string
  project_id: string
  type: 'raw' | 'derived' | 'decision' | 'workflow_template' | 'code' | 'report' | 'tool_evaluation'
  modality: 'text' | 'image' | 'audio' | 'video' | 'pdf' | 'code' | 'url' | 'structured'

  title: string
  summary?: string
  content_ref?: string
  metadata: Record<string, unknown>

  version: string
  source_refs: SourceRef[]
  created_by: ActorRef
  created_at: string
  last_verified_at?: string

  status: 'draft' | 'confirmed' | 'disputed' | 'stale' | 'deprecated' | 'superseded'
}
```

多模态资产处理原则：

```text
保存原始资产
  → 生成派生资产
  → 用户确认派生理解
  → 后续节点使用派生资产和原始资产引用
```

例如：

```text
老师语音 raw/audio
  → ASR 转写 derived/text
  → AI 总结 derived/structured
  → 用户确认 decision
  → 影响后续需求分析节点
```

## 7. WorkflowChangeSet Schema 草案

```ts
type WorkflowChangeSet = {
  id: string
  workflow_id: string
  title: string
  reason: string

  change_type:
    | 'insert_node'
    | 'delete_node'
    | 'split_node'
    | 'merge_nodes'
    | 'replace_node'
    | 'rewire_edge'
    | 'update_node_contract'

  operations: ChangeOperation[]
  impact_analysis: ImpactAnalysis

  proposed_by: ActorRef
  proposed_at: string
  status: 'draft' | 'pending_review' | 'accepted' | 'rejected' | 'deferred' | 'branched'

  reviewed_by?: ActorRef[]
  decision_record_id?: string
}
```

变更流程：

```text
用户提出自然语言修改
  → AI 生成 ChangeSet
  → 系统列出影响节点和资产
  → 用户/团队确认
  → 应用变更
  → 后续节点标记 stale / needs_review
```

## 8. 影响分析规则草案

当前 MVP 不需要复杂图算法，可以先做规则：

### 8.1 直接依赖影响

```text
如果资产 A 更新，所有 input_refs 包含 A 的节点标记 needs_review。
```

### 8.2 下游传播影响

```text
如果节点 N 输出变化，则所有依赖 N 输出资产的后续节点标记 stale。
```

### 8.3 人工确认阻断传播

```text
用户可以确认“该变化不影响后续节点”，系统记录决策，停止传播。
```

### 8.4 高风险节点强制复核

```text
如果变化影响需求、范围、接口、测试标准，则后续编码/评审节点必须 needs_review。
```

## 9. 编码节点 MVP 切法

### 方案 A：轻量版，适合毕设稳妥实现

只做 GitHub 关联，不直接内置 Codex 编程：

- 关联 repo；
- 读取 Issue / PR / Commit；
- 节点展示 GitHub 对象；
- 把 Commit / PR / Review 转成资产；
- 支持人工记录“本节点已完成”。

优点：实现可控。  
缺点：AI 编码协作展示较弱。

### 方案 B：中等版，适合体现 AI 协作核心

加入 AI 编码任务生成和本地 Codex/Claude Code 控制接口设计：

- 节点生成编码任务说明；
- 用户确认；
- 调用本地 coding agent 或通过 MCP 暴露系统上下文；
- 记录 diff/commit/test；
- 人工 Review 后合入。

优点：更贴近 AI 协作主旨。  
缺点：工程复杂度明显上升。

### 方案 C：高风险版，不建议 MVP

在系统内完整实现在线 IDE + AI 编码 + 自动 PR + 测试 + 部署。

优点：展示强。  
缺点：范围过大，容易偏题。

**建议：** MVP 采用 A + 部分 B。

## 10. 多人协作与争议处理 MVP 切法

不用一开始做完整协同编辑和 CRDT。

可以先做：

```text
变更提案
  → 评论
  → AI 影响分析
  → 负责人确认
  → 合并/拒绝/暂存
```

争议记录字段：

```ts
type DebateRecord = {
  id: string
  topic: string
  related_change_set_id?: string
  positions: {
    actor: ActorRef
    claim: string
    evidence_refs: AssetRef[]
  }[]
  ai_summary: string
  decision?: string
  status: 'open' | 'resolved' | 'deferred'
}
```

## 11. 最小可行页面组合

建议 MVP 页面：

1. **项目工作台**：当前目标、下一步、风险、最近资产。
2. **工作流画布**：React Flow 展示节点图。
3. **节点详情抽屉**：输入、输出、状态、版本、执行记录。
4. **节点工作区**：根据节点类型切换组件。
5. **资产库**：卡片、详情、来源、关系。
6. **变更提案页**：ChangeSet、影响分析、评论、确认。
7. **项目记忆页**：时间线、关键决策、资产图谱、复盘。

## 12. 推荐 MVP 技术组合

不强制，但可以作为候选：

```text
前端：React + React Flow + Zustand/Jotai + shadcn/ui
后端：Node.js/NestJS 或 Python/FastAPI
数据库：PostgreSQL + JSONB
图关系：先用关系表，后续再考虑 Neo4j
AI：OpenAI/本地模型/LiteLLM 任选，抽象 Provider
MCP：系统作为 MCP Client 接入 GitHub/filesystem；后续暴露自身 MCP Server
GitHub：REST/GraphQL API 或 GitHub MCP
资产存储：本地文件系统 / S3-compatible / MinIO
```

## 13. 论文和文档中可写进毕设的表达

可以在论文/愿景文档中这样表述：

> 传统工作流系统多关注预定义流程的自动化执行，而本系统面向 AI 参与的探索式协作场景，将工作流建模为可演化的动态有向图。系统通过统一节点协议描述不同类型的工作单元，通过资产图谱记录节点输入、输出、证据和版本，通过工作流变更集管理节点插入、拆分和替换，并结合 MCP/GitHub 等外部工具接入实现 AI 可调用的协作闭环。

---

## 14. 当前最重要的设计边界

1. 不做完整 BPMN/CMMN 引擎，只借鉴动态 Case 和人工任务思想。
2. 不做完整 Airflow/Temporal/Dagster，只借鉴状态、运行记录、资产图谱和重跑。
3. 不做完整 ComfyUI，只借鉴多模态节点图和自定义节点生态。
4. 不做完整 n8n，只借鉴能力市场、工具节点和执行记录。
5. 不做完整 GitHub，只借鉴 PR/Review/分支协作模式。
6. 不做完整 CRDT 协同编辑，MVP 先用 ChangeSet + 审批。
7. 不让 AI 直接任意生成前端代码，而是生成 ViewSpec。
8. 不把 MCP 当作工作流模型本身，而是当作工具调用协议层。
