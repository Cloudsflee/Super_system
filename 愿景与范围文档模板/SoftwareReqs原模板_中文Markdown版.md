# 1. 业务需求

业务需求为后续所有详细需求开发提供基础与参照。业务需求可以来自客户、开发组织高层、执行发起人、项目愿景提出者、产品负责人、产品经理、市场部门或其他利益相关者。这些人员应清楚项目为什么要开展，以及项目最终将为业务和客户带来什么价值。

## 1.1 背景

概述开发新产品的理由。说明导致人们认识到“应该构建该产品”的历史背景、现状或业务环境。

`<在此填写项目背景。>`

## 1.2 业务问题或机会

描述本产品要解决的业务问题，或当前存在的业务机会。若是商业产品，可描述它所竞争的市场；若是信息系统，可描述它将被使用的业务环境。

可包括：

- 对现有产品或潜在解决方案的简要比较；
- 为什么拟议产品具有吸引力；
- 当前没有该产品时无法解决的问题；
- 该产品如何契合市场趋势或组织战略方向。

## 1.5 愿景声明

撰写简洁的愿景声明，概括新产品的目的和意图，并描述当世界中存在该产品时会发生什么变化。

愿景应：

- 平衡不同利益相关者的需要；
- 同时满足开发组织自身的目标；
- 立足于现实或可预见的客户市场、企业架构、组织战略方向、成本与资源限制。

# 2. 范围与限制

项目范围定义拟议解决方案的概念和边界。明确“不包含什么”同样有助于建立利益相关者的合理预期，并为后续评估新增特性或需求变更提供参考框架。超出既定范围的需求通常应被拒绝，除非它带来的收益足以支持扩大范围，并相应调整预算、进度或资源。

## 2.2 初始版本范围

描述产品初始版本将包含的主要特性。考虑产品将为不同客户群体带来的收益，并概括能支撑这些收益的产品特性和质量属性。

填写时应避免把所有潜在客户未来可能想要的功能都纳入初始版本。应聚焦于：

- 对最广泛用户群体最有价值；
- 开发成本可接受；
- 能体现产品核心价值的特性。

# 3. 业务上下文

本节总结围绕项目的一些业务问题，包括主要客户类别画像、项目概念所依据的假设，以及项目管理层面的优先级。

## 3.1 利益相关者画像

利益相关者是主动参与项目、受项目结果影响，或能够影响项目结果的个人、群体或组织。

利益相关者画像应识别：

- 本产品的客户和其他利益相关者；
- 他们对产品的主要关注点；
- 不同业务客户、目标市场细分和用户类别；
- 每类利益相关者将从产品中获得的主要价值或收益；
- 他们对产品的可能态度；
- 他们关注的主要特性；
- 已知的、必须适应的约束。

可能的利益相关者价值包括：

- 提升生产效率；
- 减少错误与返工；
- 节约成本；
- 简化业务流程；
- 自动化原本手工完成的任务；
- 能够执行全新的任务或功能；
- 符合现行标准或法规；
- 相比当前应用提升易用性或降低挫败感。

## 3.3 部署考虑

概述确保解决方案有效部署到运行环境所需的信息和活动。

可说明：

- 用户访问系统所需条件；
- 用户是否分布在多个时区，或是否集中在同一地点；
