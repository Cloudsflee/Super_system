# 1. 业务需求

业务需求为所有详细需求开发提供基础和参照。你可以从客户处收集业务需求，也可以与高层管理者、执行发起人、项目愿景提出者、产品管理人员、市场部门或其他人员一起形成这些需求。这些人员应清楚项目为什么要开展，以及项目将为业务和客户提供什么最终价值。

## 1.1 当前状态与挑战

本节概述新解决方案的提出理由。需要说明导致人们认识到“应推进该解决方案”的历史、情况或背景。

建议回答：

- 当前状态是什么？
- 当前面临哪些问题和挑战？
- 现状中有哪些需求没有被满足？

## 1.2 业务机会与成功标准

描述拟议解决方案、它将为组织带来的价值，以及客户将如何使用它。

如存在多个可选方案，应简要描述并比较这些方案，并说明首选方案。可包括：

- 收入增长或成本节约估计；
- 投资回报分析；
- 目标发布日期；
- 如何定义和衡量本倡议的成功；
- 最可能影响成功的因素，包括组织可直接控制的因素和外部因素；
- 判断业务目标是否达成的可衡量标准；
- 与该解决方案相关的潜在风险，例如时机、用户接受度、实施问题等。

| 内容 | 填写说明 |
|---|---|
| 解决方案描述 | 说明要做什么。 |
| 组织价值 | 说明它为组织带来什么价值。 |
| 客户使用方式 | 说明用户/客户如何使用。 |
| 可选方案比较 | 如有多个方案，说明首选方案及原因。 |
| 成功标准 | 说明如何衡量成功。 |

# 3. 范围

范围定义拟议解决方案的概念和边界。说明哪些内容不包含在解决方案中也同样重要。明确范围有助于建立利益相关者的合理预期，也为评估后续提出的特性和需求变更提供参考框架。超出范围的需求通常应被拒绝，除非其收益足以支持扩大范围，并相应调整预算、进度或资源。

## 3.1 范围内

描述解决方案计划包含的主要特性。考虑该解决方案要为不同利益相关者带来的收益。应聚焦于能够以可接受开发成本，为最广泛群体提供最大价值的特性和产品属性。

# 4. 业务上下文

本节总结围绕本倡议的一些业务问题，包括主要利益相关者，以及拟议解决方案将收集或使用哪些数据、这些数据将如何管理等考虑。

## 4.1 利益相关者

利益相关者是主动参与倡议、受其结果影响，或能够影响其结果的个人、群体或组织。

利益相关者清单应识别：

- 该解决方案的客户；
- 他们对解决方案的主要关注点；
- 限制可用时间、资源或预算的约束因素。

认真梳理利益相关者有助于围绕范围建立共识，并减少后续意外。

示例表：

| 利益相关者 | 主要关注点 | 约束 |
|---|---|---|
| 高层管理者 | 比竞争对手更丰富的功能集；上市/上线速度。 | 最高预算限制。 |
| 编辑人员 | 自动纠错；易用性；高可靠性。 | 必须能在低配置工作站上运行。 |
| 法务助理 | 能处理比当前系统大得多的数据库；易学。 | 没有再培训预算。 |

## 4.2 数据考虑

描述拟议解决方案将收集或使用的数据。以下问题可用于识别数据保护与隐私方面的潜在风险。

- 是否会收集任何个人信息？如果会，涉及多少个人？保存多久？
- 能否限制所收集个人信息的数量？
- 解决方案由谁管理，是组织内部还是外部供应商？数据存储在哪里？
- 是否需要与组织已有系统集成，例如统一登录、学生/人事/课程系统等？
- 谁有权访问这些数据？如果未经授权的人获得访问权限，会产生什么影响？
