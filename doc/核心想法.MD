# 核心想法：面向具体业务场景的 MCP-first AI 协作系统

> 更新时间：2026-07-07  
> 说明：本文件只记录当前已经相对确认的方向。仍有争议、待验证、待选择的内容放在 `问题.md`。

---

## 0. 当前总定位

本毕设方向不再定位为泛泛的“通用 AI 协作平台”或“传统插件平台”，而是：

> **面向具体业务场景的 MCP-first AI 协作工作流系统。**

更完整的表述：

> 系统以具体业务场景中的 AI 协作为目标，以 MCP 作为连接外部工具、组织 AI 可调用能力、暴露系统自身能力的主要协议层；通过工作流执行、过程追溯、人类纠偏和资产沉淀，把一次项目执行过程转化为未来可复用的协作资产。

一句话原则：

> **先落地一个具体业务场景，再从真实项目过程中抽象可迁移的工作流与资产模型。**

### 0.1 默认部署与治理假设

当前系统不应按公共 SaaS 或大规模企业平台来设计权限和扩展边界，而应按以下默认假设收束：

```text
开源
自托管 / 本地优先
小团队使用
最大规模通常为数人到几十人
团队成员相对可信
Owner / Admin 对本地环境拥有最终控制权
```

这意味着系统不应过度限制用户和开发者自定义能力。更合理的原则是：

> **节点能力开放，节点接入标准化；用户决定节点能做什么，系统保证节点做过什么可追溯。**

公共 SaaS 需要强隔离、强审核、强平台治理；但本项目更接近 VS Code、Node-RED、ComfyUI、n8n community nodes 这类开源可扩展工具，重点应放在：

- 插件/节点能被注册；
- 权限和依赖能被声明；
- 启用/禁用/版本能被管理；
- 执行过程能被记录；
- 输入输出能接入资产图谱；
- 出问题时能追溯、回滚或禁用。

## 1. 选题重心调整

### 1.1 不做什么定位

当前不应把选题表达为：

```text
通用 AI 协作平台
通用 Agent 平台
传统插件市场
纯工具集成平台
AI 可观测平台
```

这些方向过大，且容易被质疑业务落地不足。

### 1.2 当前更合理的定位

应表达为：

```text
具体业务场景
  → AI 协作工作流
  → MCP 工具接入
  → 过程追溯与人类纠偏
  → 真实资产沉淀
  → 通用资产抽象
```

MCP、工具接入、资产图谱、工作流推荐都是服务于业务闭环的支撑机制，而不是脱离业务场景单独成立的目的。

---

## 2. 核心主旨

### 2.1 AI 协作是核心

系统核心是 AI 协作，不是单纯的信息管理或流程管理。

AI 的角色是：

- 理解项目上下文；
- 调用 MCP 工具；
- 辅助规划工作链；
- 生成候选方案；
- 摘要、聚类、追问；
- 记录和解释执行过程；
- 辅助复盘与资产抽象。

但 AI 不应直接替用户做最终决策。

推荐交互原则：

```text
AI 提议 → 用户确认 → 系统追溯
```

---

### 2.2 MCP-first，但不是 MCP-only

MCP 是系统的核心协议层，但不是业务内核本身。

MCP 适合承担：

- 外部工具连接；
- AI 工具调用；
- MCP Server / Tool / Resource 能力目录；
- 系统能力对外暴露；
- Codex、Claude Code 等本地 AI 对系统的控制接口。

系统自身仍需要独立维护业务模型：

- 项目；
- 任务；
- 工作流；
- 阶段；
- 资产；
- 资产关系；
- 贡献事件；
- 决策记录；
- AI Trace。

核心原则：

> **MCP 是 AI 协作和生态连接的核心协议层；业务内核不能完全依赖 MCP。**

---

### 2.3 场景驱动优先

老师反馈后，当前已确认：应优先选择一个具体业务场景落地，而不是先做通用框架。

推荐路径：

```text
选定业务场景
  → 跑通该场景的 AI 协作闭环
  → 记录真实过程
  → 沉淀真实资产
  → 抽象通用资产
  → 总结可迁移框架
```

候选场景目前包括：

- 线上营销 / 内容运营；
- 小型电商 / 直播运营；
- 独立开发者 / 开源项目维护；
- 毕设 / 研究项目管理；
- 某个更具体行业场景。

最终场景尚未确认，放在 `问题.md` 中继续讨论。

## 3. MCP 优先架构

系统应围绕 MCP 形成双向架构。

### 3.1 向外连接：系统消费外部 MCP 能力

系统通过 MCP Client 连接外部 MCP Server，例如：

- Git/GitHub MCP；
- 文件系统 MCP；
- 知识库 MCP；
- 任务/项目管理 MCP；
- 可观测 / AI Trace MCP；
- 本地模型 / 工具 MCP；
- 其他开源项目 MCP。

这些 MCP 能力为 AI 提供真实上下文和工具调用能力。

---

### 3.2 向外暴露：系统自身提供 MCP Server

系统成熟后，应建立自己的 MCP Server，使 Codex、Claude Code 等本地 AI Agent 能直接控制系统。

可暴露能力包括：

- 查询项目；
- 获取项目上下文；
- 创建/更新任务；
- 查询工作流；
- 读取 AI Trace；
- 写入知识资产；
- 触发工作流推荐；
- 生成复盘；
- 启用/禁用 MCP 连接器。

目标是让系统成为：

> **本地 AI Agent 可调用、可控制、可扩展的协作基础设施。**

---

### 3.3 MCP Runtime 中立

Docker MCP Catalog / Toolkit / Gateway、MCPHub、Coolify 等都不能作为系统核心。

更合理的架构是：

```text
系统核心
  → MCP Runtime Provider 抽象层
      → Docker MCP Catalog / Gateway
      → MCPHub
      → 手动配置 MCP Server
      → 远程 HTTP MCP Server
      → 本地 stdio MCP Server
```

原则：

> **MCP 优先，但 Runtime 中立。**

Docker MCP Catalog 可以纳入最小生态集成验证范围，但不应绑定为唯一核心依赖。

---

## 3.4 可替换 AI 协作内核：Codex 是 Runner，不是上下文主权中心

当前设想中，Codex 可以作为第一版强力 AI Runner，因为它具备较好的代码协作、记忆和上下文压缩能力。但系统架构不能让 Codex 成为唯一大脑，否则一旦未来更换为 Claude Code 或其他 CLI，系统上下文、记忆和协作状态都会被绑定。

更合理的原则是：

> **系统拥有上下文，AI Runner 消费上下文。**

系统自己应管理：

- 项目上下文；
- 工作空间结构；
- 资产图谱；
- 决策记录；
- Trace；
- Workspace Digest；
- Context Pack。

Codex / Claude Code / 其他 CLI 应定位为：

- AI Runner；
- Code Executor；
- Analysis Worker；
- Tool-using Agent。

推荐架构：

```text
Workspace System
  ├── Context Store
  ├── Asset Graph
  ├── Trace Store
  ├── Workspace Digest
  ├── Context Pack Builder
  └── AI Runner Adapter
        ├── Codex Runner
        ├── Claude Code Runner
        ├── Local LLM Runner
        └── Other CLI Runner
```

`Context Pack` 是可替换 Runner 的关键。系统应把某个工作空间需要的上下文整理为统一格式，再交给不同 Runner。

示例：

```yaml
workspace_id: implement_github_issue_sync
goal: 实现 GitHub Issue 同步能力
role: coding_agent
background:
  - 当前系统是 MCP-first AI 协作工作流系统
  - 本节点目标是完成 GitHub Issue 同步
inputs:
  - requirement_doc.md
  - github_api_notes.md
  - related_decision_records
constraints:
  - 不修改核心架构
  - 所有输出必须关联 commit 或 diff
  - 需要生成测试结果
acceptance_criteria:
  - 能读取 issue
  - 能转成系统资产
  - 能展示同步状态
available_tools:
  - filesystem
  - git
  - github_api
  - test_runner
expected_outputs:
  - diff
  - commit
  - test_report
  - implementation_note
```

不同 Runner 能力不同，因此需要能力协商：

| 能力 | 示例 |
|---|---|
| code_edit | 能否修改代码文件。 |
| shell_exec | 能否执行命令。 |
| git_ops | 能否创建分支、提交、读取 diff。 |
| mcp_tools | 能否调用 MCP 工具。 |
| long_context | 是否支持长上下文。 |
| session_memory | 是否支持会话记忆。 |
| result_schema | 是否能稳定输出结构化结果。 |

核心原则：

> **Codex 可以作为首个实现，但系统的上下文、资产、工作空间和 Trace 必须由系统自己管理，避免对单一 AI CLI 形成结构性依赖。**

## 4. 工作流与工具链推荐

### 4.1 推荐不是 AI 自由发挥

工作流推荐必须可复现、可解释、可校验。

不应采用：

```text
用户输入一句话 → AI 随机生成工作流
```

而应采用：

```text
标准化输入
  + 工作流模板库
  + MCP 能力目录
  + 项目上下文
  + 历史资产
  + 固定输出 Schema
  + 推荐校验器
  → AI 生成可解释工作链建议
```

---

### 4.2 推荐结果是可选方案

工作流推荐不是强制流程。

用户应能：

- 接受；
- 修改；
- 拒绝；
- 替换工具；
- 跳过阶段；
- 选择不同模板；
- 手动补充输入。

---

### 4.3 工作流不是线性脚本

工作流应被理解为：

> 围绕一个目标，持续消费资产、生产资产、验证资产、更新资产的过程。

一个阶段可能成功、失败、阻塞、跳过或被替换。

---

### 4.4 工作流应是可演化的动态有向图

工作流不应只是一次性预设的静态流程图，而应是可以在执行过程中持续调整的动态协作图。

用户可以通过自然语言向 AI 提出修改意图，例如：

```text
在“任务拆解”之前插入一个“竞品分析”节点。
把“测试评审”拆成“自动化测试”和“人工评审”两个节点。
这个节点产出不够，回到前置调研阶段补充材料。
```

AI 不应直接静默修改工作流，而应生成结构化的工作流变更提案：

```text
用户意图
  → AI 生成 Workflow ChangeSet
  → 系统进行影响分析
  → 用户/团队确认
  → 工作流图更新
  → 受影响节点标记为需复核或可能过期
  → 选择性重跑节点
```

其中 `Workflow ChangeSet` 应记录：

- 变更类型：插入、删除、拆分、合并、替换、重连；
- 变更位置；
- 变更原因；
- 受影响节点；
- 受影响资产；
- 是否需要重跑；
- 提出者、确认者和确认时间；
- 最终处理结果。

核心原则：

> **工作流修改不是直接覆盖，而是通过变更提案、影响分析、人工确认和版本记录完成。**

---

### 4.5 节点不是页面，而是工作单元

节点不应被理解成一个固定页面，而应被定义为：

> **有目标、有输入、有处理能力、有输出、有验收标准、有版本、有证据链的工作单元。**

节点的通用性不来自“所有节点长得一样”，而来自“所有节点遵守同一套协议”。

一个节点至少应回答：

1. 这个节点要解决什么问题；
2. 它需要哪些输入资产；
3. 它可以调用哪些工具、MCP、API 或人工能力；
4. 它应该产出什么资产；
5. 什么情况下算完成；
6. 产出依据和证据是什么；
7. 如果前置输入变化，哪些后续节点会受影响。

建议的节点抽象：

```text
WorkflowNode
  ├── id / type / title / goal
  ├── inputs：输入资产引用
  ├── outputs：输出资产定义
  ├── tools：可用能力或连接器
  ├── status：节点状态
  ├── acceptanceCriteria：验收标准
  ├── qualityChecks：质量检查
  ├── version：节点定义版本
  ├── runs：执行记录
  └── view：展示规格
```

### 4.5.1 节点应是自主工作空间，而不是原子动作

当前进一步确认：不应把工作流拆成过多细碎节点。节点不应对应“上传文件”“AI 摘要一次”“生成 ChangeSet”“沉淀资产”这类原子动作，而应对应一段用户真正关心、可以相对独立推进、具有明确完成边界的工作。

一个内容是否适合作为节点，应看它是否满足：

1. 有明确目标；
2. 有相对独立的完成边界；
3. 有用户真正关心的产出；
4. 有验收标准；
5. 可以独立推进一段工作；
6. 过程中可以包含多个内部动作；
7. 完成后会影响后续工作。

因此，节点更准确的定义应是：

> **节点 = 围绕一个目标运行的自主工作空间。**

节点内部可以包含：

- 输入材料收集；
- AI 分析；
- 工具调用；
- 人工确认；
- 代码执行；
- 测试结果；
- 讨论记录；
- 资产产出；
- ChangeSet 提案；
- 运行日志。

但这些内部动作不应都拆成主工作流上的独立节点。

更合理的系统层级是：

```text
工作流 = 若干自主工作节点组成的路线
节点 = 围绕一个目标的自主工作空间
资产 = 高于节点的项目记忆层
ChangeSet = 工作流控制层操作
Inbox = 输入收集层
Trace = 过程记录层
```

对应过程：

```text
Inbox 收集材料
  → 节点消费材料并推进工作
  → 节点产生资产、决策、代码、报告或变更提案
  → 资产进入项目记忆和资产图谱
  → 必要时节点提出 ChangeSet
  → 用户确认后工作流结构更新
```

核心原则：

> **工作流图不要拆太碎；节点内部可以很丰富。**

---

### 4.5.2 分层工作空间与 Work Thread

当前进一步确认：主工作流节点可能在立项初期非常宽泛，节点内部仍然需要继续拆分协作空间。但这种拆分不应全部上升为主工作流节点，而应形成分层工作空间。

建议层级：

```text
Project Workspace
  └── Workflow
        └── Node Workspace
              └── Sub Workspace
                    └── Work Thread
```

各层含义：

| 层级 | 含义 |
|---|---|
| Project Workspace | 项目级工作空间，承载目标、资产、工作流、决策、Trace。 |
| Workflow | 项目推进路线，由若干自主工作节点组成。 |
| Node Workspace | 主工作流上的自主工作节点，围绕一个较完整目标推进。 |
| Sub Workspace | 节点内部为了完成目标拆出的局部工作空间，不一定出现在主工作流图。 |
| Work Thread | 最小协作单位，围绕一个小目标的一次人机协作记录。 |

`Work Thread` 可以包含：

- 小目标；
- 输入上下文；
- 人 / AI / 工具参与记录；
- 过程日志；
- 产出；
- 状态；
- 关联资产。

一个 Work Thread 如果变得足够重要，可以被提升为 Sub Workspace，甚至进一步提升为主工作流节点。

核心原则：

> **主工作流保持清晰；复杂性下沉到节点工作空间、子工作空间和 Work Thread。**

---

### 4.5.3 父子工作空间的上下文传递

不同工作空间之间不应直接共享全部上下文，否则会导致上下文爆炸。更合理的方式是通过结构化摘要、资产引用、决策记录和按需展开来通信。

建议定义：

```text
Workspace Digest：工作空间对外摘要
Context Pack：提供给 AI Runner 的上下文包
Trace：原始过程记录
Asset Graph：稳定资产关系
Context Store：系统长期上下文存储
```

子工作空间呈现给父工作空间的默认内容应是 `Workspace Digest`，而不是全部聊天记录和工具调用。

示例：

```yaml
workspace_id: codex_replaceability_study
goal: 判断 Codex 是否可以被 Claude Code 替换
status: in_progress
current_conclusion:
  - Codex 可以作为首个 AI Runner
  - 但不能让 Codex 记忆成为系统唯一上下文来源
output_assets:
  - ai_runner_adapter_draft
  - context_pack_schema
confidence: medium
blockers:
  - 尚未验证 Claude Code CLI 的具体输入输出适配成本
next_actions:
  - 设计统一 AgentRunner 接口
  - 用一个编码节点分别跑 Codex 和 Claude Code 做对比
evidence_refs:
  - asset_001
  - thread_003
raw_trace_ref:
  - trace://workspace/codex_replaceability_study
```

父工作空间应有权按需进一步获取子工作空间内容，但默认只读取摘要。

推荐展开层级：

| 层级 | 内容 |
|---|---|
| L0 | 子工作空间状态和一句话结论。 |
| L1 | Workspace Digest。 |
| L2 | 输出资产和证据。 |
| L3 | 关键过程记录。 |
| L4 | 原始 Trace / 对话 / 工具调用。 |

核心原则：

> **父空间掌控全局，子空间保留细节；默认摘要通信，必要时逐层展开。**

---

### 4.6 节点展示采用“统一外壳 + 多类型工作区”

不建议试图用一个万能页面覆盖所有节点。更合理的方式是：

```text
统一节点协议
  + 统一节点外壳
  + 不同节点类型的 Renderer
  + 不同节点类型的 Executor
```

节点展示可以分为三层：

| 层级 | 作用 | 示例内容 |
|---|---|---|
| 流程图卡片 | 快速理解全局结构 | 节点标题、状态、输入输出摘要、风险标记。 |
| 节点详情面板 | 解释节点为什么这样 | 目标、输入资产、输出资产、执行记录、AI Trace、工具调用、版本历史。 |
| 节点工作区 | 执行该节点的具体工作 | 调研资料墙、AI 分析区、GitHub PR、测试报告、决策面板等。 |

节点工作区应根据节点的工作性质和能力画像变化，而不是把每个原子动作拆成一种节点。例如：

| 自主工作节点示例 | 工作区可能包含 |
|---|---|
| 根据老师反馈收束毕设选题 | 材料区、反馈要点、候选方向对比、风险评估、用户决策、受影响范围、ChangeSet 提案。 |
| 完成 GitHub Issue 同步能力 | 需求上下文、实现计划、分支/Commit/PR、Diff、测试结果、人工 Review、遗留问题。 |
| 评估 MCP Runtime 方案 | 候选工具资料、对比矩阵、试用记录、风险、推荐结论、待确认问题。 |
| 完成一轮技术可行性验证 | 假设、实验步骤、工具调用、结果截图、失败记录、结论和后续建议。 |
| 形成 MVP 范围决策 | 候选范围、实现成本、风险、导师反馈、最终决策、影响节点。 |

这些节点内部可以发生素材导入、AI 分析、工具调用、决策确认、资产更新和 ChangeSet 生成，但主工作流上不必把这些内部动作都拆出来。

---

### 4.6.1 开放节点插件机制：节点能力开放，节点接入标准化

由于系统定位为开源、自托管、小团队使用，用户和团队应拥有完整自实现节点的权力。

用户/开发者可以自实现：

- 节点定义；
- 节点执行逻辑；
- 节点配置面板；
- 节点展示组件；
- 节点输入输出 Schema；
- 节点调用 MCP / API / CLI / 本地脚本；
- 节点产出的资产类型。

系统核心不应限制节点内部能做什么，而应规定节点如何接入系统：

```text
节点必须能被注册；
节点必须声明基本信息；
节点必须能被启用/禁用；
节点必须返回运行状态；
节点运行过程应能被记录；
节点需要的权限和依赖应能声明；
节点输入输出如果要进入工作流，应尽量声明 Schema 和资产类型。
```

推荐的本地插件结构：

```text
plugins/
  github-issue-triage/
    node.manifest.yaml
    executor.ts
    renderer.tsx
    schema.json
    README.md
```

示例 manifest：

```yaml
name: github-issue-triage
version: 0.1.0
node_types:
  - github.issue_triage
permissions:
  - github.read_issues
  - github.write_labels
  - mcp.github
  - filesystem.project_read
inputs:
  - repo_url
  - issue_list
outputs:
  - issue_triage_report
  - priority_labels
  - task_candidates
```

因此，节点系统应区分两类节点：

| 类型 | 特征 | 系统能做什么 |
|---|---|---|
| 透明节点 | 明确声明输入、输出、资产类型、权限、验收标准。 | 可做影响分析、资产图谱、复用推荐、质量检查。 |
| 黑盒节点 | 只声明最小运行信息，内部逻辑由用户自定。 | 可运行、记录日志、记录输入输出文件和状态，但语义理解较弱。 |

这不是禁止黑盒节点，而是明确：

> **声明越完整，系统越能追溯、推荐和复用；声明越少，节点越接近普通脚本。**

AI 也可以辅助用户生成节点插件，但应作为“代码生成与本地启用流程”处理：

```text
用户描述节点需求
  → AI 生成 manifest / executor / renderer / schema
  → 用户或开发者审阅
  → 本地运行测试
  → Admin / Owner 启用
  → 进入工作流并记录版本和运行日志
```

核心原则：

> **节点实现开放，节点注册、权限声明、运行记录、资产接入和版本追溯标准化。**

---

### 4.7 节点输入输出必须资产化

节点之间不应只传递一段无结构文本，而应传递：

```text
资产引用 + 资产版本 + 关系说明
```

例如：

```text
节点：任务拆解
输入：需求调研报告 v2、竞品分析报告 v1
输出：任务列表 v3、MVP 范围建议 v2
```

如果前置资产发生变化，后续节点不应被自动推翻，而应被标记为：

- 可能过期；
- 需要复核；
- 建议重跑；
- 已被替代。

核心原则：

> **前置信息变化后，系统做影响分析和状态标记，由用户决定是否重跑或接受影响。**

---

### 4.7.1 资产、ChangeSet、Inbox、Trace 不应默认作为普通节点

当前确认：并不是所有系统行为都应该被建模成节点。

| 对象 | 更合理的层级 | 说明 |
|---|---|---|
| Inbox / 素材接收 | 输入收集层 | 上传文件、贴链接、导入截图、语音转写通常是节点内部输入行为，不应单独成为主工作流节点。 |
| Asset / 资产沉淀 | 项目记忆层 / 资产层 | 资产是高于节点的横向层，节点消费、产生、更新资产；资产沉淀通常是节点完成后的系统行为。 |
| Workflow ChangeSet | 工作流控制层 | ChangeSet 是工作流结构变更记录，不应默认作为业务节点存在。 |
| Trace / 日志 | 过程记录层 | AI 调用、MCP 调用、命令执行、用户确认应记录为 Trace，而不是拆成节点。 |

只有当“资产化/复盘/流程重构”本身就是明确业务目标时，才适合作为节点。例如：

```text
适合作为节点：将本次 GitHub 集成过程沉淀为可复用插件开发模板
不适合作为节点：保存某个资产到资产库
```

```text
适合作为节点：根据老师反馈重构毕设选题范围
不适合作为节点：生成一个 Workflow ChangeSet
```

```text
适合作为节点：整理老师反馈并提取对选题范围的影响
不适合作为节点：上传老师聊天截图
```

核心原则：

> **节点负责推进一段有意义的工作；资产、ChangeSet、Inbox、Trace 是支撑节点运行的系统层能力。**

---

### 4.8 编码节点、GitHub 与 Git 集成

如果系统强调 AI 协作，且具体业务流程中包含实现、脚本、自动化、开源项目维护等任务，则应允许存在编码节点。

编码节点不应只是普通聊天框，而应是带上下文和产出契约的 `Code Task Node`。

典型输入：

- 需求说明；
- 设计文档；
- 关联 Issue；
- 代码仓库；
- 约束条件；
- 测试要求。

典型输出：

- Git branch；
- commit；
- Pull Request；
- diff；
- 测试结果；
- 实现说明；
- AI Trace；
- 待确认问题。

Git / GitHub 的定位：

```text
Git 管代码、文档快照和配置版本；
GitHub 管 Issue、PR、Review、Commit 等协作对象；
系统数据库管工作流状态、资产关系、节点状态和决策记录。
```

不应试图让 Git 单独管理全部协作状态，但应将节点与 GitHub 对象建立关联：

```text
工作流节点 → GitHub Issue
节点运行记录 → Commit
节点输出资产 → Pull Request / Test Report
节点评审 → PR Review / Decision Record
```

---

### 4.8.1 编码节点应是实现工作空间，而不是聊天框

编码节点的交互不应只是“打开一个 AI 聊天框让 Codex 写代码”，而应是围绕实现目标组织上下文、计划、执行、验证和 Review 的工作空间。

例如：

```text
节点：实现 GitHub Issue 同步能力
```

页面可以分为三块：

```text
左侧：上下文
  - 需求说明
  - 关联资产
  - 接口约束
  - 相关 Issue
  - 验收标准

中间：执行区
  - AI 生成实现计划
  - 用户确认/修改计划
  - 创建 branch
  - 调用 Codex / 本地命令 / GitHub API
  - 运行测试

右侧：结果区
  - 文件 diff
  - commit
  - PR
  - 测试结果
  - 遗留问题
  - 人工 Review
```

推荐交互流程：

```text
用户进入编码节点
  → 系统展示需求、上下文和验收标准
  → AI 生成实现计划
  → 用户确认或修改计划
  → 系统创建 branch / issue
  → Codex 或本地执行器完成代码修改
  → 系统展示 diff 和测试结果
  → 用户选择接受、要求修改、放弃或创建 PR
  → 节点输出代码资产、实现记录、测试报告和遗留问题
```

编码节点效果不只验证“代码是否写出来”，还应验证：

| 维度 | 验证方式 |
|---|---|
| 用户是否理解当前任务 | 用户能否从节点中说清楚要实现什么。 |
| 用户是否理解 AI 做了什么 | 是否能找到实现计划、diff、测试结果和日志。 |
| 用户是否能控制过程 | 是否能修改计划、拒绝结果、要求重跑。 |
| 代码结果是否可验证 | 是否有关联 commit、PR、测试报告。 |
| 过程是否可追溯 | 是否能追溯输入需求、AI 操作、代码变更。 |
| 是否减少上下文切换 | 是否减少在聊天、IDE、GitHub、文档之间来回切换。 |
| 是否支持复盘 | 完成后能否生成实现经验卡或问题记录。 |

---

### 4.9 工作流与节点版本应分层管理

一个版本号无法描述全部变化，应至少区分：

| 版本层级 | 含义 |
|---|---|
| Workflow Version | 整体流程结构变了。 |
| Node Definition Version | 节点目标、输入输出、验收标准变了。 |
| Node Run Version | 同一个节点第几次执行。 |
| Asset Version | 节点产出的资产版本。 |
| Git Version | 代码层面的 commit、branch、tag、PR。 |

示例：

```text
Workflow v3
  └── Node: 竞品分析 v1
        └── Run #2
              └── Output: 竞品分析报告 v4
```

这样才能支持：

- 插入前置节点；
- 重跑后续节点；
- 保留旧方案；
- 比较不同分支；
- 回溯某个结论来自哪个版本。

---

### 4.10 协作争议应资产化，而不是淹没在聊天中

多人协作时，不同人对工作流变更、节点产出、方案选择可能有不同意见。

系统不应只保存散乱聊天，而应把关键协作内容转为：

- 观点卡片；
- 争议记录；
- 决策记录；
- 方案对比；
- 工作流变更提案；
- 复盘记录。

当存在分歧时，可以采用类似 Pull Request 的机制：

```text
提出变更
  → AI 分析影响
  → 团队讨论
  → 决策
  → 合并 / 拒绝 / 暂存 / 作为可选分支保留
```

如果短期无法达成一致，可以允许工作流分支并行存在，例如：

```text
方案 A：轻量 MVP 路线
方案 B：完整资产图谱路线
```

再通过实现成本、风险、展示效果、时间可控性等指标进行比较。

核心原则：

> **协作中的不同意见不是噪音，而是需要被结构化记录、比较和决策的资产。**

---

### 4.11 调研后的节点与工作流设计参照

根据 `探索/` 中对标准、论文、开源项目和现有方案的调研，当前确认：本系统不应凭空发明一套工作流模型，也不应直接照搬某个现有系统，而应组合吸收不同方向的成熟经验。

| 参考方向 | 可借鉴内容 | 在本系统中的定位 |
|---|---|---|
| BPMN / Workflow Patterns | Task、Event、Gateway、分支、合并、异常、人工任务等流程概念。 | 作为流程语义参考，不直接做完整 BPMN 引擎。 |
| CMMN / Case Management | 面向知识工作、动态任务、阶段、里程碑、人工判断。 | 更贴近“探索式 AI 协作工作流”的思想来源。 |
| W3C PROV | Entity / Activity / Agent 的来源追溯模型。 | 作为资产、节点执行、参与者之间关系的底层参考。 |
| ML Metadata / OpenLineage | Artifact、Execution、Context、Run、Dataset、Lineage。 | 参考节点运行记录、资产版本、影响分析和跨工具追溯。 |
| Dagster Asset Graph | 以资产为中心组织工作流，记录 materialization 和 stale 状态。 | 强化“工作流加工资产”的系统主线。 |
| Node-RED / n8n | 可视化节点、工具节点、节点市场、执行记录。 | 参考节点生态和能力市场，但不做纯自动化平台。 |
| Dify / Flowise / Langflow | LLM 节点、知识库节点、工具调用节点、AI App 编排。 | 参考 AI 节点类型和结构化输出。 |
| ComfyUI | 多模态节点图、自定义节点、参数与产物可复用。 | 参考多模态节点展示和节点生态。 |
| LangGraph / Temporal | 状态图、checkpoint、human-in-the-loop、长流程、事件驱动。 | 参考 AI 工作流运行、人类介入和恢复机制。 |
| GitHub PR / Git | 分支、变更提案、Review、合并、回滚。 | 参考工作流变更和协作争议的处理机制。 |
| MCP | Tool / Resource / Prompt、Client / Server、外部能力调用。 | 作为 AI 可调用能力层，不替代业务工作流模型。 |

调研后的核心判断：

> **现有方案分别解决了流程建模、节点展示、工作流执行、资产血缘、AI 编排、协作版本和工具调用中的一部分，但没有一个系统完整覆盖“面向具体业务场景的 MCP-first AI 协作工作流 + 动态节点 + 资产沉淀 + 人类纠偏”这一组合目标。**

因此，本系统的合理创新点不是重新发明所有基础设施，而是在具体场景中把以下能力组合成一个可验证闭环：

```text
动态工作流图
  + 统一节点协议
  + 自主工作节点与多类型工作区
  + 资产化输入输出
  + ChangeSet 变更提案
  + 影响分析与选择性重跑
  + AI / MCP / GitHub 工具接入
  + 人类确认与争议记录
  + 项目记忆与通用资产抽象
```

## 5. 资产与工作流的关系

### 5.1 核心定义

```text
工作流 = 如何做事
资产 = 做事过程中产生、依赖、复用、验证的东西
```

二者关系：

| 关系 | 说明 |
|---|---|
| 工作流消费资产 | 调研流程需要输入链接、截图、历史资料、老师反馈等。 |
| 工作流产生资产 | 阶段完成后产生调研卡、决策卡、任务、报告、复盘等。 |
| 工作流依赖资产 | 工作流可以依赖检查清单、Prompt 模板、工具链模板。 |
| 工作流验证资产 | 某个通用模板是否有效，要看它在真实项目中执行结果如何。 |
| 工作流本身也可成为资产 | 成功跑通的流程可抽象为通用工作流模板。 |

一句话：

> **工作流是资产的加工过程，资产是工作流的输入、输出、依据和复用结果。**

---

### 5.2 双层协作资产模型

系统资产分为两类：

#### 真实资产

来自具体项目和真实过程，例如：

- 链接；
- 截图；
- 文件；
- 会议记录；
- 老师反馈；
- Git commit；
- GitHub Issue / PR；
- AI Trace；
- 决策记录；
- 测试报告；
- 交付物。

特点：有来源、有时间、有上下文、有证据。

#### 通用资产

从真实资产中抽象出来，可复用于未来项目，例如：

- 工作流模板；
- 工具链模板；
- MCP 连接器组合；
- Prompt 模板；
- 决策模式；
- 问题-方案卡；
- 检查清单；
- 风险清单；
- 协作模式；
- 架构原则。

特点：可复用，但必须能追溯到真实资产。

---

### 5.3 资产图谱

资产不能只是文件夹分类，而应有关系图谱。

典型关系：

- `supports`：支撑；
- `contradicts`：反驳；
- `derived_from`：抽象自；
- `applies_to`：适用于；
- `validated_by`：被验证；
- `used_by`：被使用；
- `depends_on`：依赖；
- `superseded_by`：被新版本替代；
- `recommended_for`：推荐用于。

资产图谱的意义：

> 让 AI 和用户知道一个结论从哪里来、为什么可信、适合哪里、是否过时、如何复用。

---

## 6. 资产展现形式

### 6.1 资产不是只能是静态文档

资产可以有多种形态：

| 形态 | 示例 |
|---|---|
| 静态文本资产 | 决策卡、总结、说明文档。 |
| 结构化资产 | 任务、阶段、证据、工作流模板。 |
| 交互式资产 | 看板、时间线、图谱、仪表盘。 |
| 可执行资产 | Prompt 模板、MCP 工具链、脚本、自动化流程。 |
| 可发布资产 | 项目报告页、知识库页面、复盘网站。 |
| 可复用资产包 | 工具链 + 工作流 + 检查清单 + 示例。 |

---

### 6.2 网站化展示的原则

不建议第一版为每个资产单独新部署网站。

更合理的方式是：

> 系统内部通过资产数据 + 资产关系 + ViewSpec，渲染出项目页、报告页、图谱页、工作流页。

也就是：

```text
Asset Data
  + Asset Relation
  + ViewSpec
  + 前端渲染器
  → 资产页面 / 项目记忆页 / 报告页 / 工作流页
```

AI 可以生成 ViewSpec，但不应直接任意生成和执行前端代码。

---

### 6.3 Asset View System

建议系统中定义：

```text
Asset Data：资产本体
Asset Relation：资产关系
Asset ViewSpec：展示方式
```

同一个资产可以有多个视图：

- 卡片视图；
- 详情页；
- 图谱节点；
- 工作流阶段产出；
- 报告章节；
- MCP Resource。

---

### 6.4 多模态资产处理原则

调研后确认，多模态内容不应被强行压缩成普通文本，也不应只作为附件保存。更合理的处理方式是三层结构：

```text
原始资产层：图片、音频、视频、PDF、网页、代码、截图、仓库等；
派生资产层：OCR 文本、ASR 转写、图像描述、摘要、结构化元数据、embedding；
展示视图层：缩略图、播放器、正文、卡片、证据表、时间线、图谱、报告页。
```

典型流程：

```text
保存原始资产
  → 调用 AI / 工具生成派生资产
  → 用户确认派生理解是否正确
  → 将已确认资产作为后续节点输入
  → 保留原始资产与派生资产的来源关系
```

例如：

```text
老师语音 raw/audio
  → ASR 转写 derived/text
  → AI 总结 derived/structured
  → 用户确认 decision
  → 影响需求分析或范围调整节点
```

核心原则：

> **多模态输入先资产化，再结构化，再进入工作流；AI 生成的派生理解必须可追溯、可确认、可修正。**

---

## 7. 工作流执行与失败处理

### 7.1 阶段产出契约

每个工作流阶段都应定义：

- 阶段目标；
- 必要输入；
- 可用 MCP 工具；
- 预期输出；
- 最小完成标准；
- 质量检查；
- 阻塞条件。

这不是保证 AI 一定正确，而是保证每阶段有清晰的输入、输出、检查和阻塞机制。

---

### 7.2 阻塞处理

当阶段无法达到产出要求时，不应让 AI 硬编。

应进入：

```text
产出不足
  → 阻塞诊断
  → 请求补充输入 / 启用工具 / 降级输出 / 跳过阶段
  → 用户确认
  → 继续或终止
```

阻塞本身也可以沉淀为资产。

---

## 8. 人机交互模型

推荐模型：

```text
AI 提议 → 用户确认 → 系统追溯
```

用户不需要一开始把想法写清楚，系统应支持低门槛输入：

- 文本；
- 链接；
- 文件；
- 截图；
- 语音；
- 草图；
- 代码仓库；
- Issue / PR；
- 对话记录；
- 类比对象；
- 反例。

AI 将这些内容转为：

- 素材卡；
- 证据卡；
- 观点卡；
- 决策候选；
- 工作流候选；
- 资产候选。

用户通过轻量交互确认、否定、补充或修正。

---

## 9. 追溯与好用性的平衡

全流程追溯不能一次性暴露所有复杂信息。

应采用渐进式披露：

| 层级 | 展示内容 |
|---|---|
| L0 摘要层 | 当前结论、下一步、风险。 |
| L1 阶段层 | 工作流阶段、输入输出、状态。 |
| L2 资产层 | 资产卡片、决策卡、证据卡。 |
| L3 图谱层 | 支撑、反驳、派生、应用关系。 |
| L4 原始层 | 原始文件、日志、AI Trace、MCP 调用记录。 |

默认展示 L0-L1，需要时再展开 L2-L4。

## 10. 开源工具接入策略

### 10.1 MCP 是优先接入方式，但不是唯一方式

系统不能假设所有开源工具都有 MCP Server，也不能要求所有工具都必须 MCP 化。

核心原则：

> **MCP 是最高优先级的 AI 可调用接入方式，但不是唯一接入方式。**

系统应支持多种接入层级：

| 等级 | 接入方式 | AI 能否直接使用 | 说明 |
|---|---|---|---|
| L0 参考级 | 只记录链接、文档、仓库 | 不能 | 作为参考资料或候选工具。 |
| L1 部署级 | 通过 Docker / Coolify / Compose 跑起来 | 通常不能 | 只是能部署，不代表能进入 AI 工作流。 |
| L2 数据级 | 文件导入/导出、CSV、JSON、Markdown、PDF | 间接可用 | 可转为真实资产供 AI 分析。 |
| L3 API/CLI 级 | REST API、GraphQL、CLI、Webhook | 可通过 Adapter 使用 | 可先做普通适配器。 |
| L4 MCP 级 | 包装或使用 MCP Server | AI 可直接调用 | 可成为 MCP Tool / Resource。 |
| L5 工作流级 | 已定义输入输出、阶段契约、质量检查 | 可稳定进入工作流 | 正式成为工作流能力节点。 |

---

### 10.2 能力市场，而不是传统插件市场

系统需要类似 VS Code 市场的“随取随用”体验，但展示对象不应只是传统插件，而应是：

- MCP 连接器；
- API / CLI 适配器；
- 部署模板；
- 数据导入器；
- 工作流组件；
- 资产模板；
- 工具评估资产。

更准确名称可以是：

> **能力市场 / Capability Marketplace**

它展示的不是“装一个工具”，而是：

```text
这个工具/连接器能提供什么能力？
适合哪个阶段？
需要什么输入？
会产生什么输出？
能否被 AI 调用？
部署方式是什么？
风险和权限是什么？
```

---

### 10.2.1 能力市场更应像本地能力注册表，而不是公共应用商店

在开源、自托管、小团队场景下，“能力市场”不应被理解为中心化、强审核、强平台控制的公共 SaaS 插件市场，而应更接近：

```text
本地能力注册表
  + 官方内置能力
  + 用户自实现节点
  + 团队共享节点
  + 第三方开源节点
  + MCP / API / CLI / Docker / GitHub 等连接器
```

能力市场负责展示和管理：

- 已安装了什么；
- 当前启用了什么；
- 每个能力声明了哪些权限；
- 每个能力支持哪些节点类型；
- 每个能力输入输出是什么；
- 每个能力被哪些工作流使用；
- 每个能力最近运行是否失败；
- 每个能力是否有版本更新或兼容风险。

因此，第一版不需要做“大而全公共插件市场”，但需要保留最小开放插件能力：

```text
安装 / 注册
启用 / 禁用
权限声明
版本记录
运行日志
资产接入
```

---

### 10.3 工具进入稳定工作流前应先经过试用与评估

开源工具是否适合当前项目，通常无法只靠文档判断。

因此系统应有：

> **工具试用工作流 / Tool Audition Workflow**

流程：

```text
用户提出目标
  → AI 推荐候选能力
  → 能力市场列出候选工具
  → Runtime Provider 部署或接入候选工具
  → 用户/AI 执行最小样例任务
  → 记录输入、输出、体验和问题
  → 生成工具评估资产
  → 用户确认是否纳入正式工作流，或以未验证/黑盒能力方式临时使用
```

工具进入稳定、可复用的正式工作流前，应至少明确：

- 它解决什么能力需求；
- 输入是什么；
- 输出是什么；
- 是否可被 AI 调用；
- 是否有 API / CLI / MCP；
- 是否需要人工旁路使用；
- 是否适合当前项目阶段。

---

### 10.4 Runtime Provider 抽象

部署工具和调用工具应分离。

系统中应有 Runtime Provider 抽象：

```text
Deployment / Runtime Provider
  ├── Docker Compose Provider
  ├── Coolify Provider
  ├── Docker MCP Gateway Provider
  ├── MCPHub Provider
  ├── Manual Provider
  └── Remote Service Provider
```

Coolify 这类工具适合作为部署提供方，而不是系统核心。

它解决：

```text
如何把某个开源工具跑起来
```

但不直接解决：

```text
这个工具是否适合当前业务
AI 如何调用它
它的结果如何进入工作流
它产生什么资产
```

---

### 10.5 工作流绑定能力，而不是绑定具体工具

工作流阶段不应直接写死某个工具，而应定义“能力需求”。

例如：

```text
阶段：内容排期
所需能力：内容日历 / 任务排期 / 发布状态跟踪
候选实现：某开源工具、表格、Notion、GitHub Issue、自研任务模块
```

这样工作流更稳定，工具可以替换。

原则：

> **工作流阶段 = 目标 + 输入 + 输出 + 所需能力；具体工具 = 能力实现方式。**

---

### 10.6 非 MCP 工具接入策略

如果工具没有 MCP 层适配，系统不应直接放弃，也不应强行 MCP 化。

处理策略：

| 工具条件 | 接入策略 |
|---|---|
| 已有 MCP Server | 直接作为 MCP 连接器接入。 |
| 有 API / CLI / Webhook | 先做普通 Adapter，必要时包装成 MCP。 |
| 支持文件导出 | 通过导入器转为真实资产。 |
| 有数据库 | 只读连接，抽取必要数据。 |
| 只能人工使用 | 作为旁路工具记录，不进入自动工作流。 |
| 价值不明确 | 先进入工具试用工作流，生成评估资产。 |

最终原则：

> **能 MCP 就 MCP；不能 MCP 就 API、CLI、Webhook、文件导入、数据库只读或人工旁路；只有输入输出和价值被验证后，才进入正式工作流。**

## 11. 调研后的外部参照与实现边界

`探索/` 目录中的调研资料表明，本项目可以借鉴多个成熟方向，但必须保持系统边界清晰。

### 11.1 可借鉴但不直接照搬的方向

| 方向 | 采用方式 |
|---|---|
| BPMN / CMMN | 借鉴流程、人工任务、动态 Case 思想，不实现完整标准引擎。 |
| Airflow / Argo / Prefect / Temporal | 借鉴节点状态、运行记录、失败重试、长流程和事件恢复，不做通用调度平台。 |
| Dagster / MLMD / OpenLineage / W3C PROV | 借鉴资产图谱、运行记录、血缘追溯和影响分析，服务本系统资产模型。 |
| Node-RED / n8n / ComfyUI | 借鉴节点画布、类型化节点、节点生态和多模态展示，不做纯自动化或媒体生成平台。 |
| Dify / Flowise / Langflow / LangGraph | 借鉴 AI 节点、工具调用、human-in-the-loop、checkpoint，不把系统降级为单纯 Agent 编排器。 |
| GitHub / Git / CRDT | 借鉴 PR 式变更提案、分支、Review、版本和协作冲突处理，MVP 不做完整实时协同编辑。 |
| MCP / Docker MCP / MCPHub | 借鉴 AI 工具调用、MCP Server 管理和 Runtime Provider 思路，不把 MCP 运行时作为业务核心。 |

---

### 11.2 更稳妥的 MVP 技术收束

第一版更适合采用“够用但可解释”的实现方式：

```text
工作流图：动态有向图 + 自主工作节点 + 边表；
节点协议：WorkflowNode + NodeRun + NodeViewSpec + NodeExecutorSpec；
系统分层：Inbox 输入层 + Node/Sub Workspace 工作空间层 + Work Thread 协作线程 + Asset 项目记忆层 + ChangeSet 控制层 + Trace 记录层；
资产追溯：Asset + AssetRelation + TraceEvent；
变更管理：WorkflowChangeSet + DecisionRecord；
影响分析：先做规则型直接依赖/下游依赖标记；
多模态处理：原始资产 + 派生资产 + 用户确认；
协作冲突：先做 PR-like 变更提案和评论，不做完整 CRDT；
工具接入：优先 GitHub / filesystem / MCP，保留 API/CLI/导入适配；
AI 协作内核：Context Pack Builder + AI Runner Adapter + Tool/MCP Bridge + Result Normalizer + Trace Recorder；
展示方式：内置 Renderer + ViewSpec 作为默认路径；开发者插件可提供自定义 Renderer；AI 生成的代码需经用户/开发者审阅后再启用。
插件机制：项目本地 plugins 目录 + manifest + install/enable/disable + permission declaration + run log。
```

### 11.3 当前可以写入论文的创新表达

> 本系统面向 AI 参与的探索式协作场景，将工作流建模为可演化的动态有向图。系统通过统一节点协议描述具备自主性的工作单元，通过资产图谱记录节点输入、输出、证据和版本，通过工作流变更集记录和管理结构调整，并结合 MCP/GitHub 等外部工具接入实现 AI 可调用的协作闭环。

## 13. 明确不做什么

1. 不做完整通用 Agent 平台。
2. 不做完整企业 OA。
3. 不做商业级多租户 SaaS，也不按公共 SaaS 的强封闭治理假设限制本地用户能力。
4. 不训练自有大模型。
5. 不完全替代 Notion、Linear、GitHub、Logseq、VS Code 等已有工具。
6. 不强迫用户迁移工具链。
7. 不把贡献量化直接用于人事评价。
8. 不默认安装大量用户可能不需要的功能。
9. 不把 Docker MCP Catalog / Coolify 作为系统核心。
10. 不让 AI 未经用户/开发者确认自动启用生成代码；但允许用户自实现 Renderer / Executor / 节点插件。
11. 不让 AI 在缺少证据时硬生成结论。
12. 不假设所有开源工具都有 MCP，也不强迫所有工具必须 MCP 化。
13. 不把“能部署”误认为“能进入工作流”。
14. 不把节点设计成一个试图适配所有工作的万能页面。
15. 不让 AI 未经确认直接修改正式工作流。
16. 不把 Git 当成唯一的协作状态源。
17. 不做完整 BPMN / CMMN 引擎。
18. 不做完整 Airflow / Temporal / Dagster 式通用工作流或调度平台。
19. 不预置完整 ComfyUI / n8n / Node-RED 式大规模官方节点生态；但保留本地自定义节点插件机制。
20. 不做完整 CRDT 实时协同编辑，MVP 先用变更提案和版本记录。
21. 不把 LangGraph、Temporal、Dagster、n8n 等任何单一现有方案作为系统唯一底座。
22. 不把“安全可控”理解成封闭能力；本项目更强调自托管前提下的可声明、可追溯、可禁用、可回滚。

## 15. 互联网权威资料补充调研后的稳定校准

> 来源：`探索-1/05_互联网权威资料调研.md`、`探索-1/06_权威资料补充调研_工作空间记忆开放节点资产追溯.md`、`探索-1/资料索引_自动验证.csv`。  
> 状态：这些是经过资料对照后可以保留在核心方案中的稳定判断。

### 15.1 当前方案不是复刻某个现成工具

现有资料分别验证了方案中的不同部分，但没有一个现成项目完整等价于当前设想：

| 能力方向 | 可借鉴对象 | 本系统取舍 |
|---|---|---|
| AI coding agent / workspace runner | Codex、Claude Code、OpenHands、SWE-agent | 借鉴工作目录、工具调用、代码修改、测试反馈；不把某个 Runner 作为唯一核心。 |
| Agent 记忆与上下文管理 | Codex Memories、Claude Memory、LangGraph、LlamaIndex、AutoGen、MemGPT | 系统持有 Context Store / Asset Graph / Trace / Digest，Runner 只消费 Context Pack。 |
| MCP 工具接入 | MCP Tools / Resources / Prompts / Roots / Sampling / Elicitation | MCP-first，但 MCP 只负责工具和资源接入，不负责业务协作内核。 |
| 工作流执行历史 | Temporal、Argo、Airflow、Prefect | 借鉴事件历史、失败处理、状态追踪；不做通用调度平台。 |
| 动态 case / 人参与流程 | BPMN / CMMN | 更接近探索式 Case，而非固定自动化流程。 |
| 插件生态 | VS Code、Node-RED、n8n、ComfyUI、Backstage | 借鉴 manifest、contribution points、自定义节点、能力目录；坚持本地自托管开放节点。 |
| 资产血缘与追溯 | Dagster、W3C PROV、OpenLineage、ML Metadata | 资产高于节点，必须记录来源、版本、证据和依赖关系。 |
| AI 可观测性 | OpenTelemetry、Langfuse、Phoenix、Weave、LangSmith | Trace Recorder 是核心模块，不只是保存聊天记录。 |
| 多模态/交互式产物 | Jupyter、Observable、Streamlit、Gradio、Storybook | 资产可以有多种 ViewSpec，不限于静态文档。 |
| 本地优先协作 | Local-first、Yjs、Automerge、Dev Containers、Docker Compose、Coolify | 自托管小团队优先，MVP 用 ChangeSet + Review，长期再考虑 CRDT。 |

### 15.2 核心架构进一步稳定为“工作空间 + 上下文包 + Runner + 资产图谱”

当前核心架构应保持：

```text
Project Workspace
  ├── Workflow / ChangeSet
  ├── Node Workspace
  │     └── Work Thread
  ├── Context Store
  ├── Asset Graph
  ├── Trace Store
  ├── Workspace Digest
  └── Context Pack Builder
        └── AI Runner Adapter
              ├── CodexRunner
              ├── ClaudeCodeRunner
              ├── SimpleCLIRunner
              └── MockRunner
```

稳定原则：

1. 系统拥有上下文，AI Runner 消费上下文。
2. Digest 负责“让别人理解我现在怎样”，Context Pack 负责“让别人接着干活”。
3. Runner 内部 memory 可以利用，但不能替代系统记忆和确认资产。
4. 子工作空间默认向父空间返回 Digest、资产和证据引用，不默认泄露全量 Trace。
5. 编码节点必须是实现工作空间，而不是聊天框。

### 15.3 能力市场应覆盖工具、节点、上下文、展示和部署

调研后进一步确认：本系统不应只做“插件市场”或“MCP Server 列表”，而应做本地能力目录。

能力类型包括：

```text
Node Type：新的自主工作节点类型。
Tool Connector：普通 API / CLI / Webhook / SDK 工具适配。
MCP Server Config：AI 可调用工具/资源适配。
Context Provider：为 Context Pack 提供上下文来源。
Asset Type：新的资产类型及字段。
ViewSpec / Renderer：资产或节点的展示方式。
Runner Adapter：新的 AI Runner 接入。
Workflow Template：可复用工作流模板。
Deployment Recipe：Docker Compose / Coolify / Dev Container 等部署说明。
```

接入方式分层：

```text
L0 展示接入：link / iframe / read-only view
L1 数据导入：文件、Issue、任务、知识库导入
L2 API/CLI 适配：REST / GraphQL / CLI / SDK / Webhook
L3 MCP 适配：封装为 MCP server 供 AI 调用
L4 部署适配：Docker Compose / Coolify / Dev Container
L5 深度节点插件：Executor + Renderer + Schema + Asset 输出
```

### 15.4 资产展示应采用 Asset 与 ViewSpec 分离

资产不应被限制为静态 Markdown。更稳定的模型是：

```text
Asset：语义内容、版本、证据、来源、关系。
ViewSpec：这个资产可以如何展示。
Renderer：真正渲染页面/图表/看板/Notebook/Dashboard 的组件。
```

同一资产可以有多种展示：

```text
Markdown 文档
表格 / 看板
资产图谱
时间线
交互式 Dashboard
Notebook
Storybook-like 原型页
小型 Web Demo
```

AI 可以生成 ViewSpec 或 Renderer 草稿，但启用前需要用户/开发者确认，并记录 Trace / ChangeSet。

### 15.5 毕设 MVP 的更稳妥闭环

第一版最有价值的验证闭环：

```text
创建 Project Workspace
  → 向导收集目标、角色、已有工具
  → AI 推荐候选工具链和工作流
  → 用户确认主工作流
  → 进入 Node Workspace
  → 系统生成 Context Pack，用户预览/调整
  → CodexRunner 或 SimpleRunner 执行
  → Trace Recorder 记录 AI 调用、工具调用、人工确认、文件变化
  → Asset Extractor 生成资产候选
  → 用户确认资产
  → 更新 Workspace Digest
  → 父工作空间根据 Digest / Asset / Evidence 继续推进或提出 ChangeSet
```

这一闭环能同时验证：

1. AI 协作是否可观测；
2. Context Pack 是否改善协作效果；
3. 资产是否能从过程沉淀出来；
4. 节点是否能作为自主工作空间运行；
5. Runner 是否可以通过 Adapter 替换；
6. MCP / API / CLI 工具接入是否能进入工作流。

## 16. Codex 记忆能力在系统中的利用方式

> 来源：关于“是否需要从 0 开发完整 Agent 架构，以及 Codex 自身记忆能力如何复用”的讨论。  
> 状态：作为当前系统设计中的稳定原则保留。

### 16.1 不从 0 重写 Agent，而是把 Codex 作为首个 Workspace Runner

当前系统不应试图完整重写一个成熟 Agent。更合理的定位是：

> **本系统不重新实现完整 Agent，而是将 Codex 作为首个强力 Workspace Runner；系统负责上下文、资产、追溯、权限和协作结构，Codex 负责具体任务理解、规划、编码、工具调用和过程性推理。**

也就是说：

```text
Codex 负责干活；
系统负责组织活、交代上下文、记录过程、沉淀资产、控制边界。
```

系统真正需要实现的是一层 AI 协作外壳：

```text
Context Pack Builder
Result Normalizer
Trace Recorder
Asset Manager
Workspace Digest Manager
CodexRunner Adapter
Tool/MCP Bridge
```

而不是从零实现：

```text
自主规划 Agent
代码编辑 Agent
长期记忆 Agent
工具调用 Agent
多 Agent 协作框架
```

### 16.2 Codex Memory 的定位：经验缓存层，而不是系统事实源

Codex 自身记忆能力应被利用，但不能成为系统的主记忆数据库。

更准确的分层是：

| 记忆层 | 负责方 | 内容 | 权威性 |
|---|---|---|---|
| Codex Memory | Codex | 个人偏好、常用工作方式、项目习惯、技术栈经验、踩坑记录 | 辅助性经验记忆 |
| AGENTS.md / 项目规则文档 | 系统生成 + 用户确认 | 项目规则、开发约定、Runner 行为要求、必须遵守的边界 | 高权威项目规则 |
| Context Pack | 系统动态生成 | 当前 Workspace / Node / Work Thread 的任务上下文 | 当前任务权威上下文 |
| Asset Graph / Trace / Digest | 系统数据库 | 事实、资产、决策、证据、版本、过程记录 | 系统权威记忆 |

核心原则：

> **Codex Memory 用来让 Codex 越来越懂“怎么干活”；系统记忆用来保证“项目到底发生了什么”。**

### 16.3 适合交给 Codex Memory 的内容

适合让 Codex 通过自身记忆保留的内容：

```text
用户偏好：
- 喜欢先分析再动手；
- 修改代码前先给计划；
- 不喜欢过度抽象和无意义拆分；
- 希望保留可追溯记录。

项目习惯：
- 本项目是 MCP-first，但不是 MCP-only；
- 节点是自主工作空间，不是原子动作；
- 资产高于节点；
- Context Pack 是跨 Workspace 协作核心。

技术习惯：
- 默认考虑自托管；
- 优先保留用户已有工具链；
- 插件采用 manifest + executor + renderer；
- Git/GitHub 和 MCP 是优先接入方向。
```

这些内容具有重复性、偏好性、经验性，适合放在 Codex Memory 中辅助执行。

### 16.4 不适合只交给 Codex Memory 的内容

不应只存在 Codex Memory 中的内容：

```text
项目事实
资产内容
用户确认过的决策
工作流状态
节点运行状态
权限配置
Trace 记录
证据引用
团队分歧
版本历史
验收标准
```

这些内容必须由系统侧保存，并且可查询、可追溯、可版本化。

原则：

> **Codex 说过的话不等于系统事实；用户确认后的资产和决策才进入系统权威记忆。**

### 16.5 AGENTS.md 作为 Codex 的项目级稳定指令入口

系统可以自动维护项目根目录下的 `AGENTS.md`，用于向 Codex 注入稳定项目规则。

示例结构：

```text
project-root/
  AGENTS.md
  .ai-workspace/
    context-pack.json
    workspace-digest.md
    asset-index.json
```

`AGENTS.md` 适合放：

```md
# Project AI Collaboration Rules

## System Positioning
本项目是一个自托管、MCP-first、AI 协作为核心的分层工作空间系统。

## Hard Rules
- 不要把节点拆成原子动作。
- 节点应被视为围绕目标运行的自主工作空间。
- 资产是节点之上的项目记忆层。
- 所有重要结论必须引用输入资产、Trace 或用户确认。
- 修改代码前必须先输出计划。
- 修改后必须输出 changed_files、test_results、asset_candidates、open_questions。

## Context Pack
当前任务上下文请优先读取：
.ai-workspace/context-pack.json
```

因此：

```text
Codex Memory：记偏好和经验；
AGENTS.md：记稳定规则；
Context Pack：记当前任务上下文；
Asset Graph / Trace / Digest：记系统权威事实。
```

### 16.6 Codex Session 作为 Node Workspace / Work Thread 的连续执行上下文

每个 Node Workspace 或 Work Thread 可以绑定一个 Codex Session，使 Codex 在一个具体工作空间内保持连续上下文。

概念模型：

```ts
type CodexSessionRef = {
  workspaceId: string
  nodeWorkspaceId: string
  workThreadId: string
  codexThreadId: string
  startedAt: string
  status: "active" | "completed" | "archived"
}
```

运行方式：

```text
第一次进入节点：
  系统生成 Context Pack
  → 写入 .ai-workspace/context-pack.json
  → 启动 Codex Session
  → Codex 执行任务

后续继续节点：
  系统更新 Context Pack / Digest
  → 恢复或继续 Codex Session
  → Codex 基于自身 session + 最新系统上下文继续工作
```

注意：Codex Session 可作为节点内部连续工作上下文，但系统仍应保存关键状态，不能只依赖 Codex Session 内部历史。

### 16.7 CodexRunner 的推荐工作流

推荐执行闭环：

```text
1. 系统生成 Context Pack
2. 写入 .ai-workspace/context-pack.json
3. AGENTS.md 指示 Codex 如何读取 Context Pack
4. CodexRunner 调用 Codex 执行任务
5. Codex 利用自身 memory + session + 项目规则工作
6. 系统捕获输出、文件变化、工具调用、测试结果和关键事件
7. Result Normalizer 归一化结果
8. Trace Recorder 记录过程
9. Asset Extractor 生成资产候选
10. 用户确认后写入 Asset Graph
11. Workspace Digest 更新
```

### 16.8 设计价值表达

当前方案可以在论文或愿景文档中表述为：

> 本系统不试图重新实现一个完整 Agent，而是将 Codex 作为首个 Workspace Runner。系统通过 AGENTS.md、Context Pack、Codex Session、Codex Memory 和结构化输出机制复用 Codex 的上下文理解、代码执行和经验记忆能力；同时，系统保留资产、Trace、Digest 和工作流状态的主权，避免将项目事实完全交给 Runner 内部记忆。

## 17. 第一版原型与验证范围的收束决策

> 来源：关于“接下来需要思考和决策什么”的回复确认。  
> 状态：作为当前 MVP / 原型方向的确认约束。

### 17.1 第一版服务对象：个人核心使用，预留团队扩展

第一版优先面向个人深度使用，而不是一开始做完整团队协作平台。

当前定位：

```text
第一版：个人 / 超级个体使用的 AI 协作工作空间；
后续：自然扩展到小团队协作；
设计时：保留成员、权限、评论、Review、资产归属、决策记录等团队余量。
```

说明：

- 当前身边存在电商小业务可作为真实验证对象；
- 但系统不应被电商业务绑死；
- 演示场景可以选择电商、软件项目、毕业设计或开源项目；
- 系统核心应抽象为通用工作空间、节点、资产、Context Pack、Runner 和工具接入。

更准确的取舍是：

> **产品内核足够通用，验证场景可以具体。**

### 17.2 第一版目标：完整工程化闭环，而不是轻量 Demo

第一版不应只是概念展示或轻量 Demo，而应尽量做成可深度使用的工程化原型，用于真实业务验证。

目标闭环：

```text
创建项目
  → 描述目标 / 角色 / 已有工具 / 业务背景
  → AI 推荐工具链与工作流
  → 用户确认工作流
  → 每个节点带有预期产出与验收标准
  → 进入 Node Workspace
  → 系统生成 Context Pack
  → CodexRunner 执行任务
  → 记录 Trace / 文件变化 / 工具调用 / 人工确认
  → 生成资产候选
  → 用户确认资产
  → 更新 Workspace Digest
  → 继续下一个节点或提出 ChangeSet
```

当前原则：

> **不是做“看起来有流程”的假原型，而是做一个能让用户真的把任务推进下去的深度原型。**

### 17.3 每个节点必须有预先期望

每个节点都应具备明确的节点契约，而不是只给一个宽泛标题。

节点预期至少包括：

```text
node_goal：节点目标
expected_inputs：期望输入
expected_outputs：期望输出
acceptance_criteria：验收标准
required_context：需要的上下文
allowed_tools：允许使用的工具 / MCP / API / CLI
asset_outputs：可能沉淀的资产类型
failure_policy：未达产出时如何处理
review_policy：哪些结果需要用户确认
```

示例：

```yaml
node: 电商商品调研与选品判断
node_goal: 判断某类商品是否值得进入下一步测试
expected_inputs:
  - 商品候选
  - 平台数据或截图
  - 竞品链接
expected_outputs:
  - 调研报告
  - 风险点
  - 是否进入测试的建议
acceptance_criteria:
  - 至少列出 3 个竞品
  - 说明价格区间、卖点、风险和不确定信息
  - 标明哪些结论有证据，哪些只是推测
asset_outputs:
  - MarkdownAsset
  - DecisionAsset
  - ToolchainAsset
```

### 17.4 Codex 集成原则：以“足够有用”为目标，而不是追求某一种接入深度

Codex 的接入深度不是第一优先级，第一优先级是让 Codex 在系统里足够有用。

当前原则：

```text
Codex 可以通过 CLI / SDK / MCP Server 等方式接入；
MVP 不必执着于某一种最深集成；
但系统必须能给 Codex 提供高质量 Context Pack；
必须能接收并归一化 Codex 的结果；
必须能把 Codex 的过程和产出转化为 Trace / Asset / Digest。
```

### 17.5 Codex 不同 Session 记忆不共享，因此跨 Session 记忆必须由系统负责

已确认的重要约束：

> **不能假设 Codex 不同 Session 之间自然共享完整上下文。**

因此系统必须承担跨 Session 的记忆桥接：

```text
Workspace Digest：跨 Session 的摘要桥梁；
Asset Graph：跨 Session 的事实和资产来源；
Trace Store：跨 Session 的过程证据；
Context Pack：每次启动 / 恢复 Codex 时注入的任务上下文；
AGENTS.md：项目稳定规则入口。
```

每次开启新的 Codex Session 时，系统应重新构造启动上下文：

```text
最新项目规则
+ 当前 Workspace Digest
+ 相关资产
+ 相关决策
+ 当前节点目标
+ 验收标准
+ 可用工具
+ 历史关键 Trace 摘要
= Bootstrap Context Pack
```

结论：

> **Codex Session 是局部工作缓存；系统记忆才是跨 Session、跨节点、跨工作空间的连续性来源。**

### 17.6 第一版资产类型保持收束

第一版可先保留以下资产类型：

```text
MarkdownAsset：调研、方案、复盘、说明；
CodeChangeAsset：代码变更、diff、commit、PR；
DecisionAsset：用户确认的关键决策；
ToolchainAsset：工具链推荐与使用链路；
ContextPackAsset：某次任务上下文包；
DigestAsset：Workspace 摘要。
```

展示方式优先：

```text
Markdown
表格
简单关系图
Trace 时间线
```

### 17.7 能力市场第一版可以暂缓

由于第一版重点是个人深度使用和业务验证，完整能力市场可以暂缓。

第一版可保留：

```text
本地配置式工具接入；
少量内置连接器；
MCP server 配置；
插件机制的架构预留；
manifest 设计草案。
```

第一版不必实现：

```text
完整插件市场 UI；
远程插件仓库；
插件评分 / 搜索 / 发布流程；
复杂依赖管理；
团队级插件治理。
```

### 17.8 MCP 第一版接入范围

第一版 MCP 接入保留三种形式：

```text
stdio MCP
HTTP MCP
Docker Compose 启动的本地 MCP 服务
```

Coolify / Docker MCP Catalog / MCPHub 等可以作为后续集成对象或部署辅助，不作为第一版核心依赖。

### 17.9 验证方式：在系统中使用 Codex 完成任务

验证方式不是简单比较“直接用 Codex”和“完全不用 Codex”。

当前验证方向：

> **方案 B + A：在本系统里使用 Codex 做任务。**

也就是：

```text
用户仍然使用 Codex；
但不是裸用 Codex；
而是在系统提供的 Context Pack、节点预期、Trace、资产沉淀和 Digest 机制中使用 Codex。
```

评估重点：

```text
系统是否让 Codex 更容易获得正确上下文；
系统是否让用户更清楚 Codex 做了什么；
系统是否让任务结果更容易复盘；
系统是否能把过程沉淀成资产；
系统是否能让后续 Session / 后续节点继续接上；
系统是否能用于真实业务验证。
```

## 18. 第一版工程落地边界确认

> 来源：关于第一版系统形态、技术栈、Codex 接入、Git 集成、数据边界、节点模板和成功标准的确认。  
> 状态：作为第一版工程化原型的当前实现边界。

### 18.1 具体验证业务暂不锁死

当前确认：第一版暂不把系统绑定到某个具体业务。

原则：

```text
先搭通通用工程闭环；
具体验证业务后续再选择；
业务场景可以替换，但系统核心模型不随场景变化。
```

因此，第一版工程实现应围绕通用结构展开：

```text
Project Workspace
Workflow
Node Workspace
Context Pack
CodexRunner
Trace
Asset
Digest
Tool Registry
```

### 18.2 第一版系统形态：浏览器打开的本地服务

当前确认选择：

> **C. 浏览器打开的本地服务。**

也就是：

```text
用户在浏览器中访问本地网站；
后端服务运行在本机或本地容器；
数据优先保存在本地；
```

## 19. 使用过程中的随时 Codex 辅助与追问式协作

> 来源：关于“用户在实际使用过程中，凡是需要人工填写、判断、选择或没有思路时，都可以随时调用 Codex 辅助推进任务”的进一步确认。  
> 状态：作为第一版交互与 Runner 使用方式的新增稳定原则。

### 19.1 Codex 不只用于节点执行，也应成为随时可调用的协作助手

当前进一步确认：Codex 不应只在“执行 / 编码节点”中被调用，也不应只在工作流编排完成后才介入。用户在实际推进项目时，凡是遇到需要人工输入、判断、拆解、填写、选择、复盘或缺少思路的地方，都应能随时请求 Codex 辅助。

也就是说，系统中的 Codex 使用方式应分为两类：

```text
正式执行型调用：
  围绕某个 Node Workspace / Work Thread 执行任务，产生 Trace、Asset、Digest、Git diff 等正式产物。

协作辅助型调用：
  在用户填写目标、节点参数、验收标准、工具选择、失败处理、Review 策略、资产摘要、Digest 草稿等过程中，提供建议、追问、选项和草稿。
```

核心原则：

> **用户在系统任何需要思考和填写的地方，都可以召唤 Codex；Codex 帮用户把模糊想法推进成可确认的结构化内容。**

### 19.2 典型辅助场景

V1 中应优先支持以下随时辅助场景：

| 场景 | Codex 辅助内容 |
|---|---|
| 项目初始化 | 根据用户一句话目标追问背景、角色、约束、已有材料、可用工具。 |
| 工作流推荐前 | 帮用户澄清项目类型、目标边界、风险和适合的节点路线。 |
| 节点参数填写 | 生成 node_goal、expected_inputs、expected_outputs、acceptance_criteria 草稿。 |
| 验收标准缺失 | 给出可选择的验收标准模板，避免空泛描述。 |
| 工具选择 | 根据目标和 Tool Registry 推荐可用工具，并说明为什么。 |
| Context Pack 预览 | 解释上下文包是否缺关键材料，建议 pin/unpin 内容。 |
| 任务卡住 | 诊断阻塞原因，给出补充输入、降级输出、改节点、重跑等选项。 |
| 资产确认 | 帮用户总结资产价值、证据来源和是否应确认。 |
| Digest 更新 | 生成 Digest 草稿，并列出不确定点让用户选择。 |
| ChangeSet 提案 | 根据用户自然语言生成结构化工作流变更建议。 |
| Git Review | 帮用户解释 diff、测试结果、commit message 和 PR body。 |
| 复盘沉淀 | 根据 Trace / Asset / Decision 生成复盘问题和复用资产候选。 |

### 19.3 未确定信息必须追问，而不是硬编

当信息不足、目标不明确、约束缺失或结论不可靠时，Codex 辅助不应直接编造完整答案，而应进入追问式协作。

推荐策略：

```text
信息明确
  → 生成结构化草稿
  → 用户确认 / 修改

信息部分缺失
  → 标记假设
  → 给出 2-4 个可选项
  → 说明推荐项和影响
  → 用户选择后继续

关键信息缺失
  → 明确阻塞点
  → 提出最少必要问题
  → 可提供“先按默认方案继续”的降级选项
```

示例：

```text
用户：我不知道这个节点验收标准怎么写。
Codex：可以从三种验收方式里选：
A. 产物完整性优先：必须输出调研报告、风险列表、下一步建议。
B. 证据质量优先：每个关键结论至少绑定一个来源或标记为假设。
C. 执行结果优先：必须形成 diff、测试结果和 commit。
推荐：如果这是调研节点，选 B；如果是编码节点，选 C。
```

核心原则：

> **Codex 可以建议，但不能把未确认的信息伪装成事实；不确定就追问、给选项、标假设。**

### 19.4 辅助型调用也需要进入系统记录，但不一定都资产化

随时辅助会产生大量中间讨论，不应全部污染资产库，但也不能完全丢失。

建议分层：

```text
Assist Trace：记录辅助过程、追问、选项、用户选择。
Draft：Codex 生成的草稿，如节点契约草稿、Digest 草稿。
Confirmed State：用户确认后写入 NodeContract / Decision / Asset / Digest。
Asset：只有用户确认有复用或证据价值的内容才沉淀为资产。
```

也就是说：

- 辅助对话默认进入 Trace；
- 生成的草稿进入目标对象的 draft 字段或版本；
- 用户确认后才更新系统权威状态；
- 有长期价值的内容再作为 AssetCandidate。

### 19.5 产品交互形态：全局 Assist 与局部 Assist

V1 前端应预留两种入口：

```text
全局 Assist：
  在项目 / 工作流 / 节点页面右侧提供“Ask Codex / 帮我推进”面板。

局部 Assist：
  在具体表单字段、节点契约、验收标准、工具选择、Digest 草稿、资产确认处提供“让 Codex 帮我生成 / 追问 / 给选项”。
```

局部 Assist 应携带当前字段上下文，避免用户重复解释。例如：

```text
当前字段：acceptance_criteria
当前节点类型：research
当前节点目标：评估 MCP Runtime 方案
已有输入：Docker MCP、MCPHub、Coolify 资料
请求：生成 3-5 条可验收标准，并说明缺失信息
```

### 19.6 与 Context Pack / Trace / Asset / Digest 的关系

随时辅助不破坏已有系统分层：

| 层 | 作用 |
|---|---|
| Assist Context Pack | 面向某次辅助请求的轻量上下文包，只包含当前页面、字段、相关资产和目标。 |
| Assist Trace | 记录辅助请求、Codex 建议、追问、用户选择。 |
| Draft Object | 节点契约草稿、Digest 草稿、Decision 草稿等。 |
| Human Review | 用户确认 Codex 建议是否写入系统正式状态。 |
| Asset Candidate | 只有有复用价值或证据价值的辅助结果才进入资产候选。 |

### 19.7 对第一版的实现要求

V1 不需要做一个完整“无处不在的智能体”，但必须支持最小可用的随时辅助闭环：

```text
用户在某个页面 / 字段点击“让 Codex 帮我”
  → 系统构造 Assist Context Pack
  → CodexRunner 或 MockRunner 返回建议 / 追问 / 选项 / 草稿
  → 用户选择、编辑或拒绝
  → 系统记录 Assist Trace
  → 用户确认后写入对应对象
```

优先落地位置：

1. Project Wizard：帮用户澄清目标、角色、背景、已有工具。
2. Node Contract 编辑页：帮用户生成节点目标、输入、输出、验收标准、失败处理和 Review 策略。
3. Context Pack Preview：帮用户判断缺失信息和是否需要补充材料。
4. Asset Review / Digest View：帮用户总结、确认或追问不确定内容。

### 19.8 成功标准补充

第一版成功标准需要补充：

```text
用户不只是在节点执行时使用 Codex；
用户在项目初始化、工作流确认、节点参数填写、验收标准生成、工具选择、资产确认和复盘时，都能调用 Codex 获得追问式辅助；
当信息未确定时，系统能让 Codex 给出问题、选项、推荐理由和默认方案；
用户确认后，辅助结果能写入 NodeContract / Decision / Asset / Digest，并保留 Trace。
```

## 20. 记忆充分性、系统记忆合理性与 Codex 自身记忆协同

> 来源：关于“为了保证 AI 补全合理，系统记忆与 Codex 自身记忆都需要充分设计，让 Codex 在补全时知道一切它应该知道的东西”的进一步确认。  
> 状态：作为 Context Pack、Assist、NodeRun 与 CodexRunner 的核心质量约束。

### 20.1 目标不是让 Codex 知道一切，而是知道“当前任务应该知道的一切”

当前进一步确认：随时辅助和节点执行的质量，取决于 Codex 在补全 / 建议 / 执行时是否拥有足够、正确、最新且有权使用的上下文。

但这不等于把所有历史材料、全部 Trace、全部资产都塞给 Codex。更合理的目标是：

```text
在当前任务目标下，Codex 应知道：
  - 必须知道的事实；
  - 已确认的决策；
  - 当前节点契约；
  - 用户偏好与项目规则；
  - 可用工具与权限；
  - 相关资产和证据；
  - 最近关键上下文变化；
  - 哪些信息不确定、过期或有争议；
  - 缺少什么信息时应该追问。

Codex 不必默认知道：
  - 与当前任务无关的全部原始聊天；
  - 全量 Trace；
  - 所有历史草稿；
  - 未确认资产；
  - 无权限工具和凭据；
  - 已废弃或被 superseded 的旧结论。
```

核心原则：

> **记忆充分性不是上下文越多越好，而是“该有的都有，不该混入的不混入，缺失的明确追问”。**

### 20.2 记忆分层与权威优先级

为了避免 Codex 自身记忆、旧 Session、系统资产、用户临时输入之间冲突，需要明确记忆权威顺序。

推荐优先级：

| 层级 | 名称 | 内容 | 权威性 |
|---|---|---|---|
| L0 | 当前用户显式输入 | 用户本轮填写、选择、确认、修改的内容 | 最高，当前轮优先 |
| L1 | Node Contract / 当前任务指令 | 当前节点目标、输入、输出、验收标准、工具权限、失败策略 | 当前任务权威 |
| L2 | DecisionRecord / Confirmed Asset | 用户确认过的决策、事实、资产、代码变更、工具链 | 系统事实权威 |
| L3 | Workspace Digest | 跨 Session / 跨节点摘要、当前结论、风险、下一步 | 摘要权威，需可追溯 |
| L4 | Project Rules / AGENTS.md | 稳定项目规则、协作硬规则、编码约定 | 稳定规则权威 |
| L5 | Trace Summary | 关键过程摘要、失败原因、工具调用摘要 | 过程证据摘要 |
| L6 | Raw Trace / 原始材料 | 原始日志、对话、文件、截图、导入材料 | 证据源，按需展开 |
| L7 | Codex Memory / Codex Session | Codex 记住的用户偏好、工作方式、经验缓存 | 辅助，不得覆盖系统事实 |
| L8 | AI 推测 / 草稿 | Codex 根据上下文生成的建议、假设、补全文本 | 最低，必须标记假设 |

冲突处理原则：

```text
当前用户显式确认 > 当前 Node Contract > Confirmed Asset / Decision > Workspace Digest > AGENTS.md > Trace Summary > Raw Trace > Codex Memory > AI 推测
```

如果 Codex Memory 或旧 Session 与系统确认资产冲突，应以系统确认资产为准，并让 Codex 在输出中标记冲突。

### 20.3 系统记忆的合理性设计

系统记忆应具备以下属性：

| 属性 | 要求 |
|---|---|
| 权威性 | 区分用户确认、AI 草稿、系统生成、工具导入。 |
| 可追溯 | 重要事实、决策和资产必须能追溯到 Trace / File / NodeRun / Review。 |
| 新鲜度 | 事实类资产需要 created_at、last_verified_at、stale/superseded 状态。 |
| 作用域 | 区分 user / project / workspace / node / thread / runner scope。 |
| 相关性 | 进入 Context Pack 前必须说明为什么相关。 |
| 最小充分 | 不把无关材料塞入当前上下文。 |
| 冲突可见 | 有冲突、争议、过期时标记，而不是静默覆盖。 |
| 可复核 | 用户可以看到“Codex 为什么知道这些”。 |

系统记忆不应只是一个“知识库”，而应由以下对象共同构成：

```text
Project Profile
Node Contract
Workspace Digest
Confirmed Asset
DecisionRecord
Trace Summary
Tool Registry
Git State / CodeChange
User Preference / Project Rule
Assist History Summary
Raw Evidence Ref
```

### 20.4 Codex 自身记忆的定位与使用边界

Codex 自身记忆可以提升使用体验，但不能成为系统事实源。

适合让 Codex 自身记住的内容：

```text
用户偏好：喜欢先计划再执行、喜欢中文解释、希望给选项。
协作习惯：信息不足时先追问，不要硬编。
项目稳定原则：MCP-first 但不是 MCP-only；节点是自主工作空间；资产高于节点。
编码偏好：提交前运行测试；输出 changed_files/test_results/open_questions。
```

不适合只放在 Codex 记忆里的内容：

```text
项目事实；
已确认决策；
资产内容；
节点状态；
验收标准；
Git commit / PR；
工具权限；
Trace；
团队争议；
凭据和敏感信息。
```

V1 策略：

```text
Codex Memory：自然辅助，不作为可控数据库。
AGENTS.md：系统可维护稳定项目规则入口。
Context Pack：当前任务事实和上下文权威入口。
Asset / Decision / Digest / Trace：系统权威记忆。
```

如果未来 Codex 提供稳定可控的 Memory API，也只能作为同步偏好和稳定规则的辅助层，不能替代系统数据库。

### 20.5 记忆充分性检查：Context Sufficiency Gate

每次 Assist 或 NodeRun 前，系统应执行一次 `Context Sufficiency Gate`，判断 Codex 是否已经知道当前任务应该知道的内容。

检查项：

```text
1. 是否有明确任务目标；
2. 是否有当前 Node Contract 或当前字段目标；
3. 是否有必要输入材料；
4. 是否包含相关 confirmed assets；
5. 是否包含相关 decisions；
6. 是否包含最新 Workspace Digest；
7. 是否包含用户偏好 / 项目规则；
8. 是否包含可用工具和权限边界；
9. 是否标记 stale / disputed / hypothesis；
10. 是否有 evidence_refs；
11. 是否存在冲突记忆；
12. 是否超过上下文预算；
13. 缺失信息是否已转成追问或选项。
```

输出：

```yaml
sufficiency_status: sufficient | needs_user_input | insufficient | conflict
missing_slots:
  - acceptance_criteria
  - target_user
conflicts:
  - digest says A, confirmed decision says B
stale_refs:
  - asset_123
recommended_questions:
  - 当前节点更偏调研还是编码？
recommended_options:
  - label: 证据质量优先
  - label: 执行结果优先
included_memory:
  - ref: decision_001
    reason: 当前节点验收标准依赖该决策
excluded_memory:
  - ref: trace_999
    reason: 与当前目标无关且噪声高
```

核心原则：

> **如果 Sufficiency Gate 判断上下文不足，Codex 应先追问或给选项，而不是继续补全。**

### 20.6 Memory Manifest：让用户知道 Codex 为什么知道这些

每次 Context Pack / Assist Context Pack 都应附带 `Memory Manifest`，记录本次给 Codex 的记忆来源。

```yaml
memory_manifest:
  included:
    - ref_type: decision
      ref_id: decision_001
      reason: 当前节点目标依赖该架构决策
      authority: user_confirmed
      freshness: current
    - ref_type: digest
      ref_id: digest_v3
      reason: 提供上一节点结论
      authority: system_summary_confirmed
      freshness: current
  excluded:
    - ref_type: trace
      ref_id: trace_002
      reason: 原始日志过长，仅纳入摘要
  warnings:
    - asset_009 已标记 stale，仅作为历史参考
```

这可以解决两个问题：

1. 用户能检查 Codex 的上下文是否合理；
2. 后续复盘时能知道某次 AI 补全基于哪些记忆。

### 20.7 记忆更新闭环

系统记忆不是一次性写入，而应在每次确认后更新。

```text
用户输入 / Codex Assist / NodeRun
  → Trace 记录过程
  → 生成 Draft / AssetCandidate / DecisionCandidate
  → 用户确认
  → 写入 Confirmed Asset / Decision / NodeContract / Digest
  → 更新 Memory Index / Workspace Digest
  → 下一次 Context Pack 引用最新记忆
```

对 Codex 自身记忆的同步建议：

```text
系统发现稳定偏好或规则
  → 生成 RunnerMemoryCandidate
  → 用户确认
  → 写入 AGENTS.md 系统段或项目规则资产
  → 可选提示用户手动同步到 Codex Memory
```

V1 不直接依赖自动写入 Codex 原生 Memory。

### 20.8 对 Assist 补全的特别要求

因为 Assist 经常发生在“用户没想清楚”的场景，所以比正式 NodeRun 更需要记忆充分性检查。

Assist 在补全前必须知道：

```text
当前页面 / 字段；
用户正在试图完成什么；
已有值是什么；
哪些值已确认、哪些只是草稿；
当前节点类型和目标；
相关资产 / 决策 / Digest；
用户偏好：需要追问、给选项、不要硬编；
可以修改哪些字段；
不能修改哪些字段；
信息不足时如何提问。
```

输出时必须区分：

```text
confirmed facts：系统确认事实；
assumptions：当前假设；
questions：需要用户回答的问题；
options：可选方案；
draft_patch：建议写入的草稿；
confidence：置信度。
```

### 20.9 V1 实现要求

V1 至少要实现：

```text
Memory Manifest：每个 Context Pack / Assist Context Pack 记录 included/excluded memory。
Context Sufficiency Gate：生成上下文前做缺失、冲突、过期、权限检查。
Memory Scope：区分 user / project / workspace / node / thread / runner。
Authority 标记：区分 user_confirmed / system_confirmed / ai_draft / imported / codex_memory_hint。
AGENTS.md 生成：写入稳定项目规则和“以 Context Pack 为准”的规则。
RunnerMemoryCandidate：把稳定偏好/规则作为候选，用户确认后写入项目规则或 AGENTS.md。
```

第一版成功标准补充：

```text
Codex 在补全节点参数、验收标准、Digest 或执行任务时，能看到它应该知道的系统记忆；
用户能查看本次补全使用了哪些记忆；
当记忆不足、冲突或过期时，Codex 会追问、给选项或标记假设；
Codex 自身记忆只能辅助，不会覆盖系统确认事实。
```

## 21. 简单账户雏形与可选 GitHub 账号绑定

> 来源：关于“系统需要添加绑定 GitHub 账户功能，且是否绑定应是可选的，同时系统需要有一个简单账户雏形”的进一步确认。  
> 状态：作为第一版用户主体、Review、资产归属、GitHub PR 能力的基础设计。

### 21.1 为什么 V1 也需要账户雏形

即使第一版优先面向个人本地使用，系统也不能完全没有账户概念。原因是：

```text
用户确认资产需要确认人；
DecisionRecord 需要决策人；
HumanReview 需要 reviewer；
Git commit / PR 需要 actor；
GitHub 账号绑定需要归属到某个本地用户；
未来小团队扩展需要成员、权限、评论、审计基础。
```

因此 V1 应实现一个轻量账户模型，而不是完整企业级账号体系。

核心原则：

> **V1 账户不是为了做复杂权限，而是为了给确认、决策、资产归属、GitHub 绑定和未来团队扩展提供主体。**

### 21.2 V1 账户形态：Local Owner Account

第一版默认采用本地优先账户模型：

```text
Local Owner Account
  - 第一次启动系统时创建；
  - 默认代表当前本机使用者；
  - 可在本地单用户模式下自动登录；
  - 保留 password / session / role 字段，为后续局域网或团队部署扩展。
```

推荐 V1 账户字段：

```text
User
  id
  display_name
  email?                 # 可选
  avatar_url?            # 可选
  role: owner | member
  auth_mode: local_auto | local_password | external
  created_at
  updated_at
```

V1 可以先支持两种模式：

| 模式 | 说明 |
|---|---|
| local_auto | 本机单用户开发模式，默认自动登录 Local Owner。 |
| local_password | 可选，用户设置本地密码后需要登录。 |

后续再扩展：多人账号、邀请、团队权限、SSO 等。

### 21.3 GitHub 绑定是可选增强，不是系统使用前提

GitHub 账号绑定必须是可选的。未绑定 GitHub 时，系统仍然应能完成：

```text
Project Workspace 创建；
Workflow / Node / Context Pack；
CodexRunner 执行；
本地文件修改；
Git diff；
Git branch；
Git commit；
CodeChangeAsset；
PR body 草稿生成。
```

绑定 GitHub 后增强：

```text
读取 GitHub 用户信息；
识别 remote repo 对应的 owner/repo；
检查当前用户对仓库是否有权限；
push branch（如果本地 git 凭据或 token 可用）；
通过 GitHub API 创建 PR；
可选读取 Issue / PR 信息；
把 PR URL 写入 CodeChangeAsset；
把 GitHub 身份关联到 HumanReview / CodeChange。
```

核心原则：

> **GitHub 绑定增强协作闭环，但不能成为本地优先系统的硬依赖。**

> **V1.2 演进说明：** 本节保留 V1 的本地降级原则；当前 V1.2 首次启动流程已把 GitHub 与 Codex 验证设为 Setup 硬门禁，正式行为以 V1.2 开发计划为准。

### 21.4 GitHub 绑定方式：OAuth 优先，Token / env ref 作为本地原型 fallback

结合本地优先、自托管和毕业设计原型实际，推荐分层：

| 方式 | V1 定位 | 说明 |
|---|---|---|
| GitHub OAuth Web Flow | 推荐正式方式 | 用户在浏览器授权，系统获得访问 token。适合产品化体验。 |
| Fine-grained PAT / env ref | V1 fallback | 用户提供 token 或环境变量名，系统调用 GitHub API 验证身份。适合本地原型和自托管。 |
| GitHub App | 后续增强 | 更适合组织和细粒度安装权限，V1 可预留。 |
| gh CLI | 可选辅助 | 当前环境不应把 gh 作为硬依赖。 |

官方资料依据：GitHub OAuth Web Flow 是“重定向用户请求 GitHub 身份 → GitHub 回调 → 应用使用 access token 访问 API”的流程；GitHub 也建议个人 API 访问优先使用 fine-grained personal access token，而不是 classic token。

### 21.5 凭据保存原则

V1 不应把 GitHub token 当普通配置明文保存。

推荐策略：

```text
优先保存 secret_ref：例如 env:GITHUB_TOKEN；
如必须保存 token，本地加密保存，并标记来源、scope、过期时间；
API response 和日志必须 mask token；
Context Pack 不包含 token 明文，只能包含工具是否可用和权限摘要；
Trace 记录 GitHub API 调用摘要，不记录敏感 token。
```

数据库中应保存的是：

```text
connected_account：绑定关系；
github_account：GitHub 用户公开信息；
credential_ref：凭据引用或加密凭据 ID；
scopes / permissions summary：权限摘要；
last_verified_at / status：健康状态。
```

### 21.6 GitHub 绑定最小流程

V1 建议流程：

```text
用户进入 Settings / Account
  → 查看 Local Owner Account
  → 点击 Connect GitHub（可跳过）
  → 选择 OAuth 或 Token/env ref
  → 系统验证 GitHub 身份：GET /user
  → 保存 connected_account + github_account + credential_ref
  → 显示 GitHub login、avatar、权限状态
  → 在 Git Review / PR 页面启用 Create PR 能力
```

未绑定时：

```text
Git Review 页面显示：
  - 本地 diff / branch / commit 可用；
  - Create PR 不可用；
  - 可生成 PR body 草稿；
  - 用户可选择现在绑定 GitHub。
```

### 21.7 账户与系统对象的关系

V1 中以下对象都应记录 actor：

```text
Project.created_by
Workflow.confirmed_by
NodeContract.confirmed_by
ContextPack.confirmed_by
AssistSession.created_by
HumanReview.reviewer_id
AssetVersion.confirmed_by
DecisionRecord.decided_by
WorkspaceDigest.confirmed_by
CodeChange.committed_by
GitHub PR created_by_connected_account_id
TraceEvent.actor_id
```

这样后续扩展小团队时，不需要重构核心追溯模型。

### 21.8 对第一版成功标准的补充

第一版应补充：

```text
系统启动后存在一个 Local Owner Account；
用户确认、资产、决策、Digest、Git 操作都能记录 actor；
GitHub 绑定可选；
未绑定 GitHub 时本地闭环仍可运行；
绑定 GitHub 后可创建 PR 或至少验证账号与 repo 权限；
所有 GitHub token / secret 不进入 Context Pack、Trace 明文或前端响应。
```

## 22. GitHub 集成采用“双模式”：托管 SaaS App + 用户自带 App

> 来源：关于“个人开发者必须强关联 GitHub、主用户应拥有接近本地开发的完整权限、未来协作者需要稳妥 GitHub 协作方案”的进一步确认。  
> 状态：作为 V1.2 GitHub 集成与权限模型的核心方向。

### 22.1 核心判断

如果系统只做本地自托管，不由开发者提供统一 SaaS 服务，那么每个用户都需要自行创建 GitHub App、配置 Client Secret、Private Key、Webhook、Callback、Installation 等信息，完整 GitHub 使用成本会明显升高。

因此后续应采用“双模式”：

| 模式 | 适用对象 | 配置成本 | 自主权 | 说明 |
|---|---|---:|---:|---|
| Supersystem 托管 GitHub App / SaaS 模式 | 普通个人开发者、低成本试用用户 | 低 | 中 | 用户只需登录、授权、安装 App、选择仓库；Private Key、Webhook、installation token 由服务端托管。 |
| 用户自带 GitHub App / BYO App 模式 | 高自主权用户、自托管用户、小团队 Owner | 中高 | 高 | 用户自己创建并持有 App ID、Client Secret、Private Key、Webhook Secret；系统只读取用户提供的本地/自托管配置。 |

核心原则：

> **想让用户最省事，就提供托管 App；想让用户完全自主，就支持用户自带 App；系统最终应双模式并存。**

### 22.2 个人开发者与主用户权限一致

当前产品语义中，个人开发者就是项目主用户 / Owner。主用户应拥有接近本地开发的完整体验：

```text
强绑定自己的 GitHub 账号；
安装 GitHub App 到自己的仓库；
选择可操作仓库；
读取 / 修改 / 提交代码；
创建分支、push、PR；
读取 issue / PR / checks；
运行 Codex Docker Runner；
审批节点本质变更；
管理 GitHub / Codex / cc-switch 配置；
进入 Codex 配置时自动发现本机来源，在 cc-switch、`~/.codex` 快照、官方 Device Login 与手工 API 配置之间显式选择；
确认脱敏预览后再导入，不允许系统自动复制 Secret、切换 Profile 或覆盖既有配置。
```

目标不是让所有人都拿最高权限，而是：

> **Owner 在网站上的开发体验，应尽量等价于直接在本地开发。**

### 22.3 未来协作者采用“双重权限约束”

未来团队协作中，其他成员不应天然继承 Owner 的完整权限，而应同时满足：

```text
成员在 Supersystem 项目中拥有相应角色；
成员自己的 GitHub 账号已绑定；
GitHub 侧确认该成员对目标 repo 有对应权限；
目标 repo 已安装 Supersystem GitHub App；
敏感操作经过项目审批策略。
```

协作者默认更适合走：

```text
提交 proposal；
创建 task branch；
生成 PR 草稿或 PR；
参与 review；
由 Owner / Reviewer 审批关键变更。
```

### 22.4 User Token 与 Installation Token 分工

GitHub 集成不应只做 OAuth 登录，也不应只做 App installation。更合理的是双 token 分工：

| Token 类型 | 代表谁 | 用途 |
|---|---|---|
| User Access Token | 当前用户本人 | 身份识别、repo 权限校验、审计 actor、必要时以用户身份执行敏感操作。 |
| Installation Access Token | Supersystem GitHub App installation | 自动化读写仓库、创建 bot commit / PR、后台任务、Runner 访问 repo。 |

这意味着 V1.2 需要补齐 GitHub App installation 能力：

```text
installation callback / setup URL；
installation_id 保存；
App JWT 生成；
installation access token 生成；
repo 授权范围同步；
webhook 验签与事件处理；
用户 token 与 installation token 的权限交叉校验。
```

### 22.5 对 V1.2 的方向影响

V1.2 计划中应把 GitHub 能力从“账号绑定增强项”升级为“个人开发者高自主权开发闭环”的关键基础设施，但仍保留本地优先降级路径：

```text
未绑定 GitHub：本地 workspace / diff / commit / PR body 草稿可用；
绑定 OAuth：可识别用户、校验权限、展示 GitHub 身份；
完成 App installation：可稳定操作已授权 repo；
托管 App 模式：普通用户低成本使用；
BYO App 模式：高级用户和自托管用户获得完整自主权。
```

> **V1.2 实施说明：** 上述“未绑定时降级”保留为长期本地优先方向；当前 V1.2 验收采用 GitHub/Codex 首次 Setup 硬门禁，后续若恢复可选降级需另行修改计划和测试。

## 23. Codex 首次配置采用自动发现与四路径显式选择

> 来源：关于“第三方 API 为什么缺少 URL、cc-switch 为什么没有真正进入配置流程，以及本机已有 Codex 配置应如何复用”的进一步确认。
> 状态：作为 V1.2 Codex Setup、Secret、Profile 和 Probe 的补充核心方向。

### 23.1 核心原则：自动发现不等于自动导入

本地优先系统应帮助 Owner 发现已经存在的工具配置，避免重复填写 Provider、URL、模型和凭据；但本机配置可能包含 Secret、私人路径、危险权限和与当前项目无关的设置，因此系统不能在用户进入页面时直接复制或切换。

核心原则：

> **系统可以自动告诉用户“发现了什么”，但只有用户选择来源、查看脱敏预览并明确确认后，才可以导入配置和凭据。**

Codex Setup 提供四条路径：

| 路径 | 适用场景 | 是否需要 cc-switch |
|---|---|---:|
| cc-switch Provider | 用户已经用 cc-switch 管理第三方 Provider | 可选导入来源 |
| `~/.codex` 快照 | 用户已经配置本机 Codex CLI | 取决于当前 Provider |
| 官方 Device Login | 用户使用 ChatGPT/Codex 官方账户 | 不需要 |
| 手工 API 配置 | 用户新建或无法自动发现 | 第三方需要 |

已有有效 AIWS Profile 时，自动发现只能提供“重新发现 / 导入为新 Profile”，不得覆盖当前 Profile。

### 23.2 自动发现模型

进入 Codex Setup 后，发现与 Docker 检查并行进行：

```text
打开 Codex Setup
  ├── 检查 Docker / runner image
  ├── 检查 cc-switch 固定配置目录和数据库
  ├── 检查 ~/.codex/config.toml 与 auth.json
  ├── 检查 Codex CLI / Device Login capability
  └── 始终提供手工 API 配置
```

自动发现只返回来源摘要：

```text
source kind
available / absent / invalid / permission_denied
schema / format 是否支持
provider_count / current_present
config_present / auth_kind / credential_present
固定 path label，而不是绝对路径
```

发现和刷新不得：

- 修改 cc-switch / Codex 源文件；
- 创建 vault Secret；
- 改变 Setup 或 active profile；
- 自动运行 Provider 请求；
- 把 raw JSON、TOML、auth 或解析错误原文发送到前端。

### 23.3 cc-switch Provider 发现与导入

cc-switch 的权威本机来源是其配置数据库与 Provider 状态，不是两个开源仓库是否 clone 成功。系统应从固定路径以只读方式发现 Codex Provider，并让用户选择具体条目。

脱敏 Provider 预览包含：

```text
source_provider_id
display_name
is_current / official
model_provider / model
sanitized base_url
wire_api / api_format
credential_present
importable / issues
public_revision
```

导入关系必须绑定：

```text
AIWS profile_id
  ↔ cc-switch source_provider_id
  ↔ public_revision
  ↔ profile-scoped credential_ref
```

因此，一个历史全局 `cc_switch = synced` 状态不能解锁新建或其他 Provider。来源配置变化时只标记 stale，系统不得自动覆盖；用户需要再次预览并 re-import。

Codex 原生 Responses Provider 可以导入为直连 Profile。`openai_chat` 表示需要 cc-switch 的 Responses ↔ Chat 转换能力，只有 local proxy 生命周期和健康检查通过后才可使用，不能改一个字段就伪装成直连。

### 23.4 `~/.codex` 采用安全快照，而不是直接共用全局目录

`~/.codex/config.toml` 可能同时包含：

```text
Provider / model / base_url / wire_api；
项目 trust 与本机绝对路径；
instructions / MCP；
network 与 permission；
Windows / TUI 状态；
experimental bearer 等 Secret。
```

因此导入策略必须是：

```text
读取固定路径
  → 解析 active Provider
  → 提取允许字段
  → 展示脱敏预览与省略项
  → 用户确认
  → 重建 profile-scoped TOML
  → 写入独立 CODEX_HOME
```

默认只导入 Provider、name、model、Base URL、wire API、`requires_openai_auth` 等运行所需字段。项目路径、dangerous permission、network、MCP、instructions、Windows/TUI 状态不得隐式继承；如果未来支持，应作为独立、可审查的配置变更。

`auth.json` 至少需要区分：

| auth kind | 处理方式 |
|---|---|
| API Key | 服务端读取后直接写 vault，TOML 不保留 literal Secret。 |
| ChatGPT OAuth | 整个必要 auth bundle 作为 Secret blob 写 vault，运行时 materialize 到 Profile 的 `CODEX_HOME`。 |
| mixed | 必须让用户选择，不能自动猜测。 |
| none / invalid | 不能形成 ready Profile，转到 Device Login 或手工配置。 |

第三方 Provider 不得继承本机残留的 ChatGPT OAuth 材料，否则会把官方登录错误用于第三方 endpoint。Provider 与 auth source 必须匹配。

### 23.5 官方账户 Device Login

官方登录是独立路径，不应被包装成第三方 Provider，也不依赖 cc-switch。

```text
用户选择 Device Login
  → 系统创建独立临时 CODEX_HOME
  → 启动 codex login --device-auth
  → 展示解析后的 verification URI 与 user code
  → 等待授权 / 轮询
  → 成功后 auth bundle 直接进入 vault
  → 删除临时目录
  → 生成 official Profile
  → 非写入 Probe
```

Device Login 事件流只能发送结构化状态，不能把任意 stdout / stderr 原样推送到浏览器。需要支持 pending、expired、denied、failed、cancelled、interrupted、retry 和 terminal 状态；服务重启后未完成请求标记 interrupted，不能误判成功。

### 23.6 Profile 与状态机

推荐统一状态机：

```text
idle
  → discovering
  → choice_required
  → inspecting
  → preview_ready
  → confirmation_required
  → importing
  → credential_stored
  → profile_written
  → probing
  → ready
```

异常分支：

```text
invalid / unavailable / permission_denied
credential_missing / auth_provider_mismatch
proxy_required / insecure_endpoint
expired / denied / cancelled / interrupted
probe_failed / stale
```

Setup 的 Codex ready 必须同时由服务端确认：

```text
Docker ready
source selected
credential ready
profile TOML valid
第三方 source import / proxy 条件满足
profile-scoped Probe ready
```

### 23.7 Secret 与本机读取边界

允许读取的默认位置：

```text
CC_SWITCH_CONFIG_DIR 或 ~/.cc-switch/cc-switch.db
~/.codex/config.toml
~/.codex/auth.json
```

HTTP 请求不能传入任意路径。服务端需要执行 realpath、普通文件、符号链接/目录联接、大小、schema、JSON/TOML 和 URL 校验。Base URL 只接受 HTTP(S)，默认拒绝 userinfo、query、fragment 与疑似 Secret 路径；非 loopback HTTP 需要额外确认。

任何 API Key、OAuth token bundle 或 embedded bearer：

```text
不进入浏览器请求或响应；
不进入普通 state、Profile TOML、Trace、Context Pack、artifact 或日志；
不返回 prefix、last4、长度、hash 或 vault ref；
只在服务端短暂读取并直接写 vault；
运行时才按当前 profile 解析并注入。
```

导入失败需要回滚新 Secret；替换凭据时先成功写入并切换新 ref，再删除旧 ref。来源文件在发现、预览和导入前后必须保持不变。

### 23.8 完成标准

```text
进入 Codex Setup 会发现本机来源但不产生副作用；
用户可以选择并导入具体 cc-switch Provider；
用户可以选择并安全导入 ~/.codex 快照；
用户可以完成官方 Device Login；
四条路径最终都落到 profile-scoped CODEX_HOME / credential ref / Probe；
第三方 Provider 明确展示 Base URL 与 API format；
任何 Secret 不出现在 API、DOM、state、Trace、artifact 或日志；
来源文件 hash / mtime 不变；
桌面、平板和移动端都能完成来源选择、预览、确认、取消和重试。
```

## 24. V1.3：从工作流画布升级为受管 Codex IDE

本章记录 V1.3 的锁定设计，不代表运行时已经完成。完成状态以 `docs/completion-audit.md` 和同一工作树上的自动化结果为准。

### 24.1 Project 先形成共同理解，再获得写权限

V1.3 不再把“创建 Project”等同于“创建一个可写空画布”。Project 首先是一个可恢复的 draft 对话，必须产出版本化 Project Brief：

```text
目标 / 用户 / 范围 / 功能
约束 / 里程碑 / 验收标准
风险 / 开放问题 / 初始 workflow draft
```

brainstorm 路径允许从 0 连续澄清；existing 路径允许一个代码源和多个 context source。确认操作才原子创建 workflow、节点和 Contract，并把 Project 激活。这样页面刷新、Codex 中断或导入重试都不会制造半个 active 项目。

### 24.2 外部源是输入，managed workspace 才是执行面

用户的本地目录、已有 checkout 和远端仓库都是来源，不是 AIWS 的隐式写目标。

```text
external source（read-only）
  → staging
  → traversal / symlink / size / archive 校验
  → clone 或 copy
  → .ai-workspace/workspaces/<projectId>/repo
  → per-Turn worktree
```

GitHub/Git URL 必须 clone；本地 Git 优先 local clone；普通目录复制。所有 Agent、CLI 和 Runner 写操作只发生在受管 repo/worktree。旧项目如果仍指向外部 repo，先进入 `workspace_migration_required`，不能用兼容捷径继续原地写。

### 24.3 Assist V3 以 Turn、事件和 Review 为中心

Session 负责长期线程，Turn 负责一次有界执行，Attachment/Context Pack/Memory Manifest 负责输入，Worktree 和 Review 负责写入隔离与合并。

typed event 只展示 Codex 官方可用的公开事件：

```text
text / plan / command / file_change / test
mcp / search / usage / approval
reasoning_summary / terminal
```

内部 reasoning 不进入 API、state 或 DOM。事件 sequence 必须稳定，支持 `Last-Event-ID` 重放。follow-up 可以 queue、steer 或 interrupt，但每个状态转换都必须产生可恢复终态。

Ask/Plan 强制只读；Agent 每 Turn 创建独立 worktree；CLI 使用同样的隔离与 Review，不享有绕过审批的特殊权限。

### 24.4 真实 CLI 是传输能力，不是一种日志样式

Host Profile 使用宿主 PTY，Docker Profile 使用容器 TTY，浏览器通过 WebSocket 承载输入和输出。必须支持 resize、Ctrl-C、断线重连、stop、exit 和服务重启后的 orphan 清理。

终端展示只保留截断且脱敏的输出，完整内容作为 Artifact 保存。环境变量、API Key、OAuth token、临时配置和 reconnect secret 都不能回显。若 PTY/TTY capability 不可用，就明确禁用 CLI；绝不能把 `codex exec --json` 的日志窗口命名为终端。

### 24.5 所有“等待人”的状态进入统一 attention 模型

Workflow/Contract Proposal 和 Agent Runtime Approval 共享：

```text
interrupting → queued → resolved
```

即时弹窗用于当前上下文中的决策；关闭或 Escape 只是 defer，不是拒绝。统一审批中心负责找回 queued 项目并按类型过滤。批准并应用必须把 revision/target hash 校验和领域写入放在同一事务中，防止用户审查 A 却应用已经变化的 B。

### 24.6 配置也是需要 Review 的外部变更

Provider、endpoint、凭据引用、模型、MCP、Skills 和项目指令不是普通表单保存。它们先形成 Config Revision 或 Change Proposal，再经批准、外部工具写入、重新发现、Probe 和激活。

第三方 Provider 可从手动 API、本机 Codex 或 cc-switch Catalog 导入，默认生成 AIWS 托管 native Profile。只有用户显式选择 cc-switch 管理模式时才以受管 CLI 为变更通道；CLI 必须锁定版本和 checksum，凭据通过私有临时文件传递，禁止直接写 SQLite。失败时恢复旧 Provider 并记录 reconciliation；该模式的 native fallback 需要额外明确选择。

### 24.7 V1.3 验收原则

```text
draft 未确认，不获得 workspace-write；
外部源在所有路径中保持不变；
Ask/Plan 不写文件；
并行 Agent/CLI Turn 不共享 worktree；
Review 目标变化时拒绝 apply；
Runtime Approval 可恢复且幂等；
cc-switch 真实数据库不被测试修改；
所有公开响应和 Artifact 都通过 Secret sentinel 扫描；
完整 verify 与受控 live 验收分别记录。
```

V1.3 明确不包含 Cloud delegation、browser/computer use、voice、automations 和后台 Agent。IDE 闭环、真实 CLI、统一审批和配置治理属于本版本目标，但只有自动化与 live 证据齐备后才能标记完成。
