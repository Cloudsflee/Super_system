## Q3. 系统核心到底是“插件平台”还是“AI 协作系统”？

**当前答案：** 系统核心不是传统插件平台，也不是工具聚合器，而是 **MCP 优先的 AI 协作系统**。  

更准确表述：

> 系统以 AI 协作为核心，以 MCP 作为主要协议层，用于连接外部服务、组织 AI 可调用能力，并在系统成熟后通过自身 MCP Server 向 Codex、Claude Code 等本地 AI Agent 暴露项目、任务、知识和工作流能力。

**状态：** 已纠偏并写入核心想法与愿景文档。

---

## Q4. MCP 作为协作核心是否合理？

**当前答案：** 合理，但应表述为 **MCP-first，不是 MCP-only**。  

MCP 适合作为：

- 外部服务连接层；
- AI 工具调用协议层；
- 系统能力暴露层；
- MCP Server / Tool / Resource 的能力目录。

但业务内核仍应独立存在：

- 项目；
- 任务；
- 工作流；
- 知识资产；
- 贡献事件；
- 决策记录；
- AI Trace。

**风险：** MCP 还在发展，不能把业务模型写死在某个 MCP SDK 或 Docker MCP Catalog 上。  
**状态：** 当前判断成立，但技术实现仍需验证。

---

## Q5. MCP 层是否意味着必须搭 MCP Server？

**当前答案：** 是。只要把 MCP 作为核心连接层，就绕不开 MCP Server。  

系统需要同时考虑两种方向：

```text
向外连接：系统作为 MCP Client，连接外部 MCP Server。
向外暴露：系统自身作为 MCP Server，被 Codex / Claude Code 等本地 AI 控制。
```

**系统中的 MCP Server 类型：**

1. 已存在的外部 MCP Server，例如 GitHub、filesystem、数据库等；
2. 没有 MCP 的服务，需要包装成自定义 MCP Server；
3. 本系统自身的 MCP Server，用于暴露项目、任务、知识和工作流能力。

**状态：** 已确认是重要架构层。

---

## Q6. 本地网站能否通过 Docker 快捷部署 MCP Server？

**当前答案：** 合适，但不能让浏览器前端直接控制 Docker。应采用：

```text
本地网站前端
  → 本地后端 / MCP Runtime Manager
  → Docker / Runtime Provider
  → 本地 MCP Server 容器
```

**适合 Docker 的原因：**

- 降低依赖安装成本；
- 隔离 MCP Server；
- 便于启用、禁用、卸载；
- 适合本地一键部署多个服务。

**限制：** Docker 是部署手段，不是系统核心。  
**状态：** 可作为 MVP 集成方向，但需要 Runtime Provider 抽象。

## Q8. Coolify 是否适合作为初始本地网站部署工具？

**当前答案：** Coolify 可以作为可选部署方案，但不应作为核心依赖。  

它适合：

- 部署网站；
- 部署后端；
- 部署数据库；
- 部署 Docker Compose 服务。

但它不负责：

- MCP tools/resources 能力发现；
- MCP 权限治理；
- AI 工作链推荐；
- 资产图谱；
- 项目上下文组织。

**状态：** 可选部署层，非核心能力。

## Q9. 工作流推荐如何保证一致性？

**当前答案：** 不能让 AI 自由发挥。应采用：

```text
稳定输入结构 + 工作流模板库 + MCP 能力目录 + 固定输出 Schema + 推荐校验器
```

一致性的来源不应是“AI 自觉”，而是系统约束：

| 机制 | 作用 |
|---|---|
| 输入标准化 | 把自然语言转为稳定项目画像。 |
| 工作流模板库 | 保证基础流程稳定。 |
| MCP 能力目录 | 限制工具推荐范围。 |
| 固定输出 Schema | 限制 AI 输出结构。 |
| 低随机性参数 | 降低输出波动。 |
| Prompt / 模板版本 | 保证推荐逻辑可追溯。 |
| 推荐校验器 | 过滤不合理推荐。 |
| 推荐版本记录 | 记录同一输入下为何变化。 |

**状态：** 当前答案可用，但需要进一步设计 Schema 和校验器。

---

## Q10. 工作流的具体实现是不是不能靠 AI 随便分析？

**当前答案：** 是。工作流不能是“用户一句话 → AI 直接给结论”。  

更合理的机制：

```text
多源输入 → 素材卡 → 证据卡 → 观点卡 → 决策卡 → 工作流资产
```

AI 的职责是：

- 摘要；
- 聚类；
- 追问；
- 生成候选理解；
- 给出可确认方案；
- 生成复盘草稿。

用户的职责是：

- 补充材料；
- 判断是否正确；
- 确认或否定；
- 选择方向；
- 修正抽象。

**状态：** 当前答案为“渐进式抽象”，需要进一步实现为产品流程。

## Q13. 资产是否应该分类？

**当前答案：** 应该。至少分为两大类：

### 1. 真实资产

来自具体项目、具体事实、具体过程。  
例如：

- 资料链接；
- 会议记录；
- Git commit；
- GitHub Issue / PR；
- AI Trace；
- 截图；
- 用户语音；
- 决策记录；
- 测试报告；
- 交付物。

特点：有来源、有时间、有上下文、有证据。

### 2. 通用资产

从真实资产中提炼出来，可被未来项目复用。  
例如：

- 工作流模板；
- 工具链模板；
- MCP 连接器组合；
- Prompt 模板；
- 决策模式；
- 检查清单；
- 风险清单；
- 问题-方案模式；
- 协作模式；
- 架构原则。

特点：不绑定某个项目，但必须能追溯到真实资产。

**状态：** 已确认应采用“双层协作资产模型”。

## Q14. 通用资产模板如何复用？

**当前答案：** 通用资产模板不能简单复制粘贴，而应通过“实例化、参数化、适配、校验、回写”的方式复用。

### 推荐复用流程

```text
选择/推荐通用资产模板
  → 检查适用条件
  → 填充当前项目参数
  → 生成项目实例
  → 执行并记录真实过程
  → 评估效果
  → 回写模板经验或派生新版本
```

### 一个工作流模板应包含

| 字段 | 说明 |
|---|---|
| 名称 | 例如“前期调研工作流”。 |
| 适用场景 | 适合什么项目、阶段、角色。 |
| 前置条件 | 需要哪些输入、工具、MCP 能力。 |
| 阶段列表 | 每个阶段的目标、输入、输出、工具。 |
| 产出契约 | 每个阶段最少应该产出什么。 |
| 质量门槛 | 判断产出是否足够。 |
| 可替换步骤 | 哪些步骤可以跳过或替换。 |
| 风险提示 | 常见失败原因。 |
| 来源资产 | 从哪些真实资产抽象而来。 |
| 版本 | 模板演化历史。 |

### 复用方式

| 方式 | 说明 |
|---|---|
| 直接实例化 | 模板适用当前项目，直接生成项目工作流。 |
| 参数化复用 | 根据项目类型、角色、工具替换部分步骤。 |
| 组合复用 | 把多个模板组合成新工作流。 |
| 派生复用 | 从旧模板 fork 出新版本。 |
| 推荐复用 | AI 根据当前项目上下文推荐模板。 |
| 对比复用 | 展示多个候选模板差异，让用户选择。 |

**关键原则：**

> 通用资产不是“永远正确的结论”，而是“带适用条件、来源证据和版本记录的可执行模式”。

**状态：** 当前答案可作为系统设计基础。

## Q15. 资产图谱的意义是什么？

**当前答案：** 资产图谱不是为了炫技，而是为了支撑可追溯、可推荐、可验证、可演化。

### 资产图谱解决的问题

| 问题 | 资产图谱的作用 |
|---|---|
| 资产从哪里来？ | 通过 `derived_from` 追溯来源。 |
| 这个结论有证据吗？ | 通过 `supports` 连接证据资产。 |
| 这个模板适合当前项目吗？ | 通过 `applies_to`、`recommended_for` 判断。 |
| 这个资产是否过时？ | 通过 `validated_by`、`superseded_by`、`last_verified_at` 判断。 |
| 为什么 AI 推荐这个工作流？ | 展示推荐路径：当前项目 → 相似项目 → 已验证模板。 |
| 人类纠偏是否可能错？ | 保留纠偏来源、状态和反证关系。 |
| 未来如何复用？ | 将通用资产关联到新项目实例。 |

### 典型关系

```text
真实素材 → 支撑 → 观点
观点 → 形成 → 决策
决策 → 影响 → 工作流模板
工作流模板 → 应用于 → 新项目
新项目执行结果 → 验证/修正 → 原模板
```

**结论：**

> 没有资产图谱，资产只是文件；有资产图谱，资产才能成为 AI 可推理、可追溯、可复用的协作记忆。

**状态：** 当前答案成立，关系类型需进一步收敛。

## Q16. 资产的展现形式应该如何定义？

**当前答案：** 资产不能只有一种展示形式，应采用“统一资产对象 + 多视图展示”。

### 统一资产卡片字段

| 字段 | 说明 |
|---|---|
| 标题 | 资产名称。 |
| 类型 | 真实资产 / 通用资产。 |
| 子类型 | 资料、决策、工作流、工具链、问题-方案、Prompt 等。 |
| 阶段 | 调研、需求、设计、开发、测试、复盘等。 |
| 摘要 | 简短说明。 |
| 来源 | 原始材料或生成过程。 |
| 状态 | 草稿、待确认、已确认、已废弃、已过期等。 |
| 可信度 | AI 初判 + 用户确认 + 证据强度。 |
| 关联资产 | 支撑、反驳、派生、应用、验证等关系。 |
| 适用条件 | 适合什么项目和场景。 |
| 最后验证时间 | 用于判断是否过时。 |

### 展示方式

| 视图 | 适用场景 |
|---|---|
| 卡片视图 | 用户快速理解单个资产。 |
| 时间线 | 查看资产如何随项目演化。 |
| 图谱视图 | 查看资产之间的来源、支撑、派生关系。 |
| 阶段看板 | 查看某个工作流阶段有哪些输入/输出资产。 |
| 证据面板 | 查看一个结论由哪些真实资产支撑。 |
| 决策日志 | 查看关键判断如何形成。 |
| 复盘报告 | 项目结束后的总结输出。 |

**设计原则：**

> 默认展示摘要和关键关系，复杂追溯通过逐层展开，而不是一上来给用户看完整图谱。

**状态：** 当前答案可作为 UI 设计原则。

# C. 工作流执行与失败处理问题

## Q17. 工作流中某个阶段的产出如何保证？

**当前答案：** 不能保证每个阶段一定成功，但可以定义“阶段产出契约”和“质量门槛”。

### 阶段产出契约

每个阶段都应定义：

| 字段 | 说明 |
|---|---|
| 阶段目标 | 当前阶段要解决什么问题。 |
| 必要输入 | 至少需要哪些材料或上下文。 |
| 可用工具 | 当前阶段可调用哪些 MCP 能力。 |
| 预期输出 | 应产出什么资产。 |
| 最小完成标准 | 什么情况下算“阶段完成”。 |
| 质量检查 | 如何判断产出是否可靠。 |
| 阻塞条件 | 什么情况下不能继续推进。 |

例如“前期调研阶段”：

```text
必要输入：调研目标 + 至少 3 个来源材料或用户确认的调研问题
预期输出：调研问题卡、素材卡、候选观点卡
完成标准：每个候选观点至少关联一个来源或标记为假设
```

**结论：**

> 产出保证不是保证 AI 一定做对，而是保证每个阶段有明确的输入、输出、检查和阻塞机制。

**状态：** 需要后续设计工作流阶段 Schema。

---

## Q18. 如果工作流某个阶段卡住，没达到产出保证，怎么办？

**当前答案：** 不应该让 AI 硬编。应进入“阻塞处理流程”。

### 阻塞状态

```text
进行中 → 产出不足 → 阻塞诊断 → 请求输入/调整路径/降级输出 → 用户确认 → 继续或终止
```

### 可能处理方式

| 阻塞原因 | 处理方式 |
|---|---|
| 输入不足 | 让用户补充材料，或列出缺失信息。 |
| 工具不可用 | 推荐启用 MCP 连接器，或使用手动上传。 |
| 证据冲突 | 标记冲突，不生成确定结论。 |
| AI 不确定 | 降低置信度，生成候选而非结论。 |
| 用户无法表达 | 通过选择题、例子、反例、截图、语音降低表达门槛。 |
| 阶段不适用 | 允许跳过、替换或拆分阶段。 |

### 阻塞也应成为资产

例如：

```text
阻塞卡片：前期调研阶段缺少一手来源
影响：无法确认 MCP Runtime 方案优劣
建议：补充 Docker MCP、MCPHub、Coolify 官方资料
```

**状态：** 当前答案可作为工作流引擎设计基础。

## Q19. 人类纠偏如果是错的怎么办？

**当前答案：** 人类纠偏应被视为“带来源的决策/判断”，不是不可修改的真理。  

设计上应做到：

- 保留纠偏人；
- 保留纠偏时间；
- 保留纠偏理由；
- 保留被纠偏前的版本；
- 允许未来证据反驳；
- 允许资产状态变为“有争议”或“已废弃”；
- AI 可以基于新证据提示“该纠偏可能需要复查”。

### 推荐状态

```text
AI 草稿
  → 用户确认
  → 已确认资产
  → 被新证据挑战
  → 待复核
  → 维持 / 修正 / 废弃
```

**原则：**

> 用户拥有决策权，但系统保留证据、版本和反证能力。

**状态：** 当前答案成立，需在资产状态机中实现。

## Q20. 如果事实随着时间变化怎么办？

**当前答案：** 所有事实类资产都应有时间属性和验证状态。  

### 需要记录

| 字段 | 说明 |
|---|---|
| `created_at` | 资产创建时间。 |
| `source_time` | 来源信息发布时间或发生时间。 |
| `last_verified_at` | 最近验证时间。 |
| `valid_until` | 可选，有效期。 |
| `status` | active / stale / superseded / deprecated / disputed。 |
| `source_url` | 来源链接或引用。 |
| `verification_method` | 如何验证。 |

### 事实变化处理

```text
旧事实 → 标记为可能过期 → 触发复核 → 获取新证据 → 更新资产版本 → 保留旧版本
```

例如：

```text
“某 MCP 项目支持某功能”
  2026-07-04 确认为真
  2026-09-01 项目改版
  系统标记 stale
  用户或 AI 重新验证
```

**状态：** 当前答案成立，后续需设计自动复核机制。

# D. 人机交互与可追溯性问题

## Q21. 人机交互模型应该怎么做？

**当前答案：** 应采用“AI 提议、用户确认、系统记录”的协作模型。

```text
AI 负责生成候选
用户负责判断和选择
系统负责记录证据、版本和关系
```

### 推荐交互模式

| 模式 | 作用 |
|---|---|
| 向导式初始化 | 帮用户从模糊目标开始。 |
| Inbox 收集箱 | 接收链接、文件、截图、语音、对话、代码等原始输入。 |
| AI 候选卡片 | AI 生成摘要、观点、问题、决策候选。 |
| 用户确认按钮 | 对 / 不对 / 部分对 / 稍后处理。 |
| 证据侧栏 | 显示某个观点来自哪些材料。 |
| 阶段看板 | 展示当前工作流阶段和产出状态。 |
| 追溯时间线 | 查看过程如何演化。 |
| 资产图谱 | 高级用户查看关系网络。 |

**关键原则：**

> 不要求用户一次性写清楚，而是通过低门槛输入和逐步确认完成抽象。

**状态：** 当前答案可作为交互设计基础。

## Q22. 如何做到全流程追溯且好用？

**当前答案：** 不能把所有追溯信息一次性暴露给用户，应采用“渐进式披露”。

### 追溯层级

| 层级 | 用户看到什么 |
|---|---|
| L0 摘要层 | 当前结论、当前推荐、当前风险。 |
| L1 阶段层 | 工作流阶段、每阶段输入输出。 |
| L2 资产层 | 相关资产卡片、决策卡、证据卡。 |
| L3 关系层 | 资产图谱、支撑/反驳/派生关系。 |
| L4 原始层 | 原始文件、日志、AI Trace、MCP 调用记录。 |

默认展示 L0-L1，用户需要时再展开 L2-L4。

### 好用的关键

- 默认给结论和下一步；
- 允许查看“为什么”；
- 允许继续展开“证据是什么”；
- 允许追溯到原始材料；
- 不强迫普通用户理解完整图谱。

**状态：** 当前答案成立，但 UI 实现难度高。

# E. 当前最难但最有价值的问题

## Q24. 通用资产、真实资产、资产图谱、工作流阶段和人机交互如何形成统一系统？

**当前答案：** 可以用以下闭环描述：

```text
多源输入
  → 真实资产

  → 新项目执行
  → 新真实资产
```

| 模块 | 作用 |
|---|---|
| Inbox 输入收集箱 | 接收多源输入。 |

| Workflow Engine 工作流引擎 | 管理阶段、产出契约和阻塞状态。 |

| Human Confirmation Layer | 用户确认、纠偏、版本化。 |

# F. 当前建议的关键概念命名

## 1. 双层协作资产模型

```text
真实资产层：保存项目中实际发生的事实、证据、过程和交付物。
通用资产层：从真实资产中抽象出可复用的工作流、工具链、决策模式和经验模板。
资产图谱层：维护二者之间的来源、支撑、应用、验证和演化关系。
```

## 2. 渐进式抽象

```text
用户不需要一开始把想法完整表达清楚，系统通过持续接收材料、追问、聚类、确认和复盘，把模糊经验逐步抽象成可复用资产。
```

## 3. 阶段产出契约

```text
每个工作流阶段都定义目标、必要输入、预期输出、质量门槛和阻塞条件。
```

## 4. MCP-first，但不是 MCP-only

```text
MCP 是 AI 协作和生态连接的核心协议层；项目、任务、资产、工作流和贡献事件仍是系统自身业务内核。
```

## 5. AI 提议，人类确认，系统追溯

```text
AI 生成候选，用户做判断，系统记录来源、版本、关系和演化。
```

# H. 当前阶段的总判断

当前系统真正困难的地方不在于“接入 AI”或“接入 MCP”，而在于：

> 如何把多源输入、团队过程、AI 调用、人工纠偏和项目交付，逐步抽象为可追溯、可验证、可复用、不过度打扰用户的协作资产。

因此，系统设计应避免两个极端：

1. **AI 全自动幻想式总结**：快，但不可靠。  
2. **全流程手工记录**：可靠，但用户负担太重。

更合理的中间路线是：

> AI 辅助抽象，用户轻量确认，系统保留证据和关系，资产逐步成熟。

# I. 与老师交流后的新增问题：场景收敛与选题落地

> 记录时间：2026-07-04  
> 来源：与指导老师关于毕设选题方向的交流截图。  
> 记录目的：先作为问题与风险沉淀，不立即并入 `核心想法.MD`。

## Q25. 当前方案是否过于“通用平台化”？

**问题来源：** 老师指出，单纯做“通用工具集成 / 通用 AI 协作平台”不一定适合作为学生毕设主方向，因为这类方向容易变成泛泛的平台或框架，缺少具体业务验证。

**当前理解：** 现有方案容易被理解为：

```text
通用 AI 协作平台
  + MCP 工具集成
  + 插件/连接器管理
  + 工作流推荐
  + 资产图谱
```

但老师更希望看到的是：

```text
具体业务场景
  → 业务工作流落地
  → AI 协作介入
  → 工具/MCP 集成作为支撑
  → 形成可验证成果
```

**风险：**

- 选题过大；
- 通用性难以证明；
- 容易与已有通用 Agent 平台、工具集成平台重复；
- 答辩时容易被质疑“业务价值在哪里”；
- 可能变成“先造框架，再找应用”，落地风险高。

**当前阶段答案：** 需要把方向从“通用平台优先”调整为“场景驱动优先”。

**状态：** 重要待细化问题。

## Q26. 是否应该先选一个具体业务场景，而不是先做通用框架？

**当前答案：** 是。更稳妥的路径应是：

```text
选择一个具体业务场景
  → 落地该场景下的 AI 协作工作流
  → 使用 MCP 连接必要工具
  → 记录过程与人类纠偏
  → 沉淀真实资产和通用资产
  → 最后抽象可迁移框架
```

而不是：

```text
先设计通用 AI 协作框架
  → 再寻找业务场景验证
```

**老师交流中的核心提示：**

- “找一个载体落实工作流”；
- “偏业务感觉更合理”；
- “通用工具和集成不是学生毕设的主要方向，除非特别出类拔萃”；
- “建议去落实一个场景”；
- “先把题目从愿景落实”；
- “有理想搞一个框架肯定好，但要有具体落点”。

**状态：** 待选择具体业务场景。

## Q27. 哪些业务场景适合作为落点？

**当前候选：**

| 场景 | 业务性 | 数据/材料可得性 | AI 适配度 | 实现难度 | 当前评价 |
|---|---|---|---|---|---|
| 线上营销 / 内容运营 | 高 | 中 | 高 | 中 | 推荐进一步考虑，用户有相关实习背景。 |
| 小型电商 / 直播运营 | 高 | 中 | 高 | 中高 | 有业务感，但真实数据和流程可能较复杂。 |
| 独立开发者 / 开源项目维护 | 中 | 高 | 高 | 中 | 与 Git/GitHub MCP 很契合，但业务感稍弱。 |
| 毕设 / 研究项目管理 | 中 | 高 | 高 | 低 | 易落地，但可能显得偏学生自用。 |
| 通用 AI 协作平台 | 低/不明确 | 不确定 | 高 | 高 | 不建议作为第一落点。 |
| 具体行业 Agent，如农业、电力、汽车、环境等 | 高 | 低/中 | 中/高 | 高 | 老师提到行业更有体量，但需要专业背景。 |

**老师观点提示：**

- 未来空间更大的可能是行业；
- 行业才有体量，才有现金；
- 但行业需要专业背景；
- 对学生来说，可以先选一个自己能理解和落地的具体业务。

**当前倾向：** 可以优先考虑与已有实习/项目经历相关的线上营销、内容运营、小型业务执行，或者以独立开发者/开源项目维护作为更技术友好的备选场景。

**状态：** 待进一步比较和最终选择。

## Q28. MCP 在场景驱动方案中应该处于什么位置？

**当前答案：** MCP 不应作为选题唯一卖点，而应作为业务工作流中的技术支撑层。

更稳妥表述：

> 本系统以具体业务场景中的 AI 协作为目标，以 MCP 作为连接外部工具与本地 AI Agent 的协议层，从而支撑业务工作流中的多工具协作、过程追溯和资产沉淀。

也就是说：

```text
业务场景是问题来源
AI 协作是系统目标
MCP 是技术支撑
资产化是长期价值
```

**风险：** 如果过度强调 MCP，容易被认为是在追技术热点；如果完全弱化 MCP，又会丢失系统的前瞻性和工程特色。

## Q35. 和老师交流后的总判断

当前最重要的优化方向：

> 不要证明“我能做一个通用 AI 协作平台”；而要证明“我能在一个具体业务场景中，用 MCP-first 的 AI 协作方式，把工作流跑通，并沉淀可复用资产”。

# J. 新增问题：资产与工作流的关系、资产动态展示与网站化呈现

> 记录时间：2026-07-04  
> 来源：关于“资产和工作流之间的联系是什么、资产是否只能静态展示、是否能以网站形式给出”的讨论。  
> 记录目的：这些问题对系统形态影响很大，部分结论已同步到 `核心想法.MD`，具体实现仍需继续细化。

## Q36. 资产和工作流之间到底是什么关系？

**当前答案：**

```text
工作流 = 如何做事
资产 = 做事过程中产生、依赖、复用、验证的东西
```

二者不是并列模块，而是互相生产和验证：

| 关系 | 说明 |
|---|---|
| 工作流消费资产 | 一个调研工作流需要输入资料、链接、截图、历史知识。 |
| 工作流产生资产 | 每个阶段产出调研卡、决策卡、报告、任务、复盘。 |
| 工作流依赖资产 | 工作流可以依赖检查清单、Prompt 模板、工具链模板。 |
| 工作流验证资产 | 某个通用模板是否有效，要看它在真实项目中跑得怎么样。 |
| 工作流本身也可以成为资产 | 一个成功跑通过的流程，可以被抽象成通用工作流模板。 |

**关键结论：**

> 工作流是资产的加工过程，资产是工作流的输入、输出、依据和复用结果。

**状态：** 已同步到 `核心想法.MD`。

## Q39. 能否让协作后端根据 AI 输出直接自行调整前端？

**当前答案：** 不建议让 AI 直接生成并执行任意前端代码。

原因：

- 安全风险高；
- 输出不稳定；
- 维护困难；
- 每次生成可能不一致；
- 容易破坏系统 UI；
- 难以保证用户体验。

更推荐：

> AI 生成结构化 ViewSpec，前端根据固定组件和 Schema 渲染。

示例：

```json
{
  "view_type": "research_report",
  "title": "MCP-first AI 协作系统调研报告",
  "sections": [
    {
      "type": "summary",
      "title": "核心结论",
      "asset_ids": ["decision_001", "decision_002"]
    },
    {
      "type": "evidence_list",
      "title": "支撑证据",
      "asset_ids": ["source_001", "source_002"]
    },
    {
      "type": "timeline",
      "title": "决策演化过程",
      "query": "project_decisions"
    }
  ]
}
```

**状态：** 已同步为“AI 不直接改前端代码，而是生成 ViewSpec”。

## Q41. 工作流页面应该长什么样？

每个阶段都应能点开查看：

- 输入资产；
- 输出资产；
- AI 做了什么；
- 用户确认了什么；

# K. 新增问题：开源工具接入、能力市场与非 MCP 工具处理

> 记录时间：2026-07-04  
> 来源：关于“类似 Coolify 的开源工具如何接入系统、如何像 VS Code 市场一样让用户按需接入开源工具、没有 MCP 的工具怎么办”的讨论。  
> 记录目的：部分原则已同步到 `核心想法.MD`，具体技术实现仍需继续细化。

## Q46. 类似 Coolify 的开源工具应该如何集成到当前系统？

**当前答案：** Coolify 这类工具不应作为系统核心，也不应直接等同于 MCP。它更适合作为：

> **Deployment Provider / Runtime Provider / Self-hosted App Provider**

它解决的是：

```text
如何把某个开源工具部署起来
```

但不直接解决：

```text
这个工具是否适合当前业务
AI 如何调用它
它的结果如何进入工作流
它能产生什么资产
```

因此系统应抽象出 Runtime Provider 层：

```text
Deployment / Runtime Provider
  ├── Docker Compose Provider
  ├── Coolify Provider
  ├── Docker MCP Gateway Provider
  ├── MCPHub Provider
  ├── Manual Provider
  └── Remote Service Provider
```

**状态：** 已同步到 `核心想法.MD`。

---

## Q47. 开源工具是否可以直接塞进稳定工作流？

**当前答案：** 如果只是临时探索或黑盒使用，用户可以强制接入；但如果要进入稳定、可复用、可推荐的正式工作流，就不能因为“能部署”而直接视为合格。

一个工具进入工作流前，至少需要明确：

- 它解决什么能力需求；
- 输入是什么；
- 输出是什么；
- 是否可被 AI 调用；
- 是否有 MCP；
- 是否有 API / CLI / Webhook；
- 是否只能人工使用；
- 是否适合当前项目阶段；
- 是否经过最小试用验证。

**核心原则：**

> 工具可以被用户临时接入和试用；但要成为稳定工作流节点，必须明确输入、输出、权限、资产产出和适配度。

**状态：** 已同步到 `核心想法.MD`。

## Q49. 不实际使用，如何判断开源工具是否符合用户需求？

**当前答案：** 需要“工具试用工作流”。

```text
用户提出目标
  → AI 推荐候选能力
  → 能力市场列出候选工具
  → Runtime Provider 部署或接入候选工具
  → 用户/AI 执行最小样例任务
  → 记录输入、输出、体验和问题
  → 生成工具评估资产
  → 用户确认是否纳入正式工作流
```

试用结果应沉淀为工具评估资产，例如：

```text
工具：某开源内容日历
部署方式：Coolify
接入等级：L2 数据级
优点：界面好、部署简单
缺点：无 MCP、API 弱
结论：适合作为人工使用工具，不适合作为 AI 自动工作流核心工具
```

## Q50. 工作流应该绑定具体工具，还是绑定能力需求？


> 工作流阶段 = 目标 + 输入 + 输出 + 所需能力；具体工具 = 能力实现方式。

## Q51. 如果有些工具没有 MCP 层适配怎么办？

**当前答案：** 不强行要求所有工具都有 MCP。系统应支持多级接入。

| 等级 | 接入方式 | AI 能否直接使用 | 示例 |
|---|---|---|---|
| L0 参考级 | 只记录链接、文档、仓库 | 不能 | 一个设计参考工具。 |
| L1 部署级 | 能通过 Docker/Coolify 部署 | 不能或很弱 | 自托管看板、CMS。 |
| L2 数据级 | 能导入/导出文件、CSV、JSON | 间接可用 | 导出运营数据表。 |
| L3 API/CLI 级 | 有 REST API、GraphQL、CLI、Webhook | 可通过适配器使用 | GitHub、Metabase、Strapi。 |
| L4 MCP 适配级 | 给它包一层 MCP Server | AI 可直接调用 | 自写 mcp-wrapper。 |
| L5 工作流级 | 已定义输入输出、阶段契约、质量检查 | 可稳定进入工作流 | GitHub Issue 分析节点。 |

**状态：** 已同步到 `核心想法.MD`。

## Q52. 非 MCP 工具有哪些处理方式？

**当前答案：**

| 工具条件 | 接入策略 |
|---|---|
| 已有 MCP Server | 直接作为 MCP 连接器接入。 |
| 有 API / CLI / Webhook | 先做普通 Adapter，必要时包装成 MCP。 |
| 支持文件导出 | 通过导入器转为真实资产。 |
| 有数据库 | 只读连接，抽取必要数据。 |
| 只能人工使用 | 作为旁路工具记录，不进入自动工作流。 |
| 价值不明确 | 先进入工具试用工作流，生成评估资产。 |

核心原则：

> 能 MCP 就 MCP；不能 MCP 就 API、CLI、Webhook、文件导入、数据库只读或人工旁路；只有输入输出和价值被验证后，才进入正式工作流。

**状态：** 已同步到 `核心想法.MD`。

## Q53. MCP 在开源工具接入中的真实位置是什么？

**当前答案：** MCP 是 AI 可调用能力的优先协议层，但不是工具接入的唯一形式。

```text
开源工具接入
  → 部署层：Docker / Coolify / Compose / 手动部署
  → 数据层：文件 / API / DB / Webhook / CLI
  → AI 调用层：MCP Tool / Resource
  → 工作流层：输入输出契约 + 质量检查 + 阶段适配
```

MCP 主要解决：

```text
AI 如何调用已经接入好的能力
```

但它不直接解决：

```text
工具是否适合业务
工具如何部署
工具如何试用
工具如何评估
工具如何产出资产
```

**状态：** 已同步到 `核心想法.MD`。

## Q54. 关于开源工具接入的当前总判断

当前较稳的设计方向：

```text
用户目标
  → AI 推荐能力需求
  → 能力市场给出候选工具/连接器/模板
  → Runtime Provider 部署或接入候选工具
  → 工具试用工作流验证适配度
  → 合格工具进入正式工作流
  → 产生真实资产和工具评估资产
  → 未来作为通用资产被复用
```

需要避免两个误区：

1. **把 MCP 当成唯一接入方式。**  
   很多工具没有 MCP，但仍可通过 API、CLI、导入、数据库或人工旁路使用。

2. **把能部署当成能进入工作流。**  
   Coolify/Docker 只能说明工具能跑起来，不说明它适合业务，也不说明 AI 能调用它。

**状态：** 已同步到 `核心想法.MD`，具体实现待后续细化。

| 层级 | 作用 | 示例 |
|---|---|---|
| 流程图卡片 | 看全局结构和状态 | 节点名称、状态、输入输出摘要、风险标记。 |
| 节点详情面板 | 看节点依据和追溯 | 目标、输入资产、输出资产、AI Trace、工具调用、版本历史。 |
| 节点工作区 | 执行具体工作 | 调研资料墙、AI 分析区、GitHub PR、测试报告、决策面板。 |

**关键结论：**

> 节点展示不是“一个页面展示所有事情”，而是“统一节点外壳 + 多类型工作区渲染器”。

**状态：** 已同步到 `核心想法.MD`，UI 原型待设计。

## Q56. 是否真的存在足够通用的节点定义方式？

**当前答案：** 存在，但只能通用到“协议层”和“外壳层”，不能通用到所有内部行为。

节点的通用定义应包含：

- 节点 ID、类型、标题；
- 节点目标；
- 输入资产；
- 输出资产；
- 可用工具 / MCP / API / 人工能力；
- 状态；
- 验收标准；
- 质量检查；
- 执行记录；
- 版本；
- 展示规格。

**核心判断：**

> 节点的通用性不来自“所有节点长得一样”，而来自“所有节点都遵守同一套输入、输出、状态、版本、证据和验收协议”。

**状态：** 已同步到 `核心想法.MD`，Node Schema 待设计。

## Q57. 节点内部行为如何实现？

**当前答案：** 节点内部行为应通过不同类型的 Renderer 和 Executor 实现。

```text
WorkflowNode = 通用协议
NodeRenderer = 展示方式
NodeExecutor = 执行方式
Asset = 输入输出
```

示例：

```text
research.competitor_analysis
  → CompetitorAnalysisRenderer
  → AIResearchExecutor

code.implementation
  → CodeTaskRenderer
  → Codex/GitHub Executor

review.decision
  → DecisionPanelRenderer
  → ReviewExecutor
```

**实现含义：** 系统核心只需要理解节点的目标、输入、输出、状态、版本、依赖和资产关系；具体怎么调研、编码、评审，则交给节点类型对应的渲染器和执行器。

**状态：** 方向成立，Registry / 插件化边界待设计。

## Q58. 第一版需要哪些节点类型？

**当前修正：** 此处原先把节点拆得过细，尤其是 Human Input Node、Asset Output Node 容易把“素材接收”“资产沉淀”等系统层行为误当成主工作流节点。当前不再建议按这 6 类原子节点作为核心分类。

更合理的是：MVP 应优先做“自主工作节点”，每个节点围绕一个明确目标形成工作空间，内部可以包含输入收集、AI 分析、工具调用、人工确认、资产更新和日志记录。

第一版可保留的不是“六类原子节点”，而是几种工作空间能力：

1. 材料/上下文区；
2. AI 分析与建议区；
3. 工具/MCP/GitHub 调用区；
4. 人工确认与决策区；
5. 输出资产与影响分析区；
6. 运行日志与 Trace 区。

**待确认：** MVP 应选哪 2-3 个高价值自主工作节点做完整交互，例如“根据老师反馈收束选题”“实现 GitHub Issue 同步能力”“评估 MCP Runtime 方案”。

**状态：** 已被后续讨论修正，最新结论见 Q87-Q92。

## Q59. 如何随时向工作流插入前置节点或修改节点？

**当前答案：** 不能让 AI 直接修改正式工作流，而应通过 Workflow ChangeSet。

流程：

```text
用户自然语言提出修改
  → AI 生成工作流变更提案
  → 系统分析影响范围
  → 用户/团队确认
  → 工作流图更新
  → 后续节点标记为需复核/可能过期
```

ChangeSet 应记录：

- 变更类型：插入、删除、拆分、合并、替换、重连；
- 变更位置；
- 变更原因；
- 影响哪些节点；
- 影响哪些资产；
- 是否需要重跑；
- 谁提出、谁确认；
- 最终处理结果。

**状态：** 已同步到 `核心想法.MD`，ChangeSet Schema 待设计。

## Q60. 新插入的信息如何影响后续节点？

**当前答案：** 靠依赖关系、资产版本和影响分析处理，而不是自动覆盖后续结果。

例如：

```text
任务拆解节点原本依赖：需求调研报告 v1
后来新增：竞品分析报告 v1
任务拆解节点改为依赖：需求调研报告 v1 + 竞品分析报告 v1
```

此时任务拆解节点可以被标记为：

- 已完成但可能过期；
- 需要复核；
- 建议重跑；
- 或维持原结果但记录原因。

**关键原则：**

> 前置信息变化后，系统负责提示影响和记录版本；是否重跑、接受或忽略影响，由用户或团队确认。

**状态：** 已同步到 `核心想法.MD`，影响分析算法待设计。

## Q61. 节点是否需要在线利用 Codex / Claude Code 编程的能力？

**当前答案：** 如果选择的具体场景包含代码实现、自动化脚本、开源项目维护、工具适配或 MCP Server 开发，那么编码节点是合理的。

但编码节点不应是普通聊天框，而应是上下文受控的 Code Task Node。

输入可以包括：

- 需求说明；
- 设计文档；
- 关联 Issue；
- 代码仓库；
- 约束条件；
- 测试要求。

输出可以包括：

- Branch；
- Commit；
- Pull Request；
- Diff；
- 测试结果；
- 实现说明；
- AI Trace；
- 待确认问题。

**待确认：** MVP 是直接接入 Codex 执行编码，还是先只做 GitHub Issue / PR / Commit 关联和编码任务记录。

**状态：** 已同步到 `核心想法.MD`，实现范围待定。

## Q62. 接入 GitHub 是否可行？Git 是否适合统一管理？

**当前答案：** 接入 GitHub 可行，而且与开源项目维护、独立开发者、AI 编程协作等场景高度契合。Git 适合管理代码、配置和文档快照，但不适合单独管理全部协作状态。

推荐分工：

```text
Git 管代码、文档快照、配置版本；
GitHub 管 Issue、PR、Review、Commit 等协作对象；
系统数据库管工作流状态、资产关系、节点状态、决策记录。
```

节点可以关联：

```text
工作流节点 → GitHub Issue
节点运行记录 → Commit
节点输出资产 → Pull Request / Test Report
节点评审 → PR Review / Decision Record
```

**关键判断：**

> Git 是强版本工具，但不是完整协作语义数据库。系统需要把 Git/GitHub 对象资产化，而不是把系统状态全部塞进 Git。

**状态：** 已同步到 `核心想法.MD`，GitHub 接入深度待定。

## Q63. 不同节点的版本号如何控制？

**当前答案：** 需要分层版本，而不是一个全局版本号。

| 版本层级 | 含义 |
|---|---|
| Workflow Version | 工作流整体结构版本。 |
| Node Definition Version | 节点定义版本，包括目标、输入、输出、验收标准。 |
| Node Run Version | 节点执行记录版本，即第几次运行。 |
| Asset Version | 节点产出的资产版本。 |
| Git Version | 代码层面的 commit、branch、tag、PR。 |

示例：

```text
Workflow v3
  └── Node: 竞品分析 v1
        └── Run #2
              └── Output: 竞品分析报告 v4
```

**状态：** 已同步到 `核心想法.MD`，版本模型待设计。

## Q64. 协作过程中如何同步思想？

**当前答案：** 不应只依赖聊天记录，而应将关键思想同步为结构化协作资产。

包括：

- 观点卡片；
- 争议记录；
- 决策记录；
- 方案对比；
- 工作流变更提案；
- 复盘记录。

例如：

```text
争议：是否在任务拆解前加入竞品分析？
观点 A：需要，否则任务拆解缺少外部参照。
观点 B：不需要，会增加毕设复杂度。
AI 分析：加入后文档质量提升，但实现成本增加。
最终决策：本项目加入，但不作为所有模板的必选节点。
```

## Q65. 如何确定某个改动是否应该加入工作流？

**当前答案：** 可以采用类似 Pull Request 的工作流变更机制，但对象不只是代码，也包括工作流、节点和资产。

流程：

```text
提出变更
  → AI 影响分析
  → 人类讨论
  → 决策
  → 合并 / 拒绝 / 暂存 / 作为可选分支保留
```

可选处理结果：

- 接受并合入当前工作流；
- 拒绝并记录原因；
- 暂存，后续再评估；
- 作为可选节点保留；
- 仅本项目使用；
- 抽象为通用模板；
- 形成分支方案继续比较。

**状态：** 已同步到 `核心想法.MD`，权限和审批机制待简化。

## Q66. 如果有人认为改动不好，但另一个人认为可以，如何处理？

**当前答案：** 不应强迫所有分歧立即消失。可以记录争议，并在必要时允许工作流分支。

示例：

```text
Workflow Branch A：轻量 MVP 路线
Workflow Branch B：完整资产图谱路线
```

对比分支时可以使用：

| 指标 | 说明 |
|---|---|
| 实现难度 | 是否超出毕设周期。 |
| 展示效果 | 是否有利于答辩呈现。 |
| 风险 | 是否存在技术和范围风险。 |
| 时间可控性 | 是否能按期完成。 |
| 创新性 | 是否体现系统价值。 |
| 与场景贴合度 | 是否服务具体业务闭环。 |

**关键判断：**

> 分歧不是必须立刻消除的错误状态，而是需要被记录、比较、决策和复盘的协作资产。

**状态：** 已同步到 `核心想法.MD`，分支机制是否进入 MVP 待定。

## Q67. 关于动态节点与工作流演化的当前总判断

当前较稳的设计方向是：

```text
工作流 = 动态有向图，不是静态流程图；
节点 = 工作单元，不是固定页面；
节点通用性 = 协议统一，而不是 UI 完全一致；
节点展示 = 流程图卡片 + 详情面板 + 类型化工作区；
节点执行 = Renderer + Executor + Asset I/O；
修改工作流 = ChangeSet + 影响分析 + 人类确认；
前置信息变化 = 标记后续节点需复核，而不是自动推翻；
编码任务 = 可作为 Code Task Node 接入 Git/GitHub/Codex；
协作争议 = 观点、争议、决策和分支资产化。
```

下一步需要细化：

1. WorkflowNode Schema；
2. NodeRun Schema；
3. WorkflowChangeSet Schema；
4. NodeRenderer / NodeExecutor Registry；
5. 节点状态机；
6. 影响分析规则；
7. Code Task Node 的 MVP 范围；
8. GitHub 对象如何资产化；
9. 工作流分支和争议决策如何做到毕设可实现。

## Q72. LangGraph / Temporal / Dagster 等是否应该直接作为技术底座？

**当前答案：** 暂不建议把某一个框架作为唯一技术底座。

## Q74. 前置信息变化后的影响分析 MVP 如何实现？

**当前答案：** MVP 可以先做规则型影响分析，不必一开始做复杂图算法。

基本规则：

1. 如果资产 A 更新，所有直接引用 A 的节点标记为 `needs_review`。
2. 如果节点 N 的输出资产变化，依赖这些输出资产的下游节点标记为 `stale`。
3. 用户可以确认“该变化不影响后续节点”，系统记录 DecisionRecord 并停止继续传播。
4. 如果变化影响需求、范围、接口、测试标准等高风险资产，则后续编码/评审节点强制复核。

**待确认：** 影响分析结果是否只做提示，还是允许系统自动生成重跑建议队列。

**状态：** 部分同步到 `核心想法.MD`，算法待设计。

## Q75. GitHub PR / Git / CRDT 对协作机制有什么启发？

**当前答案：** GitHub PR 是工作流变更提案的强参考，但 Git/CRDT 不应被过度引入。

当前建议：

```text
工作流变更提案 ≈ Pull Request
节点/资产修改 ≈ diff
团队讨论 ≈ review comments
最终确认 ≈ merge / close / defer
```

# N. 新增问题：开放节点插件机制与自托管小团队定位纠偏

> 记录时间：2026-07-07  
> 来源：关于“用户是否应该拥有定义节点的权力，以及当前方案是否偏向普通用户/公共 SaaS 平台限制思路”的讨论。  
> 记录目的：纠正此前过于保守的节点治理假设，将系统定位重新对齐到开源、自托管、小团队、用户可自实现节点的方向。

## Q79. 用户是否应该拥有完整自实现节点的权力？

**当前答案：** 应该。

在开源、自托管、小团队使用场景下，系统不应像公共 SaaS 一样严格限制用户自定义节点。用户/开发者应该可以自己实现：

- 节点定义；
- 节点执行逻辑；
- 节点配置面板；
- 节点展示组件；
- 节点输入输出 Schema；
- 节点调用 MCP / API / CLI / 本地脚本；
- 节点产出的资产类型。

更准确的原则是：

> 节点能力开放，节点接入标准化。

也就是：

> 用户决定节点能做什么，系统保证节点做过什么可追溯。

**状态：** 已同步到 `核心想法.MD`。

---

## Q80. 既然节点完全开放，系统还需要固定什么？

**当前答案：** 系统不应固定节点内部逻辑，但必须固定节点接入协议。

系统核心只要求节点能够：

- 被注册；
- 被启用/禁用；
- 声明基本信息；
- 声明权限和依赖；
- 声明输入输出；
- 返回运行状态；
- 记录运行日志；
- 将输出接入资产系统；
- 标记版本和来源。

这不是限制节点能力，而是保证节点能进入工作流、资产图谱和追溯体系。

推荐口号：

```text
节点内部自由实现；
节点接入统一协议；
节点运行全程可追溯。
```

**状态：** 已同步到 `核心想法.MD`，manifest / runtime 设计待细化。

## Q83. 透明节点和黑盒节点如何区分？

**当前答案：** 开放系统不应该禁止黑盒节点，但系统应区分语义完整度。

| 类型 | 特征 | 系统能力 |
|---|---|---|
| 透明节点 | 声明输入、输出、资产类型、权限、验收标准、质量检查。 | 可做影响分析、资产图谱、复用推荐、质量检查。 |
| 黑盒节点 | 只声明最小运行信息，内部逻辑由用户自定。 | 可运行、记录日志、记录输入输出文件和状态，但语义理解较弱。 |

关键原则：

> 声明越完整，系统越能追溯、推荐和复用；声明越少，节点越接近普通脚本。

# O. 新增问题：节点过度拆分纠偏、自主工作空间与编码节点交互

> 记录时间：2026-07-07  
> 来源：关于“资产沉淀是否适合作为节点、工作流变更节点是否合理、素材接收节点是否多余、编码节点如何交互、每个节点是否应有足够自主性”的讨论。  
> 记录目的：纠正此前将工作流拆成过多原子节点的倾向，明确资产、ChangeSet、Inbox、Trace 的系统层定位。

## Q87. 资产沉淀真的适合作为节点吗？

**当前答案：** 大多数情况下不适合。

更准确的关系是：

```text
资产是高于节点的项目记忆层；
节点消费、产生、更新资产；
资产图谱记录节点之间通过资产形成的关系。
```

所以“保存资产”“关联资产”“更新资产图谱”通常不应作为主工作流节点，而应是节点完成后的系统行为。

只有当“资产化/复盘/模板抽象”本身是明确工作目标时，才适合作为节点。例如：

```text
适合作为节点：将本次 GitHub 集成过程沉淀为可复用插件开发模板
不适合作为节点：保存某个资产到资产库
```

**状态：** 已同步到 `核心想法.MD`。

---

## Q88. 工作流变更节点是否合理？

**当前答案：** 通常不合理。

Workflow ChangeSet 更像：

```text
工作流控制层操作
版本历史
图结构变更记录
影响分析结果
```

它不应默认作为业务工作流上的普通节点。

更合理的是：某个自主工作节点内部可能提出 ChangeSet。例如：

```text
节点：根据老师反馈重构毕设选题范围
  → 内部产出 ChangeSet：新增“具体业务场景选择”，标记原“通用平台范围设计”过期
```

因此：

```text
根据老师反馈重构毕设选题范围 ✅ 可以是节点
生成一个 Workflow ChangeSet ❌ 通常不是节点
```

**状态：** 已同步到 `核心想法.MD`。

---

## Q89. 素材接收节点是不是多余？

**当前答案：** 如果只是上传文件、贴链接、导入截图，那确实不应作为节点。

素材接收应属于：

```text
Inbox 输入收集层
节点输入区
资产收集区
拖拽上传 / 链接收藏 / 文件导入
```

只有当“资料整理”本身有明确目标和产出时，才适合作为节点。例如：

```text
适合作为节点：整理老师反馈并提取影响选题范围的关键信息
不适合作为节点：上传老师聊天截图
```

**状态：** 已同步到 `核心想法.MD`。

---

## Q90. 什么东西才配叫工作流节点？

**当前答案：** 一个东西只有满足以下条件，才适合作为主工作流节点：

1. 有明确目标；
2. 有相对独立的完成边界；
3. 有用户真正关心的产出；
4. 有验收标准；
5. 可以独立推进一段工作；
6. 过程中可以包含多个内部动作；
7. 完成后会影响后续工作。

因此，节点更准确的定义是：

> 节点 = 围绕一个目标运行的自主工作空间。

节点内部可以包含素材导入、AI 分析、工具调用、人工确认、代码执行、测试、资产更新、ChangeSet 提案和 Trace 记录，但这些内部动作不应都拆成主工作流节点。

**状态：** 已同步到 `核心想法.MD`。

## Q91. 编码任务节点到底应该怎么交互？

**当前答案：** 编码节点不应是“开个聊天框让 Codex 写代码”，而应是一个实现工作空间。

例如：

```text
节点：实现 GitHub Issue 同步能力
```

页面可以分为：

```text
左侧：上下文
  - 需求说明
  - 关联资产
  - 接口约束
  - 相关 Issue
  - 验收标准

中间：执行区
  - AI 生成实现计划
  - 用户确认/修改计划
  - 创建 branch
  - 调用 Codex / 本地命令 / GitHub API
  - 运行测试

右侧：结果区
  - 文件 diff
  - commit
  - PR
  - 测试结果
  - 遗留问题
  - 人工 Review
```

交互流程：

```text
用户进入节点
  → 系统展示需求、上下文和验收标准
  → AI 生成实现计划
  → 用户确认或修改计划
  → 系统创建 branch / issue
  → Codex 或本地执行器完成代码修改
  → 系统展示 diff 和测试结果
  → 用户选择接受、要求修改、放弃或创建 PR
  → 节点输出代码资产、实现记录、测试报告和遗留问题
```

**状态：** 已同步到 `核心想法.MD`，UI 原型待设计。

## Q92. 如何验证编码节点交互效果？

**当前答案：** 不能只验证“代码是否写出来”，还要验证节点是否改善 AI 编码协作体验。

可验证维度：

| 维度 | 验证方式 |
|---|---|
| 用户是否理解当前任务 | 用户能否从节点中说清楚要实现什么。 |
| 用户是否理解 AI 做了什么 | 是否能找到实现计划、diff、测试结果和日志。 |
| 用户是否能控制过程 | 是否能修改计划、拒绝结果、要求重跑。 |
| 代码结果是否可验证 | 是否有关联 commit、PR、测试报告。 |
| 过程是否可追溯 | 是否能追溯输入需求、AI 操作、代码变更。 |
| 是否减少上下文切换 | 是否减少在聊天、IDE、GitHub、文档之间来回切换。 |
| 是否支持复盘 | 完成后能否生成实现经验卡或问题记录。 |

可以做一个毕设小实验：

```text
任务：实现一个 GitHub Issue 同步功能
方式 A：直接使用 Codex + GitHub + 文档
方式 B：通过系统编码节点完成
比较：完成时间、过程理解、记录完整性、Review 便利性、复盘资产生成情况
```

**状态：** 待后续转化为测试计划。

## Q93. 这次纠偏后的总模型是什么？

**当前答案：**

```text
工作流 = 若干自主工作节点组成的路线
节点 = 围绕一个目标的自主工作空间
资产 = 高于节点的项目记忆层
ChangeSet = 工作流控制层操作
Inbox = 输入收集层
Trace = 过程记录层
```

```text

  → 资产进入项目记忆和资产图谱
  → 必要时节点提出 ChangeSet
  → 用户确认后工作流结构更新
```

核心原则：

> 工作流图不要拆太碎；节点内部可以很丰富。

# P. 新增问题：分层工作空间、上下文传递与可替换 AI Runner

> 记录时间：2026-07-07  
> 来源：关于“节点前端展现、工作空间内部是否需要继续划分、子工作空间如何协作、不同工作空间上下文如何交互、是否可内置 Codex 以及未来替换为 Claude Code/其他 CLI 是否可行”的讨论。  
> 记录目的：将当前模型从单纯节点系统推进为“分层工作空间系统 + 可替换 AI 协作内核”。

## Q94. 节点在前端是否应该直接等于一个完整页面？

**当前答案：** 不应该简单等同。

更合理的是：

```text
工作流节点 = 外部可见的目标单元
节点工作空间 = 节点内部的协作环境
子工作空间 = 节点内部为完成目标拆出的局部任务空间
Work Thread = 最小协作单位
```

推荐层级：

```text
Project Workspace
  └── Workflow
        └── Node Workspace
              └── Sub Workspace
                    └── Work Thread
```

**状态：** 已同步到 `核心想法.MD`。

---

## Q95. 工作空间的最小单位应该是什么？

**当前答案：** 建议定义为 `Work Thread / 工作线程`。

Work Thread 是围绕一个小目标的一次人机协作记录，包含：

- 小目标；
- 输入上下文；
- 参与者：人 / AI / 工具；
- 过程记录；
- 产出；
- 状态；
- 关联资产。

Work Thread 可以被聚合为 Sub Workspace；如果某个子工作空间足够重要，也可以提升为主工作流节点。

**状态：** 已同步到 `核心想法.MD`，具体 Schema 待设计。

---

## Q96. 工作空间内部多个子工作空间如何协作？

**当前答案：** 子工作空间之间不应直接共享全部上下文，而应通过资产、摘要、决策和事件通信。

不建议：

```text
A 的全部聊天记录 → B
B 的全部 Trace → C
```

更建议：

```text
子工作空间 A
  → 输出 Workspace Digest / 资产 / 决策 / 证据引用
  → 子工作空间 B 按需读取
```

核心原则：

> 默认摘要通信，必要时逐层展开原始记录。

**状态：** 已同步到 `核心想法.MD`。

---

## Q97. 子工作空间呈现给父工作空间的内容应该是什么？

**当前答案：** 应该是 `Workspace Digest / 工作空间摘要包`，而不是全量过程记录。

建议字段：

```yaml
workspace_id: string
goal: string
status: draft | running | blocked | completed | needs_review
current_conclusion: string[]
output_assets: AssetRef[]
confidence: low | medium | high
blockers: string[]
next_actions: string[]
evidence_refs: AssetRef[]
raw_trace_ref: TraceRef[]
```

父工作空间默认看 Digest；需要时再展开资产、证据、过程记录和原始 Trace。

**状态：** 已同步到 `核心想法.MD`，字段待细化。

---

## Q98. 父工作空间是否有权进一步获取子工作空间内容？

**当前答案：** 应该有，但不应默认加载全部内容。

推荐展开层级：

| 层级 | 内容 |
|---|---|
| L0 | 子工作空间状态和一句话结论。 |
| L1 | Workspace Digest。 |
| L2 | 输出资产和证据。 |
| L3 | 关键过程记录。 |
| L4 | 原始 Trace / 对话 / 工具调用。 |

这样既能让父空间掌控全局，又不会造成上下文爆炸。

**状态：** 已同步到 `核心想法.MD`。

---

## Q99. 是否应该直接内置 Codex 作为 AI 协作核心？

**当前答案：** Codex 可以作为第一版强力 AI Runner，但不能成为系统的上下文主权中心。

正确原则：

> 系统拥有上下文，AI Runner 消费上下文。

系统应自己管理：

- 项目上下文；
- 工作空间结构；
- 资产；
- 决策；
- Trace；
- Workspace Digest；
- Context Pack。

Codex / Claude Code / 其他 CLI 应只是：

- AI Runner；
- Code Executor；
- Analysis Worker；
- Tool-using Agent。

**状态：** 已同步到 `核心想法.MD`。

## Q100. 不同工作空间的上下文如何交给 AI？

**当前答案：** 通过系统构建的 `Context Pack`。

Context Pack 应包含：

- workspace_id；
- goal；
- role；
- background；
- inputs；
- constraints；
- acceptance_criteria；
- available_tools；
- expected_outputs；
- relevant_assets；
- parent_digest；
- sibling_digest；
- trace_refs。

这样 Codex、Claude Code 或其他 CLI 都可以消费同一种上下文包。

**状态：** 已同步到 `核心想法.MD`，Schema 待设计。

## Q101. AI 协作核心可拆分、可替换真的可行吗？

**当前答案：** 可行，但不是无成本“无缝替换”。前提是系统自己定义 `AI Runner Adapter`，并把上下文、资产、Trace 和工作空间状态保存在系统侧。

推荐结构：

```text
Workspace System
  ├── Context Store
  ├── Asset Graph
  ├── Trace Store
  ├── Workspace Digest
  ├── Context Pack Builder
  └── AI Runner Adapter
        ├── Codex Runner
        ├── Claude Code Runner
        ├── Local LLM Runner
        └── Other CLI Runner
```

更换 Runner 时，目标是：

```text
业务模型不变
工作空间不变
资产不变
上下文包不变
只替换 Runner Adapter
```

**状态：** 已同步到 `核心想法.MD`，Adapter 接口待设计。

## Q102. AI Runner Adapter 最小接口应该考虑什么？

**当前答案：** 至少需要处理：

- Runner 名称；
- 能力声明；
- 启动会话；
- 运行指令；
- 取消任务；
- 返回结果；
- 标准化输出；
- 记录 Trace。

概念接口：

```ts
interface AgentRunner {
  name: string
  capabilities(): AgentCapability[]
  startSession(input: {
    workspaceId: string
    contextPack: ContextPack
    tools: ToolPermission[]
  }): Promise<SessionRef>
  run(input: {
    sessionId: string
    instruction: string
    expectedOutputs: OutputSpec[]
  }): Promise<AgentRunResult>
  cancel(sessionId: string): Promise<void>
}
```

**状态：** 待细化为系统设计。

## Q103. 不同 AI Runner 能力不同怎么办？

**当前答案：** 需要能力协商，而不是假设 Codex、Claude Code、普通 LLM 完全等价。

能力维度可以包括：

| 能力 | 说明 |
|---|---|
| code_edit | 能否修改代码文件。 |
| shell_exec | 能否执行命令。 |
| git_ops | 能否创建分支、提交、读取 diff。 |
| mcp_tools | 能否调用 MCP 工具。 |
| long_context | 是否支持长上下文。 |
| session_memory | 是否支持会话记忆。 |
| result_schema | 是否能稳定输出结构化结果。 |

系统根据任务需求选择合适 Runner。

**状态：** 待设计能力协商机制。

## Q104. 良好的节点工作空间前端应该长什么样？

**当前答案：** 默认应展示目标、结论、下一步和风险，细节按需展开。

建议结构：

```text
顶部：目标栏
  - 当前节点目标
  - 状态
  - 下一步建议
  - 风险提示

左侧：上下文栏
  - 输入资产
  - 父工作空间给的上下文
  - 相关决策
  - 相关工具

中间：工作区
  - 当前活跃 Work Thread
  - AI 计划
  - 人类确认
  - 工具执行

右侧：产出栏
  - 当前结论
  - 输出资产
  - 待确认问题
  - 对后续影响

底部/折叠：Trace
  - AI 调用
  - MCP 调用
  - Git 操作
  - 原始日志
```

**状态：** 待后续做 UI 原型。

## Q105. 这次讨论后的总判断是什么？

**当前答案：** 当前系统应从“工作流节点系统”进一步升级为：

> 分层工作空间系统 + 可替换 AI 协作内核。

核心模型：

```text
Project Workspace
  └── Workflow
        └── Node Workspace
              └── Sub Workspace
                    └── Work Thread
```

上下文模型：

```text
Context Store：系统长期记忆
Workspace Digest：工作空间对外摘要
Context Pack：喂给 AI Runner 的上下文包
Trace：原始过程记录
Asset Graph：稳定资产关系
```

AI 模型：

```text
AI Collaboration Core
  = Context Pack Builder
  + AI Runner Adapter
  + Tool/MCP Bridge
  + Result Normalizer
  + Trace Recorder
```

一句话：

> Codex 可以作为第一个强力 Runner，但不能成为系统的上下文主权中心。

## Q106. 现有工具是否能直接作为系统底座？

**当前答案：** 暂不建议。现有项目分别覆盖了一部分能力，但都不能完整等价于当前设想。

| 候选 | 不足 |
|---|---|

## Q107. Context Pack 的质量到底如何评价？

**当前答案：** 现有工具证明 Context Pack/Repo Map/Context Provider 有必要，但很少直接回答“上下文包是否足够好”。

可考虑的评价指标：

1. 是否包含任务目标；
2. 是否包含已确认事实；
3. 是否区分假设与事实；
4. 是否包含必要约束；
5. 是否包含验收标准；
6. 是否包含相关资产和证据引用；
7. 是否排除过期/争议信息；
8. 是否说明可用工具与权限；
9. 是否让 Runner 少问重复问题；
10. 是否能产生符合预期的结构化结果。

**状态：** 待设计 Context Pack 评分/自检机制。

## Q108. 资产从 Trace 中自动抽取到什么程度？

**当前答案：** 不能完全自动，也不能完全手动。

可能方案：

```text
AI 生成资产候选
  → 系统标记来源 Trace / 证据 / 输入材料
  → 用户确认或驳回
  → 确认后进入 Asset Graph
```

风险：

- 自动抽取过多会污染资产库；
- 手动确认过多会增加负担；
- 错误资产会污染下游 Context Pack；
- 资产如果没有证据引用，后续很难复盘。

**状态：** MVP 先做“候选资产 + 用户确认 + 证据引用”。

## Q109. 工作流推荐如何保持一致性？

**当前答案：** 不能只依赖 AI 随机生成，需要模板、约束、评分和版本。

可行机制：

```text
用户目标 / 角色 / 已有工具 / 项目类型
  → 匹配工作流模板库
  → AI 在模板约束下生成候选方案
  → 系统用规则评分
  → 给出 2-3 个可选方案和理由
  → 用户确认后保存 workflow_version
```

一致性来源：

- 固定 Prompt；
- 模板库；
- 输出 JSON Schema；
- 工具能力目录；
- 评分规则；
- 版本记录；
- 用户确认。

**状态：** 待设计 workflow recommendation schema。

## Q110. 用户自定义节点如何兼顾自由度和学习成本？

**当前答案：** 开源自托管场景下，不应限制用户自实现节点；但需要分层入口。

分层方式：

```text
普通用户：选择已有节点 + 配置参数。
进阶用户：复制节点模板并修改 manifest / schema。
高级用户：实现 executor / renderer / context provider。
开发者：发布完整能力包。
```

关键不是限制能力，而是提供：

- 节点模板；
- manifest 示例；
- 输入输出 schema；
- 权限声明；
- 本地调试工具；
- 预览与回滚；

- 示例项目。

## Q113. 如何处理事实变化导致的资产过期？

**当前答案：** 需要资产状态和影响分析。

资产状态至少包括：



## Q115. 多 Runner 替换是否真的能无缝？

**当前答案：** 架构上可以降低耦合，但实际不会完全无缝。

差异来源：

- 是否能编辑代码；
- 是否能执行 shell；
- 是否支持 MCP；
- 是否支持长会话；
- 是否支持结构化输出；
- 是否能导出工具日志；
- 是否能恢复 session；
- 权限模型不同；
- 输出格式不同。

系统应支持降级：

```text
强 Runner：代码修改 + 工具调用 + 测试。
中 Runner：分析 + 结构化建议。
弱 Runner：只读总结 / 规划。
MockRunner：测试系统流程。
```

**状态：** 待设计 capability negotiation 与 fallback strategy。

## Q116. 多模态交互式资产到底以什么方式落地？

**当前答案：** 不应只在“新部署一个网站”和“AI 直接改前端”之间二选一。

更合理的候选：

1. 内置视图：表格、图谱、时间线、看板、Markdown；
2. 声明式 ViewSpec：用 JSON/YAML 描述展示结构；
3. 插件 Renderer：项目本地提供 React/Vue/Svelte 等渲染组件；
4. 外部应用链接：Streamlit/Gradio/Observable/Jupyter 等独立服务；
5. 部署型资产：通过 Deployment Recipe 启动一个本地 Demo；
6. AI 生成展示草稿：先预览，确认后作为候选 Renderer 或 ViewSpec。

**状态：** MVP 先实现内置视图 + 简单 ViewSpec + 外部链接；Renderer 插件可作为进阶功能。

# R. Codex Memory 与系统记忆边界相关问题

> 来源：关于“Codex 本身的记忆能力在系统中如何利用，以及是否需要从 0 开发完整 Agent”的讨论。

## Q117. Codex Memory 和系统记忆冲突时以谁为准？

**当前答案：** 以系统侧确认资产、DecisionRecord、Workspace Digest 和最新 Context Pack 为准。

Codex Memory 只能作为执行辅助，不能覆盖系统权威数据。

冲突处理流程：

```text
Codex Memory / Session 中的判断
  与系统 Asset / Digest / Decision 冲突
    → 标记 conflict
    → 要求 Codex 读取最新 Context Pack
    → 需要时生成待确认问题
    → 用户确认后更新系统资产或决策
```

**状态：** 原则已确认，具体冲突检测机制待设计。

## Q118. 哪些内容应该写入 AGENTS.md，哪些应该进入 Context Pack？

**当前答案：** AGENTS.md 放稳定规则，Context Pack 放当前任务上下文。

| 内容 | 放置位置 |
|---|---|
| 项目定位 | AGENTS.md |
| 编码/协作硬规则 | AGENTS.md |
| Runner 输出格式要求 | AGENTS.md / output schema |
| 当前节点目标 | Context Pack |
| 当前输入资产 | Context Pack |
| 当前验收标准 | Context Pack |
| 当前工具权限 | Context Pack |
| 最新 Digest | Context Pack / `.ai-workspace/workspace-digest.md` |
| 临时假设 | Context Pack，并标记 hypotheses |

**状态：** 待设计 AGENTS.md 生成模板和 Context Pack 引用规范。

## Q119. Codex Session 应绑定到哪个粒度？

**当前答案：** 倾向绑定到 `Work Thread` 或 `Node Workspace`，而不是整个 Project Workspace。

原因：

- Project 级别 session 太大，容易污染上下文；
- Node Workspace 级别适合围绕一个目标连续推进；
- Work Thread 级别更细，适合具体实现、调研或修复任务；
- 父空间应通过 Digest / Asset 获取子空间结果，而不是直接继承所有 session 历史。

候选策略：

```text
默认：Node Workspace 一个主 Codex Session。
复杂节点：每个 Work Thread 一个 Codex Session。
父空间：不直接复用子 session，只读取 Digest / Asset / Evidence。
```

**状态：** 待结合实际 Codex resume / session 管理能力验证。

## Q120. 如何避免过度依赖 Codex？

**当前答案：** Codex 作为首个强 Runner，但系统接口必须面向 Runner Adapter，而不是面向 Codex 私有能力。

需要避免：

```text

资产格式依赖 Codex 输出习惯；

Context Pack 只能被 Codex 理解。
```

替代方案：

```text
Context Pack 使用系统定义 schema；
Runner 输出使用 return_schema；
TraceEvent 使用系统事件模型；
Asset 使用系统资产模型；
CodexRunner 只是 AgentRunner 的一个实现。
```

**状态：** 已纳入核心原则，Adapter 具体实现待设计。

## Q137. 用户是否应该只能在节点执行时调用 Codex？

**当前答案：** 不应该。Codex 不只应作为“执行 / 编码节点”的 Runner，也应作为用户在系统各处随时可调用的协作助手。

```text
项目目标怎么写；
背景信息还缺什么；
工作流该怎么选；
节点参数怎么填；
验收标准怎么定义；
```

因此，系统应支持：

```text

```

关键原则：

> Codex 不只是执行器，也是结构化协作助手；但它生成的内容默认是草稿，必须经用户确认后才进入系统事实。

## Q138. 当用户信息没有填全或自己也没想清楚时，Codex 应该直接补全吗？

推荐逻辑：

```text

  → 用户确认 / 修改

  → 标记假设
  → 给出 2-4 个选项
  → 说明每个选项的影响
```


- 用户选择了什么；

## Q141. Assist 与正式 NodeRun 的关系是什么？

**当前答案：** Assist 是轻量协作调用，NodeRun 是正式节点执行调用。二者都可以使用 CodexRunner，但上下文、结果和落库目标不同。

| 项 | Assist 调用 | NodeRun 调用 |
|---|---|---|
| 目标 | 帮用户填写、选择、澄清、生成草稿 | 推进节点工作并产出正式结果 |
| 上下文 | Assist Context Pack，聚焦当前页面 / 字段 | Node Context Pack，聚焦节点目标和验收标准 |
| 输出 | 建议、追问、选项、草稿 | NodeRunResult、文件变化、资产候选、测试结果 |
| 状态写入 | 用户确认后写入目标对象 | NodeRun 完成后进入 Trace/Asset/Digest/Git 闭环 |
| 资产化 | 默认不资产化 | 常产生 AssetCandidate |
| Trace | Assist Trace | NodeRun Trace |

核心原则：

> Assist 降低用户表达和决策成本；NodeRun 推进正式任务执行。两者都可调用 Codex，但系统必须区分它们的语义。

**状态：** 待在数据模型和 API 中明确 AssistSession 或复用 TraceEvent 的实现方式。

## Q143. 系统记忆的权威层级应该如何排序？

**当前答案：** 需要明确权威优先级，避免 Codex Memory、旧 Session、Digest、资产之间互相覆盖。

推荐顺序：

```text
当前用户显式输入
  > 当前 Node Contract / 当前任务指令
  > 用户确认的 DecisionRecord / Confirmed Asset
  > Workspace Digest
  > AGENTS.md / Project Rules
  > Trace Summary
  > Raw Trace / 原始材料
  > Codex Memory / Codex Session
  > AI 推测 / 草稿
```

含义：

- Codex Memory 不能覆盖系统确认资产；
- Digest 是摘要，不是最终事实源；
- Asset / Decision 必须可追溯证据；
- AI 草稿必须标记假设；
- 用户本轮确认永远优先。

**状态：** 已确认，应写入 Memory Policy。

## Q144. Codex 自身记忆应该怎么利用？

**当前答案：** Codex 自身记忆适合保存偏好、习惯和稳定规则，但不能作为系统事实源。

适合 Codex 记住：

```text
用户喜欢先分析再执行；
信息不足时先追问并给选项；
本项目 MCP-first 但不是 MCP-only；
节点是自主工作空间；
资产高于节点；
输出需要 changed_files / test_results / open_questions。
```

不适合只放在 Codex 记忆：

```text
项目事实；
资产内容；
用户确认决策；
节点状态；
验收标准；
Git commit / PR；
工具权限；
Trace 和证据。
```

V1 策略：

```text
Codex Memory 自然辅助；
AGENTS.md 放稳定项目规则；
Context Pack 放当前任务权威上下文；
Asset / Decision / Digest / Trace 放系统权威记忆。
```

如果需要同步长期偏好，系统先生成 RunnerMemoryCandidate，由用户确认后写入 AGENTS.md 或项目规则资产；不依赖自动写入 Codex 原生 Memory。

**状态：** 已确认，V1 不把 Codex Memory 当数据库。

## Q145. 什么是 Context Sufficiency Gate？

**当前答案：** 这是每次 Assist 或 NodeRun 前的上下文充分性检查。

检查项：

```text
是否有明确目标；
是否有当前字段 / 节点契约；
是否有必要输入；
是否包含相关资产和决策；
是否包含最新 Digest；
是否包含项目规则和用户偏好；
是否包含工具权限；
是否标记 stale / disputed / hypothesis；
是否有证据引用；
是否存在冲突；
是否超出上下文预算；
缺失信息是否已转成问题或选项。
```

输出状态：

```text
sufficient：可以调用 Codex 补全或执行；
needs_user_input：需要追问或给选项；
insufficient：缺少关键材料，不能继续；
conflict：存在冲突记忆，需要用户确认。
```

**状态：** 待实现为 ContextPackModule / AssistModule 的必经步骤。

## Q146. Memory Manifest 有什么作用？

**当前答案：** 它用于解释“这次 Codex 为什么知道这些”。

每个 Context Pack / Assist Context Pack 应记录：

```text
included memory：本次纳入了哪些资产、决策、Digest、规则、Trace 摘要；
include reason：为什么纳入；
authority：用户确认、系统确认、AI 草稿、导入内容、Codex memory hint；
freshness：current / stale / disputed / superseded；
excluded memory：哪些材料被排除以及原因；
warnings：冲突、过期、证据不足。
```

价值：

- 用户能检查上下文是否合理；
- 系统能复盘 AI 补全为什么这样；
- 下次生成 Context Pack 时可以复用或修正选择策略；
- 防止 Codex 基于旧记忆或错误记忆补全。

**状态：** 应进入 `context_packs.content_json.memory_manifest` 和 `context_sufficiency_checks`。

## Q147. 系统记忆如何持续更新？

**当前答案：** 记忆应通过“Trace → Draft/Candidate → Human Review → Confirmed Memory → Digest → 下一次 Context Pack”闭环更新。

流程：

```text
用户输入 / Codex Assist / NodeRun
  → Trace 记录过程
  → 生成 Draft / AssetCandidate / DecisionCandidate
  → 用户确认
  → 写入 Confirmed Asset / Decision / NodeContract / Digest
  → 更新 Memory Index / Workspace Digest
  → 下一次 Context Pack 引用最新记忆
```

特别注意：

- 草稿不是事实；
- Digest 不是唯一事实源；
- Codex Memory 不是事实源；
- 已确认资产和决策必须可追溯；
- 过期或冲突记忆必须显式标记。

**状态：** 已确认，应同步到开发计划和测试计划。

## Q150. GitHub 绑定第一版用 OAuth 还是 PAT？

**当前答案：** 推荐分层：OAuth Web Flow 作为产品化方向，fine-grained PAT / env ref 作为本地原型 fallback。

理由：

```text
OAuth Web Flow 用户体验更像正式产品；
但本地自托管原型需要配置 client_id / client_secret，成本较高；
fine-grained PAT / env ref 更适合 V1 快速验证；
GitHub App 更适合后续组织级安装和更细权限控制。
```

V1 可支持：

```text
方式 A：配置 GITHUB_OAUTH_CLIENT_ID / SECRET 后走 OAuth；
方式 B：用户填写 env:GITHUB_TOKEN 或本地加密 token，系统 GET /user 验证身份；
方式 C：未绑定，降级为本地 commit + PR 草稿。
```

**状态：** 待在 GitHubIntegrationModule 中实现至少 B + C，A 可作为增强。

## Q151. GitHub token / secret 应该如何保存？

```text
可以记录 scopes、expires_at、last_verified_at、status。
```
