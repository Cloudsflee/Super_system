# V3-Clean Schema Contract

Status: normative clean-baseline design.
Schema family: v3-clean.
Baseline: 001 (PRAGMA user_version = 1).
Storage: SQLite WAL with a separate content-addressed store (CAS).

This schema is a replacement, not a continuation of the V1-V6 migration
chain. Historical collection names in the capability matrix are source
evidence. They are mapped by the importer to the canonical tables below.

## 1. Common record rules

All identifiers are opaque UTF-8 text generated by the clean runtime. A source
identifier is retained in import_id_map; it is never used as a foreign key
unless it was accepted as the canonical id. Every mutable aggregate row has:

| Column | Rule |
| --- | --- |
| id | immutable primary key, unique within its table |
| revision | positive integer, incremented by one for every accepted mutation |
| created_at | UTC RFC 3339 timestamp, immutable |
| updated_at | UTC RFC 3339 timestamp, changed with revision |
| created_by_actor_id | actor that created the row, nullable only for system bootstrap |
| updated_by_actor_id | actor that committed the latest mutation |
| deleted_at | nullable tombstone timestamp; physical deletes are limited to purge jobs |

Canonical JSON fields are stored as UTF-8 JSON text with a deterministic key
order. A companion *_sha256 is the SHA-256 of that canonical value. JSON
numbers, timestamps, and enum values are normalized before hashing.

## 2. System and concurrency tables

| Table | Key fields and purpose |
| --- | --- |
| schema_meta | singleton family marker, baseline id, runtime build, canonicalization version |
| schema_migrations | migration id, checksum, applied timestamp, tool version, receipt hash |
| actors | user/service/agent actor, display metadata, status, identity revision |
| teams | team identity, owner actor, status, revision |
| team_memberships | team/actor role, invitation and membership state, grant revision |
| sessions | actor session metadata, expiry, revocation; no session secret |
| credential_refs | provider, external reference, scopes, status, rebind_required, revision |
| provider_profiles | Codex/GitHub/MCP profile metadata and profile snapshot hash |
| aggregate_heads | one row per (aggregate_type, aggregate_id), current revision/hash, last event sequence |
| aggregate_revisions | immutable snapshot per aggregate revision, canonical payload/hash, source operation |
| operations | generic long-running command receipt and lifecycle |
| operation_links | (operation_id, aggregate_type, aggregate_id, relation) links; replaces Assist-specific operation tables |
| events | append-only event log, sequence, aggregate revision, redacted payload/hash |
| event_cursors | consumer/scope cursor for SSE, replay, and workers |
| idempotency_keys | actor, command, key, request hash, result envelope, expiry |
| audit_events | redacted administrative/security audit envelope, linked to an event or operation |

aggregate_heads is the sole head mechanism. Domain tables do not contain a
second *_head_id pointer. A transaction updates the mutable row,
aggregate_heads.current_revision, aggregate_revisions, and events; a
deferred foreign-key check verifies that the revision/hash pair agrees.

## 10. Canonical state machines

### 10.1 Generic operation

~~~text
accepted -> queued -> running -> succeeded | failed | cancelled
                         |
                         -> paused -> running
~~~

Retry creates a new operation linked to the failed operation; it does not
rewrite a terminal receipt. Cancel is accepted once and becomes a terminal
event after the worker acknowledges it.

### 10.2 Project and repository

~~~text
project: draft -> confirming -> active -> archived -> purged
intake: collecting -> submitted -> processing -> ready | failed
repository line: pending -> ready -> faulted -> recovering -> ready | removed
workspace: requested -> provisioning -> ready -> locked -> released | orphaned
~~~

### 10.3 Workflow, execution, and outcome

~~~text
workflow: draft -> proposed -> active -> superseded | archived
generation: queued -> running -> critic_pending -> proposed -> applied
             -> rejected | failed | cancelled
execution: created -> ready -> running -> paused -> completed
           -> completed_with_gaps | failed | cancelled
outcome: pending -> evaluating -> passed | completed_with_gaps | waived | blocked
~~~

### 10.4 Context, Assist, and quality review

~~~text
projection: queued -> running -> completed | failed | cancelled
assist turn: draft -> queued -> running -> awaiting_input -> completed
             -> failed | cancelled
quality: queued -> preparing -> checking -> reviewing -> awaiting_human
         -> completed | failed | cancelled | stale
~~~

Any source asset, workflow rubric, or execution input change marks an active
quality run stale; the old report and human review stay immutable.

### 10.5 Delivery and import

~~~text
delivery: planned -> staging -> checks_pending -> draft_pr -> ready
          -> merged | rejected | failed | needs_reconcile
import: inspected -> dry_run -> running -> checkpointed -> verified
        -> cutover -> completed | failed | rolled_back
~~~

## 11. CAS and Evidence rules

1. The CAS key is sha256(canonical_bytes), independent of host path.
2. A blob is written to a temporary object, fsynced, hashed again, and then
   atomically promoted by hash.
3. asset_versions reference blobs; they never contain unbounded content in
   SQLite.
4. Every Evidence relation carries source asset/version, operation, actor,
   policy revision, and input/output hashes.
5. Secret scanning runs before an asset, event, log, or Evidence record is
   committed. A hit produces a redacted failure receipt.
6. Deleting a logical asset creates a tombstone. CAS garbage collection waits
   for retention, Evidence, backup, and import references to clear.

## 12. Transaction and integrity requirements

Each command transaction performs, in order:

1. begin immediate and establish the request/actor context;
2. load the canonical aggregate and verify project permission;
3. compare expected_revision and idempotency request hash;
4. validate the command and external references;
5. write mutable state, immutable revision, operation link, and head;
6. append redacted event and audit row;
7. store the idempotent result envelope and commit.

Foreign keys, unique constraints, deferred head/hash checks, and a final
PRAGMA foreign_key_check protect the commit. A failing adapter receipt rolls
back the transaction and leaves the operation in a retryable failed state.

## 13. Baseline and migration policy

The clean baseline creates all tables above in migration 001-clean-baseline.
Later migrations are forward-only and carry a checksum. Each migration must
provide a precondition, SQL/application change, postcondition, snapshot
receipt, and rollback rehearsal for deployment artifacts. Rollback restores a
volume and receipt; it does not execute a down migration or recreate a legacy
schema family.

Startup sequence:

~~~text
open -> verify family/checksum -> foreign_key_check -> verify CAS manifest
      -> load policy -> expose /livez -> expose /readyz -> accept API v2
~~~

An old schema, missing checksum, failed foreign-key check, or CAS mismatch
blocks readiness and emits an operations receipt with the importer command.
