# V3 功能恢复开发计划

## 约束

- V2.3 基线 `e18dc0b` 仅作只读行为来源，V3 基线为 `14324a9`。
- 所有公共接口固定使用 `/api/v1`，mutation 使用 `Idempotency-Key` 和资源 revision。
- Broker 保持 Docker CLI 唯一所有者；Runner digest、签名 Job Spec、路径绑定和 Evidence CAS 不降级。
- 恢复批次只在临时目录、临时数据库和动态端口验证，不操作正式 `4317` 实例。
- 功能状态以根目录 `feature-catalog.json` 为准。`planned` 不能作为已恢复能力发布；Terminal 已通过后端 PTY、bundle、浏览器交互和回滚闸门。

## 数据与接口基线

核心热路径继续使用 `projects`、`brief_revisions`、`workflow_revisions`、`executions`、`task_attempts`、`events`、`asset_versions`、`evidence_links` 和 `deliveries`。成熟功能的持久化表已经在同一个 V3 schema 中预留，包含 identity/setup、Assist、Workflow generation/outcome、Repository line、Context projection 和 Quality Review 六组。预留表不自动表示对应行为已完成。

每个新增命令必须返回 V3 error envelope；每个长任务必须产生可 replay cursor 或 operation receipt；Secret 只允许以 credential reference 进入持久层。不得新增旧路由别名、版本后缀 runtime、全局 state snapshot 或独立 MCP 服务。

## 每批交付物

1. 从 V2.3 提取行为，不复制旧运行时文件。
2. 更新 `feature-catalog.json` 的 source、target、table、API、UI、event 和 test 映射。
3. 完成 V3 实现及聚焦测试。
4. 执行 `pnpm recovery:catalog`、`pnpm recovery:coverage` 和 `pnpm recovery:impact --audit`。
5. 执行受影响测试与 `pnpm verify`。
6. 在 `.ai-workspace/recovery` 保存治理 receipt，在 release 目录保存发布/Evidence receipt。
7. 提交实现和可执行反向提交说明；闸门未闭合时保持 `planned` 或 `partial` 描述。

## 完成标准

目录中所有条目都必须达到 implemented，并同时具备聚焦测试、集成测试、浏览器或外部探针证据、发布演练结果和回滚验证。真实 Codex Runner 或 GitHub App 未通过时，发布状态保持 candidate。
