# 系统技术路线说明

> 形成日期：2026-07-23  
> 适用课题：面向超级个体的AIGC协作开发工作流平台设计与实现  
> 说明对象：本系统自身的技术架构、运行机制与验证路线

## 一、对“技术路线”的纠正理解

本任务书中的技术路线是“这个系统如何实现AIGC驱动的协作开发工作流”，不是“本人如何借助Codex开发这个系统”。因此，版本迭代、人工提出需求、Codex辅助编码等研发过程不再作为正文技术路线；它们属于项目实施方法，不能代替系统架构与运行机制。

老师批注指出原路线“看起来是传统工作流”，问题不在于使用Node.js、数据库、权限、幂等或自动化测试，而在于此前没有说明谁负责生成步骤、选择工具和处理不确定结果。如果业务步骤由后端预先写死，AI只在固定节点中被调用一次，那么系统本质上仍是传统工作流引擎。

修正后的核心判断是：

- AIGC负责开放式决策，包括目标理解、动态规划、工具选择、结果观察、反思修正和必要时重规划；
- 确定性程序负责边界控制，包括权限、状态、结构校验、审批、凭据隔离、持久化和失败恢复；
- 两者不是相互替代。系统既不能把固定业务顺序伪装成AIGC编排，也不能把权限和安全边界完全交给概率模型。

## 二、总体架构

系统采用“AIGC编排层 + 确定性控制层”的双层架构。

| 层次 | 主要组成 | 负责内容 | 不负责内容 |
|---|---|---|---|
| AIGC编排层 | LLM Orchestrator、Agent任务、规划器、反思与重规划机制 | 根据目标生成工作流，选择MCP工具，观察执行结果，判断继续、修正或重规划 | 不直接决定权限，不绕过审批，不保存明文凭据 |
| 确定性控制层 | Node.js服务、状态与资产存储、能力目录、策略校验器、审批、Runner Adapter | 校验DAG与输入输出，控制工具权限和执行环境，持久化状态，记录证据，提供恢复与审计 | 不预先写死每类开放式任务的业务执行顺序 |
| 受控执行层 | Codex/其他Runner、MCP Server、Git worktree、Docker或受管本地环境 | 执行代码读取与修改、测试、构建、仓库和外部工具操作 | 不自行扩大任务范围或突破授权边界 |
| 人机协同层 | 工作流画布、Task工作区、审批、Diff Review、人工接管 | 确认目标和正式计划，审批高风险动作，审查差异和最终交付 | 不要求用户手工编排每一个固定节点 |

## 三、系统运行主链路

```text
用户目标、Project Brief、资料、仓库快照、约束和验收标准
  -> LLM Orchestrator理解目标与可用能力
  -> 动态生成Workstream/Task DAG及输入输出、依赖和验收条件
  -> 确定性校验器检查无环、覆盖、依赖完整性和能力可用性
  -> 用户确认正式工作流
  -> 按当前Task动态组装最小充分Context Pack
  -> Agent根据计划和观察自主选择MCP工具或代码执行器
  -> Runner在受控环境执行，返回命令、测试、Diff和错误等观察结果
  -> Agent执行Reflect，选择完成、局部修正、重试或提出Replan
  -> 高风险、低置信度或超限场景进入人工审批或接管
  -> 验收、资产归档、证据记录和最终交付
```

这条链路中的DAG不是开发人员针对每类需求预先配置好的固定模板。系统可以保留通用约束和可复用模式，但具体任务、依赖、工具序列和修正路径由Orchestrator结合当前目标与上下文生成。

## 四、八项基本技术路线

### 1. 目标与上下文建模

将用户目标、Project Brief、需求资料、代码仓库快照、约束条件和验收标准转换为结构化输入，同时维护MCP能力目录。Orchestrator由此理解目标、项目现状、禁止事项和可调用能力，减少只依据一段自然语言直接生成计划所产生的歧义。

### 2. 动态工作流生成

采用Plan-and-Execute方式，由LLM Orchestrator动态生成Workstream/Task组成的DAG，并为节点给出目标、显式输入、直接依赖、预期输出和验收条件。Node.js中的确定性校验器仅检查DAG是否无环、需求是否被覆盖、依赖是否完整、能力是否存在，不替AI决定具体业务步骤。校验通过且经用户确认后，计划才进入正式执行。

### 3. Agent任务与MCP编排

每个Task被建模为带有目标、上下文、可用工具和完成条件的Agent任务。Agent依据当前计划和执行观察决定调用哪个MCP工具、Codex或其他Runner，以及调用顺序。后端提供统一工具入口、参数校验、权限和执行限制，但不把“先调用A再调用B”写死为所有任务共用的流程。

### 4. 动态Context Pack与记忆组织

系统不把全部历史对话直接塞入模型，而是按当前Task，从显式输入、直接依赖、项目决策、相关代码、仓库快照和历史资产中检索、压缩并组装最小充分Context Pack。上下文与任务、版本和依赖变化同步更新，并记录来源，降低信息遗漏、冲突、无关信息干扰和上下文漂移。

### 5. 执行、观察、反思与自我修正

采用“Plan - Execute - Observe - Reflect”循环。Agent执行工具或修改代码后读取命令输出、测试结果、错误、Diff和验收状态，再判断任务是否完成。可恢复问题在限定次数内修正并复测；如果原计划失效、依赖变化或验收条件无法满足，则生成重规划提案。达到重试上限、置信度不足或涉及高风险操作时，停止自主执行并交给用户处理。

### 6. 人机协同与确定性治理

用户确认目标、正式工作流、高风险写入和最终交付，并可以审批、拒绝、撤销或人工接管。Node.js控制层通过权限校验、凭据隔离、受管worktree、幂等、状态持久化、失败恢复和审计记录约束Agent行为。这些机制构成安全边界，但不替代AIGC对开放式任务的动态规划与工具决策。

### 7. 分层测试与AI Eval

测试分为两类：

| 对象 | 验证方法 | 典型内容 |
|---|---|---|
| 确定性控制层 | 单元、集成、端到端、故障与安全测试 | 权限、状态转换、接口、数据、DAG校验、审批、隔离和恢复 |
| 概率性AIGC编排层 | 版本化Eval场景集与重复运行 | 需求覆盖、DAG有效性、工具选择、上下文充分性、验收通过、范围偏离、自我修正和重规划结果 |

Eval固定Brief、仓库快照、模型版本、Prompt版本和能力集合，进行多次运行并报告通过率、波动与失败类型。Prompt、模型、规划器或Context Pack策略变化后执行回归Eval。传统测试没有被删除，而是只用于适合确定性断言的部分；AI输出不再只用“输入A必须逐字得到输出B”的方式评价。

### 8. 集成部署与迭代优化

集成Codex、MCP、Git/GitHub和Docker，通过代表性软件任务、工具失败、上下文缺失、重规划和人工接管等场景验证端到端链路。依据自动化测试、AI Eval和人工Diff Review结果，迭代Prompt模板、规划器、Context Pack选择策略、工具权限、停止条件和交互方式，形成可运行原型、部署文档、测试报告与评测报告。

## 五、与传统工作流的本质区别

| 维度 | 传统工作流 | 本系统的AIGC驱动工作流 |
|---|---|---|
| 拓扑 | 开发时预置固定DAG或状态机 | Orchestrator按目标动态生成并可重规划 |
| 节点执行 | 预设程序执行，AI是其中一个被动API | Task是Agent任务，可基于观察自主选择工具 |
| 工具顺序 | 由后端业务代码固定 | Agent在权限边界内动态决定MCP/Runner调用 |
| 异常处理 | 固定重试、异常分支 | 确定性恢复与Reflect/Self-Correction共同处理 |
| 上下文 | 固定字段或完整对话传递 | 按Task动态检索、压缩和组装Context Pack |
| 测试 | 主要断言固定输入输出 | 工程测试与重复运行的AI Eval分层 |
| 人的角色 | 配置流程并处理异常 | 确认目标与计划，审批风险，审查Diff并可接管 |

## 六、技术边界

动态不等于无约束。动态DAG、Agent工具选择和自我修正都必须受能力白名单、权限、预算、重试次数、停止条件和人工审批约束。反过来，确定性控制也不等于传统工作流：只要Node.js负责的是安全与一致性边界，而开放式业务步骤仍由AIGC按目标规划，系统就保持AIGC驱动属性。
