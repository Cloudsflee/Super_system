# 五个核心评价维度的选择依据

> 形成日期：2026-07-23  
> 研究对象：面向超级个体的AIGC协作开发工作流平台  
> 用途：说明五个核心评价维度的选择理由，以及未将研发效能与资源效率列为核心维度的理由

## 一、结论

本课题选择以下五个核心评价维度：

1. 任务有效性；
2. 工程产物质量；
3. 人机协作与可控性；
4. 过程可信与可追溯性；
5. 平台工程能力。

这五个维度分别回答五个不同问题：

| 核心问题 | 对应维度 |
|---|---|
| 平台是否帮助用户完成了正确的任务 | 任务有效性 |
| 代码、测试、文档等交付物是否合格 | 工程产物质量 |
| 用户是否能够理解、审查和控制AI行为 | 人机协作与可控性 |
| 从需求到交付的过程是否有证据、受约束且可审计 | 过程可信与可追溯性 |
| 平台本身是否可靠、可集成、可替换和可部署 | 平台工程能力 |

本课题没有将“研发效能与资源效率”列为核心评价维度。耗时、Token、重试、工具调用和费用可以记录，但真实AI开发任务很难满足公平比较和因果归因所需的条件。这些数据适合说明某次案例发生了什么、识别运行异常和呈现平台开销，不适合据此宣称平台普遍提高开发效率或降低开发成本。

## 二、维度选择原则

老师批注中提到的范围、开发效率、开发成本和开发质量是帮助思考工程项目能力的方向示例，不是预设的评价框架。本课题按照以下原则确定维度：

### 1. 与课题目标直接对应

评价对象是一个AIGC协作开发工作流平台。维度需要覆盖平台实际承诺的能力：需求和任务保持一致、工程产物达到验收要求、用户保有控制权、执行过程有证据、平台能够稳定运行并连接外部工具。

### 2. 各维度回答不同问题

维度之间需要有明确边界。例如，生成代码中的缺陷属于工程产物质量；平台API失败属于平台工程能力；审批缺失或证据断链属于过程可信与可追溯性。这样可以避免同一问题在多个维度重复计数。

### 3. 能够获得可验证证据

每个维度都应能落到可采集的数据或可复核的材料，而不是只给主观等级。本项目可以使用需求追踪矩阵、验收结果、测试报告、Git记录、交互事件、审批记录、Trace、Asset、契约测试和部署演练作为证据。

### 4. 结论强度与研究条件相匹配

能够记录某项数据，不代表能够公平比较，更不代表能够把观察到的差异归因于平台。核心维度应当在本课题可获得的样本、工具和时间范围内形成有边界的结论。

## 三、资料基础与推导关系

维度不是从老师举例的名词直接拆分，而是综合软件质量、人机协作、AI治理、过程来源和平台工程资料后形成。

| 资料领域 | 代表资料 | 对维度选择的作用 |
|---|---|---|
| 软件与AI系统质量 | ISO/IEC 25010、25023、25059 | 区分功能适合性、可靠性、可维护性、安全性及AI系统质量 |
| 有效性与可用性 | ISO 9241-11 | 区分有效性、效率和满意度，支持任务是否完成及交互是否可用的测量 |
| 人机协作 | Human-AI Interaction Guidelines、适当信任、NASA-TLX、Grounded Copilot | 支持状态理解、人工介入、认知负荷和适当依赖 |
| AI风险与安全 | NIST AI RMF、AI代码生成安全研究 | 支持权限、风险处置、敏感信息和安全质量检查 |
| 来源与过程证据 | W3C PROV、Open Provenance Model | 支持来源关系、证据链、审计、复现和恢复 |
| 智能体与互操作 | Agent综述、ChatDev、SWE-agent、MCP规范 | 支持工作流、工具调用、执行器边界和互操作能力 |
| 开发者生产力研究 | SPACE、DevEx、DORA、GitHub Copilot及METR研究 | 说明生产力具有多维性，并揭示任务、人员、模型和实验条件对效率结论的影响 |

推导链条如下：

```text
平台要证明的能力
-> 为每项能力提出一个独立评价问题
-> 检查该问题是否有明确证据来源
-> 合并语义重叠的指标，分离对象不同的指标
-> 形成五个边界清晰的核心维度
```

## 四、五个核心维度的选择理由

### 1. 任务有效性

**选择理由：** 工作流平台首先需要证明“做的是正确的任务”。如果需求、Task和交付物不一致，即使代码能够运行，也不能说明平台完成了目标。

**主要观察内容：**

- 必需验收条件是否全部通过；
- 需求是否映射到负责的Workflow、Workstream和Task；
- 是否存在未经确认的范围新增、遗漏或错误实现；
- 必需输出是否绑定到可核验的交付证据；
- 任务是否在无需重大返工的情况下完成。

**证据来源：** Project Brief、Node Contract、需求追踪矩阵、Task状态、验收记录、Diff和交付记录。

**边界：** 该维度回答“是否做对了该做的事”，不评价代码内部质量，也不评价平台自身是否稳定。

### 2. 工程产物质量

**选择理由：** 本课题属于软件工程项目，最终产出的代码、测试、文档和交付物必须满足正确性、安全性和可维护性要求。仅检查任务是否完成，无法说明成果是否达到工程质量标准。

**主要观察内容：**

- 单元、集成和端到端验收结果；
- 缺陷数量、严重度和返工情况；
- lint、类型检查、复杂度和重复率等静态质量门禁；
- 依赖漏洞、凭据泄漏和高风险代码问题；
- 接口兼容、模块边界、测试覆盖和变更影响检查。

**证据来源：** 测试报告、静态分析、SAST、依赖扫描、Issue、代码评审和Git记录。

**边界：** 该维度评价任务输出物。平台API故障或Runner崩溃归入平台工程能力，审批缺失或证据断链归入过程可信与可追溯性。

### 3. 人机协作与可控性

**选择理由：** 平台不是完全自动化代码生成器，而是由用户与代码智能体共同完成需求澄清、执行、审查和交付。用户能否理解当前状态、发现AI错误并在必要时接管，是平台价值的重要组成部分。

**主要观察内容：**

- 用户能否理解当前目标、依据、风险、阻塞原因和下一步；
- 澄清、审批、拒绝、撤销、接管和手工修复是否有效；
- Diff Review是否支持用户识别范围偏离和高风险变更；
- 关键交互任务能否完成，错误率和认知负荷是否可接受；
- 用户是否在AI正确时合理利用、在AI错误时进行核验或拒绝。

**证据来源：** 交互事件、审批与决策记录、可用性任务、NASA-TLX、访谈和场景注入测试。

**边界：** 信任不是越高越好。该维度关注适当依赖和实际控制行为，不以“用户是否喜欢AI”替代可控性评价。

### 4. 过程可信与可追溯性

**选择理由：** 本平台的重要特征是把需求、上下文、工具调用、人工决策、测试和交付组织为可追溯证据链。只检查最终代码无法验证执行过程是否受约束，也无法支持审计、复现和失败恢复。

**主要观察内容：**

- 必需节点是否绑定来源、执行、验证和交付证据；
- 敏感写入是否在有效审批后发生；
- Context Pack、仓库快照、工具版本和输出是否可关联；
- checkpoint、幂等重试、回滚和失败恢复是否有效；
- 凭据是否进入前端、Context Pack、Trace、日志或提交；
- 内容哈希、版本和来源关系是否一致。

**证据来源：** Asset、Trace、Workspace Digest、审批日志、工具调用记录、内容哈希、Git记录和故障恢复测试。

**边界：** “有日志”不等于可信。证据需要能够回答来源、顺序、责任、完整性和复现条件。

### 5. 平台工程能力

**选择理由：** 研究成果是一个可运行的软件平台。除了评价平台帮助完成的任务，还需要验证平台自身是否可靠、可集成、可替换和可部署。

**主要观察内容：**

- 关键API和任务执行的成功率、错误处理及恢复情况；
- MCP能力发现、工具调用、取消和错误映射的契约测试；
- Runner Adapter能否隔离具体执行器差异；
- Codex、Git、GitHub和Docker等集成是否可用；
- 并发、锁、幂等、路径隔离和数据迁移是否正确；
- 部署、健康检查、升级和回滚是否能够复现。

**证据来源：** 单元、集成、端到端、契约、负载、迁移和部署演练报告。

**边界：** 固定接口或固定负载下的平台响应时间可以作为平台可靠性测试数据，因为测试对象和条件能够控制；它不等同于真实软件任务的总体研发效率。

## 五、五个维度如何形成完整而不重复的覆盖

| 评价对象 | 核心维度 | 典型证据 |
|---|---|---|
| 任务与需求的一致性 | 任务有效性 | 需求追踪、验收记录 |
| 代码、测试、文档和交付物 | 工程产物质量 | 测试、静态分析、评审 |
| 用户与AI的协作行为 | 人机协作与可控性 | 交互事件、审批、量表、场景测试 |
| 执行过程及来源关系 | 过程可信与可追溯性 | Trace、Asset、哈希、审批日志 |
| 承载工作流的软件平台 | 平台工程能力 | 接口、契约、集成、故障和部署测试 |

五个维度的对象依次是任务、产物、人机关系、过程和平台。对象不同，因此能够覆盖主要工程问题，又不需要把所有数据合成一个缺少理论权重的总分。

## 六、未选择研发效能与资源效率作为核心维度的理由

### 1. 可记录不等于可比较，更不等于可归因

运行数据需要经过三个层次才能支撑平台能力结论：

| 层次 | 需要回答的问题 | 本课题能够达到的程度 |
|---|---|---|
| 可记录性 | 是否能获得时间、Token、重试、费用和状态数据 | 部分数据可以稳定记录 |
| 可比性 | 不同运行的任务、人员、模型、上下文和质量要求是否足够等价 | 真实开发场景中难以充分满足 |
| 可归因性 | 差异是否主要由平台造成，而不是随机性、经验或环境造成 | 小样本条件下难以成立 |

本课题能够较可靠地描述某次运行，却无法仅凭这些数据证明平台普遍提高效率或降低成本。

### 2. 真实软件任务难以等价

两个看起来规模相近的Issue，可能在架构耦合、技术债、测试基础、隐含约束、安全要求和开发者熟悉度上存在实质差异。使用完全相同的任务又会产生学习效应。少量“匹配任务”无法证明比较对象真正等价。

### 3. 模型输出存在随机性和版本漂移

同一模型、提示和仓库快照也可能产生不同计划、检索路径、工具调用和代码结果。模型版本、服务端策略、缓存、reasoning配置、MCP工具和依赖还会持续变化。一次运行之间的差异可能来自随机路径，而不是平台机制。

### 4. 多智能体并行使“时间”没有唯一口径

AI开发至少包含墙钟时间、人工注意力时间和智能体计算时间。多个智能体并行、用户在等待时切换任务后，这三类时间会显著不同。METR在2026年的实验设计说明中也指出，多智能体并行和任务切换使单任务花费时间难以可靠记录。

### 5. 平台与直接工具的交付范围不同

本平台会额外形成Project Brief、Context Pack、审批、Diff Review、测试、Asset、Trace、checkpoint和Git交付证据。若直接工具只生成代码，两种方式得到的结果范围不同，耗时和资源自然不能直接比较；若强制输出完全一致，又会排除平台最重要的治理能力。

### 6. Token和费用不是稳定的跨模型尺度

Token受分词方式、上下文结构、缓存、reasoning和计价规则影响。更完整的上下文可能增加输入Token却减少返工；并行智能体可能缩短墙钟时间却增加计算总量；供应商价格调整也会改变历史费用的含义。因此Token和费用适合诊断具体运行，不适合跨模型、跨时间形成通用排名。

### 7. 毕业设计样本不足以支持普遍因果结论

毕业设计通常只能完成少量代表性案例。软件任务之间的方差很大，模型环境又快速变化。小样本可以证明平台闭环是否可运行、某次案例是否有充分证据，但不足以估计稳定的效率提升比例或长期投资回报。

### 8. 现有研究结果具有明显情境依赖

GitHub Copilot早期研究在特定受控任务中观察到完成速度提升；METR针对有经验开源开发者的2025年研究则曾观察到不同方向的结果。METR在2026年又因智能体使用方式、选择效应和时间记录困难调整实验设计。这些研究并不互相简单否定，而是说明效率结论高度依赖任务、参与者、模型和测量设计，不能直接迁移为本平台的能力结论。

## 七、时间和资源数据的合理用途

未列为核心维度不等于不记录。数据应按用途归类：

| 数据 | 保留方式 | 可以回答的问题 | 不能支持的结论 |
|---|---|---|---|
| 墙钟时间 | 案例背景 | 本次案例持续多久 | 平台普遍更快 |
| 人工审批与审查时间 | 人机协作证据 | 用户在哪些环节介入 | 总体研发效率提升 |
| Token与模型调用 | 运行诊断 | 是否出现上下文膨胀或异常循环 | 跨模型资源效率排名 |
| 重试与工具调用 | Trace诊断 | 失败发生在哪里、如何恢复 | 平台普遍降低开发成本 |
| 当次模型费用 | 注明模型、价格和日期后记录 | 本次运行的直接模型开销 | 长期成本优势或通用ROI |
| 固定API响应时间 | 平台工程测试 | 平台接口在固定条件下是否稳定 | 复杂软件任务的总体效率 |

记录时应注明任务、模型及版本、上下文、工具版本、仓库快照、环境和价格日期，避免脱离条件解释数据。

## 八、报告边界

任务书和论文可以表述：

- 平台记录运行时间、Token、重试、工具调用和人工决策，用于案例复盘与异常诊断；
- 五个核心维度分别使用需求、测试、交互、过程证据和平台测试材料进行评价；
- 场景验证报告同时说明样本、模型版本和外部服务限制。

任务书和论文不应表述：

- 平台将开发效率提高了某个百分比；
- 平台普遍降低了模型费用或总体开发成本；
- 将异质任务的时间或Token简单平均后形成平台排名；
- 用单次案例差异证明平台带来了因果效果。

## 九、可直接用于任务书的表述

> 评价维度按照与课题目标直接对应、相互边界清晰和能够取得可验证证据三项原则确定。依据软件产品质量、人机协作、AI风险治理和平台工程研究，选择任务有效性、工程产物质量、人机协作与可控性、过程可信与可追溯性、平台工程能力五个核心维度，分别回答任务是否做对、产物是否合格、用户能否控制AI、过程能否审计追溯以及平台能否可靠运行。没有将研发效能与资源效率列为核心维度，是因为真实AI开发任务难以等价，模型版本、随机输出和多智能体并行使耗时、Token、重试与费用难以公平比较和归因；相关数据仅用于案例复盘和运行诊断。
