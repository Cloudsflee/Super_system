# 后续行动清单

> 来源：2026-07-23指导教师沟通记录  
> 原则：先完成任务书终稿与文献合规，再同步推进开题报告和原型验证。

## P0：任务书终稿

- [ ] 将题目统一为当前建议版本：“面向超级个体的协作开发工作流平台设计与开源集成”（23字），提交前再次确认学院题目字数规则。
- [ ] 检查任务书正文是否仍使用过大的“AIGC平台”或“通用超级个体”表述，改为与协作开发工作流和开源集成相匹配的边界。
- [ ] 在正文中给出“超级个体”的操作性定义，并说明当前优先验证的软件项目协作开发场景。
- [ ] 明确Codex、GitHub、MCP等是当前可替换的集成对象，不把单一工具写成系统长期价值。
- [ ] 将参考文献精简到确有必要的范围，同时确保总数不少于12篇。
- [ ] 将中文文献控制在3篇以内。
- [ ] 确保参考文献表前3篇均为近三年且与课题高度相关的文献。
- [ ] 按老师给出的格式标准逐篇校验作者、题名、类型、出处、年份、卷期、页码、DOI和URL。
- [ ] 为每篇文献取得合格的原始PDF或正式来源页面。
- [ ] 核对正文中的每个引用观点，记录对应原文页码或章节。
- [ ] 删除无法取得原文、相关性不足、格式无法核准或正文没有实际使用的文献。
- [ ] 完成后向老师提交任务书终稿，不再只提交未经核验的文献清单。

### P0验收条件

- [ ] 题目、中文题名和相关正文表述一致。
- [ ] 文献总数、中文文献数量和前三篇年份符合要求。
- [ ] 每条文献均能打开正式来源或原始PDF。
- [ ] 每条正文引用均能在原文中定位。
- [ ] 著录格式逐条人工复核完成。

## P1：开题报告与翻译

- [ ] 接收并归档老师提供的往届开题报告模板和两份参考材料。
- [ ] 从前三篇高相关文献中优先选择1篇最适合作为翻译来源的正式外文文献。
- [ ] 确认该文献相关性、来源合规性、原始PDF完整性和可引用性。
- [ ] 根据论文结构标记需要翻译的核心章节，并核对学院字数要求。
- [ ] 使用AI生成初译后，由本人逐段校对术语、逻辑、图表引用和结论。
- [ ] 保存原始PDF、翻译稿及原文页码对应关系。
- [ ] 在开题报告中补充“超级个体”定义、研究边界、真实需求依据和工作流验证方法。

## P2：真实需求与原型验证

- [ ] 寻找身边具有真实软件开发或项目协作需求的潜在使用者。
- [ ] 记录其真实目标、现行步骤、使用工具、协作对象、阻塞点和交付标准。
- [ ] 用真实任务走通当前原型，不以演示性的固定流程代替实际过程。
- [ ] 区分应长期固化的信息、可由AI动态生成的步骤和必须人工确认的决策。
- [ ] 收集使用者对工作流形式、上下文保留、MCP调用、进度展示和协作交接的反馈。
- [ ] 根据验证结果修订用户定义、系统范围、工作流模型和验收指标。
- [ ] 保留访谈记录、任务样例、操作过程、问题清单和版本修改证据，供论文使用。

## P3：方法论补课

- [ ] 复习项目管理中需求、范围、风险、进度和利益相关者管理的基本方法。
- [ ] 补充UE、用户旅程、可用性验证和原型测试方法。
- [ ] 复习Sprint及迭代开发方法，并说明其如何落到本项目的版本与验证过程。
- [ ] 区分“开源集成方法”“开发工作流”和“业务工作流”，避免概念混用。
- [ ] 把方法论落实为项目材料和验证证据，不只写成概念说明。
